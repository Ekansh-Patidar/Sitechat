1. app/main.py: building the application

Job: create the FastAPI application object, attach the storage objects ("stores"), add the middleware, register the routes, and serve the widget's files. When Cloud Run starts the container, it runs uvicorn app.main:app, which means "import the module app.main and serve the object called app in it". So the very last line of the file matters:

app = create_app()

Importing the module runs create_app() once and names the result app.

Line by line, the parts that need explaining:

  • A function that builds the app (a "factory") rather than building it at the top of the file. Tests call create_app(tenant_store=InMemoryTenantStore(), ...) to get a fresh app wired to in-memory stores; production calls it with nothing. This is the dependency injection from Phase 0, section 8.12.
  • **docs unpacks a dictionary into keyword arguments. In production it becomes FastAPI(..., docs_url=None, redoc_url=None, openapi_url=None), which turns off the automatic API documentation pages. Locally they stay on (useful for trying routes at /docs). Real output below: /docs returns 200 locally; in production it's 404.
  • app.state is a place FastAPI gives you to hang your own objects on the app. Each route later reads request.app.state.conversation_store, without knowing which kind it is.
  • add_exception_handler(RateLimitExceeded, ...): when a rate limit is exceeded, slowapi raises an exception; this handler turns it into a 429 response with {"error": "Rate limit exceeded: 5 per 1 minute"} instead of a 500.
  • Middleware order. Each add_middleware wraps everything added before it, so the last one added runs first. RequestContextMiddleware is added last so it's outermost: the request id exists before CORS handling, the route and the background tasks run (section 4). CORS is explained in Phase 1, section 9.
  • /health is the simplest possible route: if this answers, the process is alive. It's named /health, not the more common /healthz, because Google's front end intercepts /healthz before it reaches the container (a challenge below).
  • include_router attaches the routes defined in app/api/routes.py and internal.py. mount("/widget", StaticFiles(...)) serves files from the static/ folder as they are, so /widget/widget.js is the chat widget and /widget/test-page.html a page to try it on.

1.2 lifespan: start-up and shut-down

@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()
    setup_logging(settings.log_level, as_json=settings.is_production)

    if settings.sentry_dsn.get_secret_value():
        import sentry_sdk
        sentry_sdk.init(**sentry_options(settings))
        logger.info("Sentry enabled")

    logger.info("Starting up in %s mode", settings.environment)

    # Only build real cloud clients if stores were not supplied.
    # Tests pass their own, so nothing touches Google credentials.
    if not hasattr(app.state, "tenant_store"):
        app.state.tenant_store = FirestoreTenantStore(settings.gcp_project_id)
    ...                                   # the same for the other eight stores

    yield

    logger.info("Shutting down")

A lifespan is code FastAPI runs once when the server starts and once when it stops. The yield is the dividing line: everything before it runs at start-up; then the server serves requests for as long as it lives; everything after it runs at shut-down. @asynccontextmanager is the decorator that turns a function with one yield into that start/stop pair (the same idea as with open(...), from Phase 0).

The important line is if not hasattr(app.state, "tenant_store"): "only create a real Firestore store if nobody supplied one". Tests supply in-memory stores through create_app, so their lifespan creates nothing that needs Google credentials. This exact pattern was added after the very first CI failure, when tests built real Firestore clients and failed on GitHub's machines, which have no credentials.

1.3 sentry_options: error reports without personal data

def sentry_options(settings) -> dict:
    return dict(
        dsn=settings.sentry_dsn.get_secret_value(),
        environment=settings.environment,
        traces_sample_rate=0.1,
        send_default_pii=False,
        include_local_variables=False,
        max_request_body_size="never",
    )

Sentry is a service that collects error reports (stack traces) from the running server. The three privacy settings each close a different leak: send_default_pii=False stops it sending things like IP addresses and cookies; include_local_variables=False stops it attaching every variable's value at each line of the stack (which would include the visitor's message, and sometimes their email); max_request_body_size="never" stops it attaching the request body (the message itself). The second and third were added after testing showed the first alone still sent the visitor's email from a local variable. tests/test_sentry_privacy.py uses the real Sentry library with an in-memory transport to prove nothing personal leaves.

2. app/config.py: every setting, validated once

Job: one class, Settings, that lists every configurable value with its type and default, reads overrides from environment variables (or a local .env file), and checks them all at start-up. A missing or malformed value fails immediately with a clear message, not deep inside a request later.

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    environment: Literal["development", "production"] = "development"
    log_level: str = "INFO"
    gcp_project_id: str = ""
    rate_limit_per_visitor: str = "5/minute"
    ...
    openai_api_key: SecretStr = SecretStr("")
    openai_model: str = "gpt-4o-mini"
    ...

    @property
    def is_production(self) -> bool:
        return self.environment == "production"


@lru_cache
def get_settings() -> Settings:
    """Return the settings, building them only once per process."""
    return Settings()
  • BaseSettings (from the pydantic-settings library) is a Pydantic model that fills itself from the environment. The field openai_api_key is read from an environment variable named OPENAI_API_KEY (case doesn't matter). If it isn't set, the default is used.
  • env_file=".env": locally, values come from a file named .env in the folder you run from. In production there's no file: Cloud Run sets real environment variables, and secrets come from Secret Manager (Phase 6). extra="ignore": unknown variables in .env are ignored rather than an error.
  • Literal["development", "production"]: the only two values allowed. ENVIRONMENT=prod would fail at start-up instead of quietly running with development behaviour.
  • SecretStr: a string that prints as asterisks. A failing test, a logged exception or a Sentry report can print the settings object; with SecretStr the keys don't appear. Code that needs the real value calls .get_secret_value(). Real output: repr(s.openai_api_key) gives SecretStr('**********'), while get_secret_value() gives sk-test-123.
  • @property makes settings.is_production read like a field while being computed.
  • @lru_cache on get_settings means the function's result is remembered: the first call builds Settings() (reading the environment), every later call returns the same object. One settings object per process, created on first use.

3. app/rate_limit.py: the limiter and who a visitor is

Job: create the one shared rate limiter, and decide what "one visitor" and "one tenant" mean for counting. Phase 1, section 10 explained why client_ip reads the last entry of X-Forwarded-For and why IPv6 addresses are grouped by /64. Here's what the rest of the file does.

def site_key(request: Request) -> str:
    """Key for the per-tenant limit. get_tenant has already validated it."""
    return "site:" + request.headers.get("x-site-key", "")


limiter = Limiter(key_func=client_ip)

slowapi is the rate-limiting library. A Limiter counts requests per key and refuses once a key passes its limit within the time window. key_func=client_ip sets the default key: the visitor's address. Individual routes can count by another key, as /chat does with key_func=site_key for its per-tenant limit (section 9). The "site:" prefix keeps tenant counters from ever colliding with visitor counters.

Why its own file? The limiter is used by routes.py (to decorate routes) and by main.py (to attach it to the app). When it lived in main.py, routes.py had to import main, while main imported routes: a circular import, which Python can't resolve (one module ends up half-loaded). Moving the shared object to a third module that both import is the standard fix.

Counters live in memory. There's no storage_uri, so each server process keeps its own counts. Cloud Run may run up to 10 copies ("instances") under load, each counting separately, so the real worst case is 10 times each limit. At today's traffic there's one instance, so the limits are effectively exact. The plan, written in config.py: shared counters (a hosted Redis) once there's regularly more than one instance.

4. app/request_context.py: request ids that follow the work

Job: make every log line say which request, which tenant and which conversation it belongs to, so "show me everything that happened in this conversation" is one search instead of guesswork.

4.1 The problem with a global variable

The obvious approach, a global variable current_tenant = "...", breaks immediately: the server handles many requests at once, so two requests would overwrite each other's value. What's needed is a variable whose value is per request.

4.2 Context variables

request_id: contextvars.ContextVar[str] = contextvars.ContextVar(
    "request_id", default=""
)
tenant_id: contextvars.ContextVar[str] = contextvars.ContextVar(
    "tenant_id", default=""
)
conversation_id: contextvars.ContextVar[str] = contextvars.ContextVar(
    "conversation_id", default=""
)

A ContextVar (from Python's standard contextvars module) is a variable that can hold a different value in each "context". Each request runs in its own context, so tenant_id.set("pyramid-yogshala") in one request is invisible to another. .get() reads the current context's value, or the default.

4.3 The middleware that gives each request an id

class RequestContextMiddleware:
    def __init__(self, app) -> None:
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        token = request_id.set(new_request_id())
        try:
            await self.app(scope, receive, send)
        finally:
            request_id.reset(token)

This is raw ASGI middleware. ASGI is the standard interface between a Python web server (uvicorn) and a web app (FastAPI): an app is anything that can be called with (scope, receive, send), where scope describes the request, receive gets its body and send sends the response. A middleware is an app that wraps another app: it does something, calls the inner app, and does something after.

Here: for HTTP requests (not other connection types), set a fresh 12-character id, run the entire inner app (routing, the route, and the background tasks after the response, which Starlette runs inside this same call), then reset the variable using the token set returned, restoring whatever it was before. try/finally guarantees the reset even if the request fails.

4.4 Threads, and why bound() exists

@contextlib.contextmanager
def bound(tenant: str, conversation: str = ""):
    """Tag every log line inside the block with this tenant and conversation.

    Set where the code runs, not in a dependency: FastAPI runs sync
    dependencies and background tasks in worker threads, each with its own
    copy of the context, so a value set in one is gone in the next.
    """
    tokens = (tenant_id.set(tenant), conversation_id.set(conversation))
    try:
        yield
    finally:
        tenant_id.reset(tokens[0])
        conversation_id.reset(tokens[1])

Sitechat's routes are ordinary (def, not async def) functions, so FastAPI runs each one in a worker thread to avoid blocking the server. Each worker thread starts with a copy of the context. A copy inherits the request id set by the middleware, but anything set inside one thread is lost when it finishes. The first version set the tenant id in the get_tenant dependency, which runs in its own thread, so the value vanished before the route ran: a review found that no production log line had a tenant id at all.

The fix sets values where the work happens: the /chat route sets them at its start (they last for the route's thread), and background work and each digest conversation run inside with bound(tenant, conversation):. One more trap: a new thread pool starts with an empty context, so the orchestrator's parallel retrieval submits its tasks with contextvars.copy_context().run (Phase 4b).

6. app/retention.py: an expiry date on personal data

FIELD = "expire_at"

def with_expiry(data: dict) -> dict:
    """data with expire_at set, or unchanged if retention is off (0 days)."""
    days = get_settings().retention_days
    if days > 0:
        data[FIELD] = datetime.now(timezone.utc) + timedelta(days=days)
    return data

Every write of a conversation, lead or feedback record passes through this, which adds a date 365 days ahead. A Firestore TTL policy on expire_at (set up once with gcloud, in notes/retention-setup.md) deletes documents after that date. Because each write moves the date, an active conversation keeps living; a quiet one disappears a year after its last activity. It must be a real date object, not text: Firestore only honours TTL on real timestamps, which is why it's added after model_dump(mode="json") has turned the model's own dates into strings. Phase 4e shows where it's called, and tests/test_retention.py fails if any full write forgets it.

7. app/api/schemas.py: the shapes going in and out

Phase 1, section 8 walked through ChatRequest and ChatResponse as an API contract. What's left is how validation works and the two other models.

class ChatRequest(BaseModel):
    message: str = Field(min_length=1, max_length=2000)

    @field_validator("message")
    @classmethod
    def _visible_only(cls, value: str) -> str:
        value = strip_invisible(value)
        if not value.strip():
            raise ValueError("Message is empty")
        return value

    conversation_id: str | None = Field(
        default=None, pattern=r"^[A-Za-z0-9-]{1,64}$"
    )
  • Field(min_length=1, max_length=2000): Pydantic rejects an empty or over-long message before any of our code runs; FastAPI turns that into a 422 response listing what's wrong.
  • @field_validator("message") runs our own function after the type checks. It removes invisible characters (Phase 3, section 17) and refuses a message that was nothing but invisible characters. Whatever it returns becomes the field's value, so the rest of the app only ever sees the cleaned message. @classmethod is required by Pydantic for validators: it receives the class, not an instance.
  • The conversation_id pattern allows 1 to 64 letters, digits and hyphens. Two reasons, both learned the hard way: a / splits a Firestore document path and caused a 500, and __ is the separator between tenant and conversation in document ids. Server-issued ids (uuid4, e.g. 1f1a1dca-710d-...) always match.

8. app/api/dependencies.py: who is this request for?

Job: the get_tenant function, which runs before the route on every /config, /chat and /feedback request. It turns the site key into a tenant, refuses inactive tenants and wrong domains, and protects the database from floods of made-up keys. Phase 1 explained the Origin check (_origin_allowed, dot-boundary matching). Here's the rest.

8.1 FastAPI dependencies

A route declares tenant: Tenant = Depends(get_tenant). Before calling the route, FastAPI calls get_tenant, giving it what it asks for: the Request, and headers by name (x_site_key: str = Header(...) reads X-Site-Key; ... means required, so a missing header is a 422). If it raises HTTPException, the route never runs and the client gets that status. If it returns, the route receives the tenant. Write the check once, use it on every route.

8.2 The cache, including "not found"

# site_key -> (tenant, or None for a key that matched none, time cached).
_cache: dict[str, tuple[Tenant | None, float]] = {}

MAX_SITE_KEY_LENGTH = 64
MAX_CACHED_KEYS = 10_000


def _cached_lookup(store: TenantStore, site_key: str) -> Tenant | None:
    ttl = get_settings().tenant_cache_seconds
    now = time.monotonic()

    entry = _cache.get(site_key)
    if entry and (now - entry[1]) < ttl:
        return entry[0]

    tenant = store.get_by_site_key(site_key)
    if len(_cache) >= MAX_CACHED_KEYS:
        _cache.clear()
    _cache[site_key] = (tenant, now)
    return tenant
  • Looking a tenant up in Firestore on every message would cost a database read each time. The cache keeps each answer for 60 seconds (tenant_cache_seconds). The trade-off: a change to a tenant (say, a new allowed domain) takes up to a minute to apply.
  • time.monotonic(), not the clock time: a monotonic clock only moves forward, so a computer adjusting its clock can't make a cache entry live forever or expire early.
  • "Not found" is cached too (the None). Originally only found tenants were cached, so a loop sending made-up keys was one Firestore read per request: enough to burn through the 50,000 free daily reads and start billing. Now repeating a made-up key costs one read per minute.
  • Two memory guards: keys longer than 64 characters are refused without a lookup (real keys are short), and if made-up keys ever fill the cache to 10,000 entries it's cleared, so a flood can't grow memory without bound.

8.3 Counting refusals against the visitor

def _reject(request: Request, code: int, detail: str) -> NoReturn:
    """Refuse the request, counting it against the visitor."""
    limiter.limiter.hit(_rejected_limit(), "rejected", client_ip(request))
    raise HTTPException(status_code=code, detail=detail)


def get_tenant(request: Request, x_site_key: str = Header(...),
               origin: str | None = Header(default=None)) -> Tenant:
    store: TenantStore = request.app.state.tenant_store

    if not limiter.limiter.test(_rejected_limit(), "rejected", client_ip(request)):
        raise HTTPException(status_code=429, detail="Too many requests")

    tenant = None
    if len(x_site_key) <= MAX_SITE_KEY_LENGTH:
        tenant = _cached_lookup(store, x_site_key)
    if tenant is None:
        logger.warning("Unknown site key")
        _reject(request, status.HTTP_401_UNAUTHORIZED, "Invalid site key")

    if not tenant.is_active:
        _reject(request, status.HTTP_403_FORBIDDEN, "This chat is not currently available")

    if not _origin_allowed(tenant, origin):
        logger.warning("Blocked origin %s for tenant %s", origin, tenant.tenant_id)
        _reject(request, status.HTTP_403_FORBIDDEN, "This domain is not allowed to use this site key")

    return tenant

Here's a subtle ordering problem. slowapi's route limits run after dependencies. So a request refused by get_tenant never reached the limiter and was never counted: a script could send unlimited bad requests, each costing a lookup. The fix uses the limiter's lower-level object directly (limiter.limiter, from the limits library): hit adds one to a counter, test asks "would one more be allowed?" without adding. Every refusal is a hit under the key ("rejected", visitor); every request first tests it. Past 20 refusals a minute, the visitor is refused before the lookup, even with a valid key. NoReturn tells the type checker _reject always raises, so it knows tenant can't be None after it.

9. app/api/routes.py: /config, /chat, /feedback

The file's opening comment states its boundary: "HTTP concerns only: tenant resolution, rate limits, mapping model failures to a 503 and scheduling background work. What a reply is made of lives in app/agent/orchestrator.py."

9.1 GET /config

@router.get("/config", response_model=WidgetConfig)
@limiter.limit(lambda: get_settings().rate_limit_config_per_visitor)
def get_config(request: Request, tenant: Tenant = Depends(get_tenant)) -> WidgetConfig:
    return WidgetConfig(
        display_name=tenant.display_name,
        greeting=tenant.greeting,
        suggested_questions=tenant.suggested_questions,
        accent_colour=tenant.accent_colour,
        privacy_url=str(tenant.privacy_url) if tenant.privacy_url else None,
    )
  • Two decorators, order matters. Decorators apply bottom-up: @limiter.limit wraps the function first, then @router.get registers the wrapped version as the route. slowapi requires this order, and requires the function to take a request: Request parameter (it reads the visitor's address from it).
  • A lambda as the limit: a tiny function that returns the limit string when called. slowapi calls it per request, so the limit is read from settings at that moment rather than frozen at import time (which helps tests change it).

9.2 POST /chat

def _tenant_limit(key: str) -> str:
    tenant = cached_tenant(key.removeprefix("site:"))
    if tenant is not None and tenant.rate_limit:
        return tenant.rate_limit
    return get_settings().rate_limit_per_tenant


@router.post("/chat", response_model=ChatResponse)
@limiter.limit(lambda: get_settings().rate_limit_per_visitor)
@limiter.limit(_tenant_limit, key_func=site_key)
def chat(request: Request, body: ChatRequest, background: BackgroundTasks,
         tenant: Tenant = Depends(get_tenant)) -> ChatResponse:
    conversation_id = body.conversation_id or str(uuid.uuid4())
    reply_id = uuid.uuid4().hex[:16]
    store = request.app.state.conversation_store
    fact_store = request.app.state.fact_store

    # Lasts for this worker thread, which runs the whole reply.
    request_context.tenant_id.set(tenant.tenant_id)
    request_context.conversation_id.set(conversation_id)
    logger.info("Chat request")

    lead_store = request.app.state.lead_store
    # Before the turn, so the card shows only on the turn that placed it.
    was_waiting = request_is_waiting(lead_store, tenant.tenant_id, conversation_id)

    try:
        reply, _, stored_message = generate_reply(
            tenant, conversation_id, body.message, store, fact_store,
            request.app.state.vector_store, request.app.state.chunk_store,
            request.app.state.lead_store,
            programme_store=getattr(request.app.state, "programme_store", None),
            usage_store=getattr(request.app.state, "usage_store", None),
        )
    except LLMError as exc:
        raise HTTPException(status_code=503, detail=exc.user_message) from exc

    background.add_task(after_reply, tenant, conversation_id, stored_message, reply,
                        store, request.app.state.lead_store, get_settings(), reply_id)

    return ChatResponse(
        reply=reply,
        conversation_id=conversation_id,
        confirmation=request_confirmation(tenant, lead_store, conversation_id, was_waiting),
        reply_id=reply_id,
    )

Step by step:

  1. Two limits. Per visitor (5 a minute, keyed by address) and per tenant (keyed by site:<key>, with the limit from _tenant_limit: the tenant's own rate_limit such as "300/hour" if set, else 60/hour). Sizing a customer's limit is a data change, not a deploy. Real output, one visitor sending 7 chats in a row: [200, 200, 200, 200, 200, 429, 429] with {"error":"Rate limit exceeded: 5 per 1 minute"}.
  2. Ids. A new conversation gets a uuid4 (random, practically unique). Every reply gets a 16-character reply_id, which the widget sends back with thumbs up/down.
  3. Log context is set for this thread (section 4).
  4. was_waiting is read before the reply: was a contact request with contact details already waiting? After the reply, the same question is asked again; the confirmation card is shown only if the answer changed from no to yes on this turn. Otherwise the card would reappear on every later message.
  5. The reply. All the AI work is one call, generate_reply (Phase 4b). It returns three things; the middle one (retrieved passages, used by the evaluation) is ignored here with _. stored_message is the visitor's message with contact details removed, which is what gets stored. getattr(..., None) tolerates apps built without those two stores (older tests).
  6. AI failure → 503. LLMError carries a message written for visitors ("We're a bit busy right now..."). raise ... from exc keeps the original error attached for logs and Sentry. The 503 status lets monitoring count failures that a 200 would hide (Phase 1, section 7).
  7. Background work. background.add_task(after_reply, ...) schedules a function to run after the response has been sent: storing the turn, summarising, emailing the team. The visitor doesn't wait for any of it. after_reply is the subject of Phase 4b.

9.3 POST /feedback

@router.post("/feedback", status_code=status.HTTP_204_NO_CONTENT)
@limiter.limit(lambda: get_settings().rate_limit_feedback_per_visitor)
def feedback(request: Request, body: FeedbackRequest,
             tenant: Tenant = Depends(get_tenant)) -> None:
    store = getattr(request.app.state, "feedback_store", None)
    if store is None:
        return
    store.save(Feedback(
        tenant_id=tenant.tenant_id,
        conversation_id=body.conversation_id,
        reply_id=body.reply_id,
        rating=body.rating,
        reason=body.reason if body.rating == "down" else None,
    ))

204 No Content means "done, nothing to send back". A reason is kept only with a thumbs down (changing from down to up clears it). Feedback changes nothing the bot does; it's for reviewing replies with scripts/feedback.py. Only ids are stored, because the reply itself is written in the background and a quick tap can arrive before it exists.

10. app/api/internal.py: the endpoint only Google may call

Job: POST /internal/lead-digest, called every 5 minutes by Google Cloud Scheduler. It sends due lead emails (Phase 4b) and refreshes any tenant's facts more than a day old (Phase 4e). The problem: the service must be public (the widget needs it), so how do you make one route callable only by Google's scheduler?

def require_scheduler(authorization: str | None) -> None:
    settings = get_settings()
    if not settings.lead_digest_invoker:
        # Off until configured: indistinguishable from no endpoint at all.
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND)

    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED)
    try:
        claims = _verify_identity_token(
            authorization.removeprefix("Bearer "), settings.lead_digest_audience
        )
    except Exception:
        logger.warning("Lead digest: invalid identity token")
        raise HTTPException(status_code=status.HTTP_401_UNAUTHORIZED) from None

    if claims.get("email") != settings.lead_digest_invoker or not claims.get("email_verified"):
        logger.warning("Lead digest: token from %s refused", claims.get("email"))
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN)

Cloud Scheduler is configured to attach an OIDC identity token to each call: a short-lived, signed statement from Google saying "this request comes from the service account lead-digest@..., intended for the audience sitechat-lead-digest". The checks, in order:

  1. Not configured → 404. Until LEAD_DIGEST_INVOKER is set, the route pretends not to exist. Real output: 404 {'detail': 'Not Found'}.
  2. No token → 401. The Authorization header must be Bearer <token>.
  3. Signature, expiry and audience. id_token.verify_oauth2_token (Google's library) checks the token was signed by Google's published keys, hasn't expired, and was issued for our audience. A token made for another service is refused, so a token leaked from elsewhere can't be replayed here. Any failure → 401. from None hides the library's internal error from the chain, since the log line says what matters.
  4. Right account → else 403. The token is real, but is it our scheduler? The email in it must equal the configured invoker, and be verified.

No password or shared secret is stored anywhere: the trust comes from Google's signature. The route then calls send_due_digests and sync_stale_facts and returns their counts, which appear in the log as Lead digest sweep: {'due': ..., 'sent': ...}.

Say it in an interview

"The service is public because the widget needs it, so the internal endpoint authenticates the caller cryptographically: Cloud Scheduler attaches a Google-signed OIDC token, and we verify the signature, expiry and audience, then require the token's email to be the one service account allowed. No shared secret to leak or rotate. And until it's configured, it returns 404, so it isn't even discoverable."

11. The order everything runs in

For one POST /chat, the layers in order. Each refusal happens before anything more expensive:

  1. RequestContextMiddleware: a new request id.
  2. CORSMiddleware: answers preflights; adds the CORS header to the response.
  3. Routing: POST /chat → chat.
  4. Dependencies: get_tenant (refusal limit, key, active, domain). Then the body is parsed into ChatRequest (422 if invalid). Checked for real in Phase 1: a bad key plus an empty message gives 401, so the dependency runs first.
  5. slowapi route limits: per visitor, per tenant (429).
  6. The route body: generate_reply (the only step that costs money), 503 on AI failure.
  7. The response is sent.
  8. Background: after_reply, still inside the middleware's call, so its log lines carry the request id.

12. Challenges we faced

1. The circular import

What happened: main.py imported the router from routes.py, and routes.py imported the limiter from main.py. Python loads a module top to bottom; when routes asked for main.limiter, main was only half-loaded and the name didn't exist yet. Fix: the limiter moved to its own module, app/rate_limit.py, which both import. Lesson: shared objects go in a module that depends on neither user.

2. Three commits to fix one duplicated line

What happened (12 Oct): during an edit, the router and the static files mount were registered twice in create_app. Two mounts on the same path broke the app, with the confusing error 'NoneType' object is not callable and "ASGI 'lifespan' protocol appears unsupported". While removing the duplicates, the module-level app = create_app() line was deleted too, giving Attribute "app" not found in module "app.main". The fix took three commits with the same message. Lesson (recorded in the notes): for a file edited many times, look at the whole file, not a description of the edit; and check for unsaved files before testing (it cost about an hour more than once).

3. /healthz returned Google's 404

What happened: the health route was called /healthz (a common convention) and returned 404 on Cloud Run. The clue: the 404 page was Google's HTML, not FastAPI's {"detail":"Not Found"} JSON, so the request never reached the container. Cloud Run's front end reserves that path. Fix: renamed to /health; it worked immediately. Lesson: read whose error page you're looking at.

4. Every visitor was one visitor

What happened: the limiter first keyed on request.client.host. On Cloud Run that is Google's front end, 169.254.169.126, for every visitor, so all visitors shared one bucket: five messages a minute for the whole world. Nobody knew for sure what the headers looked like in production, so a temporary log line recorded them, it was deployed, and the real shape was read before choosing. Fix (15 Oct): client_ip takes the X-Forwarded-For entry trusted_proxy_hops from the end (1, measured), with IPv6 grouped by /64; the per-tenant limit, defined but never applied, was applied. Lesson: when you don't know what production sends, measure it before writing the code.

5. A slash in a conversation id crashed the request

What happened: conversation_id was unchecked client input going straight into Firestore document ids. A / made an odd-length document path and a 500. Fix: the pattern ^[A-Za-z0-9-]{1,64}$, which also keeps out __, the tenant separator. Lesson: anything a client sends that ends up in a key or path must be validated at the edge.

6. No log line had a tenant id

Section 4.4: values set in a sync dependency vanished because it ran in its own thread with a copied context. Found by a review checking production logs, not by any test, so a test now checks every line of a chat carries its ids (tests/test_log_context.py).

7. Bad keys could run up the database bill

Section 8: unknown keys weren't cached, /config had no limit, and refusals were never counted because route limits run after dependencies. Fixed with negative caching, a /config limit, the refusal counter and key-length and cache-size guards.

8. Smaller hardening from the 16 Oct review
  • API docs public in production: /docs listed /internal/lead-digest to anyone. Not exploitable alone, but it published the attack surface. Now off in production (a test checks).
  • Keys printable: API keys were plain strings, so a printed settings object would show them. Now SecretStr (a test checks they don't appear when printed).
  • Sentry received personal data: confirmed by test before fixing (section 1.3).

Glossary

Factory function
A function that builds and returns a configured object (create_app).
Lifespan
Code run once when the server starts (before yield) and once when it stops (after).
Middleware
A layer wrapping the whole app, run for every request before and after the route.
ASGI
The standard interface between Python web servers and apps: an app is called with (scope, receive, send).
uvicorn
The server program that runs the FastAPI app and speaks HTTP.
Router
A group of routes defined in one file and attached to the app.
Dependency (FastAPI)
A function FastAPI runs before a route, declared with Depends; its return value is passed in.
Decorator
A function that wraps another; written @name above it. Stacked decorators apply bottom-up.
pydantic-settings / BaseSettings
A Pydantic model that fills itself from environment variables and .env.
SecretStr
A string type that prints as asterisks.
lru_cache
A decorator that remembers a function's result so later calls return it without recomputing.
ContextVar
A variable with a separate value per request (per context).
Worker thread
A separate thread FastAPI runs sync functions in, so the server isn't blocked.
Monotonic clock
A clock that only moves forward; used for measuring durations.
Negative caching
Remembering that something was not found, to avoid looking again.
BackgroundTasks
FastAPI's way to run work after the response is sent.
OIDC identity token
A short-lived token signed by Google naming who is calling and for which audience.
Audience
The intended recipient named inside a token; tokens for other audiences are refused.
Circular import
Two modules importing each other, which Python can't resolve cleanly.
TTL policy
A Firestore rule deleting documents after the date in a named field.

Check yourself

Why is app = create_app() at the bottom of main.py essential, and why is create_app a function at all?

uvicorn is started with app.main:app, so it imports the module and looks for the name app; without that line it fails to start. It's a function so tests can build fresh apps wired to in-memory stores.

In lifespan, what does if not hasattr(app.state, "tenant_store") protect against?

Building a real Firestore client when a test already supplied an in-memory store. Without it, tests would need Google credentials and fail in CI.

Why is RequestContextMiddleware added last?

The last middleware added is the outermost, so it runs first and its context covers everything inside: CORS, the route and the background tasks.

A tenant id set inside get_tenant didn't appear in logs. Why?

Sync dependencies run in a worker thread with a copied context; values set there are lost when it finishes. The value must be set where the work runs.

Why does get_tenant count refusals itself instead of relying on @limiter.limit?

Route limits run after dependencies, so a request refused by the dependency never reached them and was never counted.

Why cache "not found" for unknown site keys?

Otherwise each request with a made-up key is a Firestore read, so a loop could exhaust the free tier. Cached, it's one read per key per minute.

A company wants 300 chats an hour. What changes: code, config or data?

Data: set rate_limit="300/hour" on their tenant record. _tenant_limit reads it from the cached tenant.

Someone copies a valid OIDC token Cloud Scheduler made for a different service. Can they call the digest?

No. The token's audience must be sitechat-lead-digest, and its email must be our lead-digest account.

Why does WidgetConfig exist when the route could return the tenant object?

As the response_model, it limits the response to public fields, so the team email or facts sheet id can't leak.
