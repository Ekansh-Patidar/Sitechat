1. Three computers, one conversation

The first thing to get right is who talks to whom. Most people picture "the yoga school's website talks to the chatbot". That's wrong, and the wrong picture makes everything later confusing. There are three separate computers, owned by three different parties:

Computer 1 · the visitor'sThe browser

Chrome or Safari on the visitor's phone or laptop. It's the only one that talks to both of the others.

Computer 2 · the school'sThe school's web server

Hosts pyramidyogshala.com: the pages, the photos. It hands the browser one extra line of HTML, the <script> tag. After that it plays no part in the chat.

Computer 3 · oursSitechat's server

Runs on Google Cloud Run at sitechat-api-uukevi3qpq-uc.a.run.app. It sends the browser the widget's code, and answers every chat message.

Here's the order things happen in:

  1. The visitor opens pyramidyogshala.com. The browser asks the school's server for the page and gets HTML back. Somewhere near the bottom of that HTML is this line, which the school pasted in once (from notes/install-guide.md):

    <script src="https://sitechat-api-uukevi3qpq-uc.a.run.app/widget/widget.js"
        data-site-key="pk_YOUR_KEY"></script>

  2. The browser sees src= pointing at our server, so it asks our server for widget.js and runs it inside the school's page. That JavaScript draws the chat bubble.

  3. From then on, every chat message goes straight from the browser to our server. The school's server never sees a single chat message. It doesn't even know the chat exists.

Analogy

The school's website is a shop. The shop owner sticks a "Questions? Call this number" sticker by the door (the script tag). A customer who wants help dials the number from their own phone (the browser) and talks to a call centre in another city (our server). The shop owner never hears the call. Everything interesting in this phase is about that phone line: how the number is looked up, what language the call is in, and the rules the phone itself enforces.

In Sitechat

This is why a school can install Sitechat by pasting one line, on any kind of website (WordPress, Wix, hand-written HTML): nothing has to run on their server. It's also why the browser's security rules (section 9) matter so much. JavaScript loaded from our server is running inside their page and talking back to us, and browsers are deeply suspicious of exactly that pattern.

2. Clients, servers, requests and responses

Every exchange on the web has the same shape. One program, the client, sends a request. Another program, the server, sends back exactly one response. Then that exchange is over.

Client (browser)request →Server (Sitechat)response →Client

Three rules follow from this shape, and each one shows up in Sitechat's design.

Rule 1: the server only ever answers; it never starts

A server can't reach out to a browser and say "here's a new message for you". It can only reply to a request it has received. That's why the bot can't send a message on its own after the visitor goes quiet: the widget would have to ask first. (There are ways around this, like WebSockets, but Sitechat doesn't need them and doesn't use them.)

The same rule applies to our server's own timed jobs. Sitechat must email the school about leads that went quiet, but a server that only answers can't wake itself up to do it. So Google Cloud Scheduler acts as a client: every 5 minutes it sends a request to POST /internal/lead-digest, and the server does the email sweep as its response. A timer outside, a request inside.

Rule 2: one request, one response, and a deadline

The browser waits for the response. While Sitechat is working out the answer (searching documents, calling OpenAI), the request is "open" and the visitor sees the waiting dots. Google Cloud Run gives up on any request still open after 60 seconds (--timeout=60 in cloudbuild.yaml). That's why the AI settings are sized to fit inside that window: 15 s per OpenAI attempt, and a 40 s budget for the whole reply.

Work that doesn't need to finish before the visitor sees the answer (saving the conversation, emailing the school) runs after the response has been sent, as a background task. You'll see the exact line in section 12.

Rule 3: each request stands alone ("stateless")

The server doesn't remember a browser between requests. When the second message arrives, nothing about the request itself says "this is the same person as two minutes ago", unless the client says so. So the client has to carry something that identifies the conversation, every time. In Sitechat that's the conversation_id:

  • On the first message, the widget sends no id. The server makes one up (a random UUID, like 0cbf3d1f-5267-4a7d-a7d2-840df5cc3fc2) and sends it back with the reply.
  • The widget saves it in the browser and includes it in every later message. The server uses it to load that conversation's history from the database.

app/api/routes.py

conversation_id = body.conversation_id or str(uuid.uuid4())

Read it as: "use the id the widget sent; or, if it sent none, make a new random one". In Python, None or x gives x.

Why not use a cookie, the usual way websites remember you? A cookie belongs to the site that set it. The chat runs on the school's site but talks to ours, so our cookie would be a third-party cookie, and browsers increasingly restrict those (Safari blocks them; Firefox keeps a separate cookie jar for each site, so ours set on one school's site isn't seen anywhere else), because advertisers used them to follow people from site to site. An id that the widget stores and sends itself works in every browser.

Analogy

A call centre with no caller ID, where every call is picked up by whichever agent is free. The first agent gives you a ticket number. Every time you call back, you read out the ticket number, and the agent pulls up your file. The agents remember nothing; the file and the number do all the remembering.

3. Finding the server: IP addresses, ports, DNS

The script tag says sitechat-api-uukevi3qpq-uc.a.run.app. That's a name for people. Computers on the internet find each other by number.

IP addresses

Every machine reachable on the internet has an IP address. There are two kinds:

  • IPv4: four numbers from 0 to 255, like 34.143.72.2. There are only about 4 billion of these, which isn't enough for every device in the world.
  • IPv6: the newer, much longer kind, like 2600:1900:4242:200::. There are enough of these for every device many times over.

DNS: turning the name into a number

Before the browser can send anything, it asks the Domain Name System (DNS), the internet's phone book: "what is the address of sitechat-api-uukevi3qpq-uc.a.run.app?" I asked it from this laptop, and this is the real answer (the end of it):

> nslookup sitechat-api-uukevi3qpq-uc.a.run.app
	  34.143.72.2
	  34.143.78.2
	  34.143.77.2
	  34.143.76.2
	  34.143.74.2

Several addresses, not one, and none of them is "our computer". They belong to Google's front end: a fleet of Google machines that receive traffic for every Cloud Run service, check it, and pass it on to the right container. Our code runs somewhere behind them, and we never learn exactly where. You'll see Google's front end announce itself (server: Google Frontend) in a real response in section 5. It matters again in section 10, because it changes how we tell visitors apart.

DNS answers are cached (remembered) by the browser and the operating system for a while, so this lookup happens once, not on every message.

Ports: which program on that machine

One machine can run many programs that listen for requests. A port is a number from 0 to 65535 that says which program you want. Two are so common they're usually left out of addresses:

PortUsed forIn Sitechat
443HTTPS (encrypted web traffic)Every visitor's request to the live server. Not written in the URL, because https:// implies 443.
80HTTP (unencrypted)Not used.
8080A common choice for programs under developmentWhere uvicorn listens: on your laptop (uvicorn app.main:app --port 8080), and inside the container on Cloud Run, where Google's front end forwards each request to it.

localhost: your own machine

localhost is a special name that always means "this same computer" (address 127.0.0.1). When you run Sitechat on your laptop and open http://localhost:8080/widget/test-page.html, the browser and the server are two programs on one machine, talking through port 8080. Nothing leaves the laptop.

Dockerfile

CMD exec uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8080} --workers 1

--host 0.0.0.0 means "accept connections that arrive through any of this machine's network connections". The alternative, 127.0.0.1, would mean "only from programs on this same machine". Inside a container that difference is everything: Google's front end is outside the container, so a server listening only on 127.0.0.1 would never hear it. ${PORT:-8080} means "the port Cloud Run gives us in the PORT environment variable, or 8080 if there isn't one".

Analogy

The domain name is a company's name. DNS is directory enquiries, which gives you the switchboard number (the IP address). The port is the extension: the same building has a reception desk (443) and a workshop (8080).

4. URLs and origins

A URL (Uniform Resource Locator) is the full address of one thing on the web. Here's the real one from the script tag, taken apart:

PartIn our URLWhat it means
SchemehttpsThe rules (protocol) for the conversation: HTTP, encrypted. Section 11.
Hostsitechat-api-uukevi3qpq-uc.a.run.appThe name that DNS turns into an address. Read it right to left: app is the top-level domain, run.app is Google's domain for Cloud Run, and the rest names our one service: sitechat-api, a code Google chose, and uc for the region (us-central).
Port(not written, so 443)Which program on that host.
Path/widget/widget.jsWhich thing on that server. Section 8 shows how each path maps to Python code.

Two more parts appear in other URLs:

  • A query string after ?: extra named values, like /search?q=yoga&page=2. Sitechat's public API doesn't use them; everything goes in headers and the body.
  • A fragment after #: a place within the page. Phase 0's "Updated" note links to #abc, which jumps to section 8.12. The browser never sends the fragment to the server; only the browser uses it.

The origin: the most important idea in this phase

An origin is the first three parts together: scheme + host + port. The path is ignored. The browser uses the origin to decide "is this the same website or a different one?", and all of its security rules (section 9) are built on that one decision. Two URLs have the same origin only if all three parts match exactly:

Compared with https://pyramidyogshala.comSame origin?Why
https://pyramidyogshala.com/coursesYesOnly the path differs.
https://www.pyramidyogshala.comNoDifferent host: www. makes it a different name.
http://pyramidyogshala.comNoDifferent scheme (and so a different port: 80, not 443).
https://pyramidyogshala.com:8443NoDifferent port.
https://sitechat-api-uukevi3qpq-uc.a.run.appNoA completely different host: that's us.

So when the chat bubble, running in a page from https://www.pyramidyogshala.com, sends a message to https://sitechat-api-uukevi3qpq-uc.a.run.app, that's a cross-origin request. Hold on to that phrase; section 9 is all about it.

In Sitechat

The widget works out our server's origin from its own script tag, so the address is written in only one place (the tag the school pasted):

static/widget.js

var script = document.currentScript;               // the <script> tag running this code
var siteKey = script && script.getAttribute("data-site-key");
var API = new URL(script.src).origin;              // "https://sitechat-api-uukevi3qpq-uc.a.run.app"

new URL(...) takes a URL apart into its pieces, and .origin puts the first three back together. On your laptop the same line gives http://localhost:8080, so the identical file works locally and live with no changes. This is also why the install guide says not to add async to the tag: document.currentScript is empty for scripts loaded that way, so the widget couldn't find its own tag, its site key or our address.

The origin also decides where the browser keeps saved data. The widget saves the conversation_id in localStorage, a small store inside the browser, for 30 days:

static/widget.js (shortened)

var STORAGE_KEY = "sitechat:" + siteKey;
var MAX_AGE_MS = 30 * 24 * 60 * 60 * 1000;          // 30 days in milliseconds
...
localStorage.setItem(STORAGE_KEY, JSON.stringify({ id: id, at: Date.now() }));

localStorage belongs to the page's origin, and the widget runs inside the school's page. So the id is stored under https://www.pyramidyogshala.com, not under our server. A visitor who comes back on https://pyramidyogshala.com (no www.) is, as far as the browser is concerned, on a different origin with separate storage, and starts a fresh conversation.

5. HTTP: what actually travels

HTTP (HyperText Transfer Protocol) is the agreed format for requests and responses. In its classic form (HTTP/1.1) a request is just lines of text. Here is the chat request the widget sends, written out exactly as it travels (inside the encryption of section 11). The browser adds a few more headers, left out here:

POST /chat HTTP/1.1
Host: sitechat-api-uukevi3qpq-uc.a.run.app
Origin: https://www.pyramidyogshala.com
Content-Type: application/json
X-Site-Key: pk_pyramid_yogshala_001
Content-Length: 46

{"message":"How much is the 200-hour course?"}

A request always has the same four parts, in this order:

  1. The request line: POST /chat HTTP/1.1. The method (what kind of action), the path (which thing), and the version of HTTP.
  2. Headers: one per line, Name: value. Information about the request: who it's for, what format the body is in, how long the body is.
  3. A blank line. This is how the server knows the headers have ended.
  4. The body: the actual content, here the visitor's message as JSON. It's exactly 46 characters long, which is why the header says Content-Length: 46: the server reads exactly that many bytes and knows the request is complete.

The response has the same layout, with a status line instead of a request line. This is the real response from Sitechat running locally (with a stand-in reply text), plus two headers that Google's front end adds on the live server:

HTTP/1.1 200 OK
content-type: application/json
access-control-allow-origin: *
content-length: 161
server: Google Frontend

{"reply":"The 200-hour course costs ...","conversation_id":"0cbf3d1f-5267-4a7d-a7d2-840df5cc3fc2","actions":[],"confirmation":null,"reply_id":"174dce9255d84e40"}

200 OK is the status code (section 7): the server's verdict on the request. Then headers, a blank line, and the body.

That's genuinely all HTTP is. Newer versions (HTTP/2 and HTTP/3) pack the same information into a compact binary form and can carry many requests over one connection at once, but the meaning is identical: method, path, headers, body; status, headers, body. The live server even advertises HTTP/3 in a header you'll see in section 13 (Alt-Svc: h3=":443").

Methods: what kind of action

MethodMeaningSitechat uses it for
GET"Give me this." Has no body. Must not change anything on the server, so browsers, caches and proxies feel free to repeat or reuse it./health, /config, /widget/widget.js
POST"Here's some data, act on it." Has a body. May change things, so it's never repeated automatically./chat, /feedback, /internal/lead-digest
OPTIONS"What am I allowed to send you?" Sent by the browser on its own, before a cross-origin request.The CORS preflight (section 9). Our code never handles it directly.
PUT, PATCH, DELETEReplace, change, delete.Not used.

Why is /chat a POST and not a GET? Two reasons. It changes things (it stores the turn, may email the school, and spends AI tokens), so it must never be repeated by accident. And the message belongs in a body: a GET would have to put it in the URL, and URLs get written into server logs, browser history and analytics. What happens if you send the wrong method? FastAPI refuses it. Real response:

GET /chat            →  405  {"detail":"Method Not Allowed"}

Headers: information about the request

These are the headers that matter in Sitechat, and what each one does here:

HeaderSet byWhat it does in Sitechat
HostBrowserWhich site the request is for. Google's front end serves thousands of services on the same addresses, and this is how it knows to send the request to ours.
Content-TypeSenderThe format of the body. application/json tells FastAPI to read the body as JSON.
Content-LengthSenderHow many bytes of body follow.
X-Site-KeyThe widgetWhich school this chat belongs to. A custom header: names starting X- are an old convention for "not part of the standard, our own". It's not a password: it's printed in the school's page source for anyone to see. Section 9 explains what actually protects us.
OriginBrowser onlyThe origin of the page that made the request, e.g. https://www.pyramidyogshala.com. JavaScript in the page cannot set or change it; the browser writes it. Sitechat checks it against the school's allowed domains.
AuthorizationCloud SchedulerBearer <token>: a signed token from Google proving the request comes from our scheduler account. Only /internal/lead-digest uses it.
X-Forwarded-ForProxiesThe visitor's real IP address, added by Google's front end. Section 10.
Access-Control-Allow-*Our serverResponse headers telling the browser what it may let the page read. Section 9.
Date, ServerServersWhen the response was made, and by what. On the live server, Server: Google Frontend.

Header names don't care about capitals: X-Site-Key, x-site-key and X-SITE-KEY are the same header. (That's why the responses above show lower-case names.) FastAPI makes use of this: the Python parameter x_site_key is automatically matched to the header X-Site-Key, with the underscore turned into a hyphen.

app/api/dependencies.py

def get_tenant(
    request: Request,
    x_site_key: str = Header(...),               # required: refuse the request without it
    origin: str | None = Header(default=None),   # optional: None if the browser sent none
) -> Tenant:

Header(...), with the three dots, means "required". Leave the header out and FastAPI answers before any of our code runs. Real response:

POST /chat  (no X-Site-Key)  →  422
{"detail":[{"type":"missing","loc":["header","x-site-key"],"msg":"Field required","input":null}]}

"loc":["header","x-site-key"] says where the problem is: in the headers, the one called x-site-key.

Analogy

An HTTP request is a posted parcel. The request line is the instruction on the front ("deliver to: chat department"). The headers are the labels (sender's address, "contents: JSON", "weight: 46 bytes", a customer reference number). The blank line is the edge of the label. The body is what's in the box.

6. JSON: the shape of the data

The body could be in any format, as long as both sides agree. Nearly every web API, Sitechat's included, uses JSON (JavaScript Object Notation): plain text, readable by people, that every programming language can turn into its own data. Its whole grammar fits in one table, and every row has a Python twin from Phase 0:

JSONExampleBecomes in PythonBecomes in JavaScript
object{"reply": "Hi", "actions": []}dictobject
array["What are the dates?", "Fees?"]listarray
string"pk_pyramid_yogshala_001"strstring
number46, 0.86int, floatnumber
true / falsetrueTruetrue
nullnullNonenull

The rules are strict, and a single mistake makes the whole body unreadable: names must be in double quotes, strings must use double quotes (never single), no comma after the last item, no comments.

The round trip of one message

Follow the data through four translations. This is where most bugs between a front end and a back end come from, so it's worth seeing once:

  1. JavaScript object → JSON text (in the browser). JSON.stringify turns the widget's object into a string, which becomes the body:

    static/widget.js

    var body = { message: text };
if (conversationId) body.conversation_id = conversationId;
...
body: JSON.stringify(body),        // '{"message":"How much is the 200-hour course?"}'

  2. JSON text → Python object (on our server). FastAPI parses the text and builds a ChatRequest Pydantic object from it, checking every field on the way (section 8). Our route function receives body.message as an ordinary Python str.

  3. Python object → JSON text (on our server). The route returns a ChatResponse object; FastAPI turns it into JSON. None becomes null, the empty list becomes []: look at "confirmation":null and "actions":[] in the response in section 5.

  4. JSON text → JavaScript object (in the browser). r.json() reads the body and parses it, and the widget reads data.reply and data.conversation_id.

What if the body isn't valid JSON at all? Real response, after sending the plain word hello as the body:

POST /chat  body: hello  →  422
{"detail":[{"type":"json_invalid","loc":["body",0],"msg":"JSON decode error","input":{},"ctx":{"error":"Expecting value"}}]}

Notice that error messages are JSON too. The widget can always parse whatever comes back, even a refusal.

7. Status codes: the server's one-number verdict

The first line of every response carries a three-digit status code. The first digit gives the family:

FamilyMeaningWhose fault, roughly
2xxSuccessNobody's.
3xxGo somewhere else (a redirect)Not used by Sitechat.
4xxThe request was refusedThe client's: a wrong key, a bad body, too many requests. Sending the same request again will fail the same way.
5xxThe server couldn't do itThe server's, or something it depends on. Trying again later may work.

That last column is the reason status codes exist. Code that receives a response (the widget, a monitoring tool) can decide what to do from one number, without reading the body. Here's every status Sitechat's public routes return, each one produced for real:

{"detail":[{"type":"string_too_short","loc":["body","message"],
            "msg":"String should have at least 1 character","input":"","ctx":{"min_length":1}}]}

Choosing the right code is a design decision

Look at how the widget reacts. It checks the code first, and only reads the body when the code says the body is worth reading:

static/widget.js (shortened)

.then(function (r) {
  if (r.status === 429) throw new Error("rate");           // our own friendly text
  if (r.status === 503) {
    // The server's 503 messages are written for visitors; show them as text.
    return r.json().then(function (data) { ... error.detail = data.detail; throw error; });
  }
  if (!r.ok) throw new Error(String(r.status));            // anything else that isn't 2xx
  return r.json();                                         // success: read the reply
})

r.ok is true for any 2xx code. And on the server, the route turns an AI failure into a 503 on purpose:

app/api/routes.py

except LLMError as exc:
    # The model failed. Return the visitor-safe message with a 503 so
    # monitoring can tell this apart from a normal reply.
    raise HTTPException(
        status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
        detail=exc.user_message,
    ) from exc

It could have returned 200 with "Sorry, please try again" as the reply. The visitor would see the same words. But then every dashboard would count the failure as a success, and nobody would notice OpenAI was down. The code is for machines; the body is for people.

401 versus 403 is the same kind of choice. 401 means "I don't know who you are" (a key that matches nobody). 403 means "I know who you are, and the answer is no" (a real key, used from the wrong website). The widget prints different advice for each, so the person installing it knows whether to fix the key or ask for their domain to be added.

In Sitechat

One deliberate trick: /internal/lead-digest answers 404 Not Found, not 401 or 403, while the digest isn't set up yet (app/api/internal.py: "indistinguishable from no endpoint at all"). Someone probing the server can't even tell the route exists.

8. APIs: the contract between widget and server

An API (Application Programming Interface) is the set of requests a program promises to accept, and what it promises to send back. For a web API that means: which paths, which methods, which headers, what the body must look like, and what the response will look like. It's the same idea as Phase 0's abstract class, a promise of a shape, stretched across the internet: the widget and the server are written separately, in different languages, and work together only because both keep to it.

Sitechat's whole public API

POST /chatThe widget, per messageX-Site-Key; body: message, conversation idReply, conversation id, reply id, confirmation card

How a path becomes a Python function

A route connects a method and path to a function. In FastAPI, it's the decorator from Phase 0, section 8.10:

app/api/routes.py (shortened)

@router.post("/chat", response_model=ChatResponse)
@limiter.limit(lambda: get_settings().rate_limit_per_visitor)
@limiter.limit(_tenant_limit, key_func=site_key)
def chat(
    request: Request,
    body: ChatRequest,
    background: BackgroundTasks,
    tenant: Tenant = Depends(get_tenant),
) -> ChatResponse:

Every line here is part of the contract, and FastAPI reads all of it:

  • @router.post("/chat", ...): "a POST to /chat runs this function". Any other method gets the 405 you saw.
  • response_model=ChatResponse: what comes back always has the shape of ChatResponse. FastAPI checks the function's result against it, and leaves out any field that isn't declared there, so nothing extra can leak out by accident.
  • The two @limiter.limit lines: rate limits, per visitor and per school (section 10).
  • body: ChatRequest: "read the JSON body and build a ChatRequest from it". If that fails, the function never runs and the visitor gets a 422.
  • tenant: Tenant = Depends(get_tenant): "before running this, run get_tenant, and hand me what it returns". This is a dependency. get_tenant reads the headers, finds the school, checks the origin, and refuses the request (401, 403, 429) if anything is wrong. By the time chat starts, it can trust that tenant is a real, active school, used from an allowed website.

The order of checks matters, and I tested it. A request with both a wrong site key and an empty message gets 401, not 422: FastAPI runs the get_tenant dependency first, so a stranger with a made-up key is turned away before their message is even looked at.

9. The browser's rules: same-origin policy and CORS

This is the part of web development that confuses almost everyone, including experienced developers, so we build it from the reason up.

The danger the rule exists for

You're logged in to your bank in one tab. In another tab you open a random website. That website's JavaScript runs:

fetch("https://yourbank.com/api/balance")

Your browser holds your bank's login cookie, and it attaches cookies for yourbank.com to every request going there, whoever asked. So the bank sees a perfectly logged-in request and answers with your balance. If the random website's JavaScript could read that answer, any page you visit could read your bank account, your email, your company's internal tools. (Newer browsers also hold back some cookies on requests between sites, a second layer added in recent years. The rule below is the original and main defence.)

The rule: the same-origin policy

So every browser enforces the same-origin policy: JavaScript from one origin may send requests to another origin, but it may not read the response, unless the other server explicitly says that's allowed. (Recall from section 4: origin means scheme + host + port.)

Notice what it protects: the visitor's data in their browser, from other websites. It's a rule the browser applies on the visitor's behalf. It says nothing about who may talk to a server in general: a program that isn't a browser (curl, a Python script) ignores it completely.

The exception: CORS

CORS (Cross-Origin Resource Sharing) is how a server says "it's fine, let that page read my response". It does it with response headers. The main one:

access-control-allow-origin: *

means "any origin's JavaScript may read this response". (The alternative is naming one origin, e.g. https://www.pyramidyogshala.com.) The browser checks the header when the response arrives. If it's missing or doesn't match, the browser throws the response away and the page's JavaScript gets only a vague network error, with a red CORS message in the console.

This is exactly Sitechat's situation. The widget's JavaScript runs on the school's origin and reads responses from ours. Without CORS headers from our server, every chat would fail in the browser, even though our server answered correctly.

The preflight: asking before sending

For some requests the browser doesn't even send the real request until it has asked permission. Browsers treat a cross-origin request as "simple", and send it straight away, only if it uses GET, HEAD or POST, carries only a few standard headers, and has a plain body type (like a web form's). These are the kinds of requests ordinary web pages could always send, long before CORS existed, so servers were already built to cope with them.

Sitechat's requests are not simple, for two reasons: they carry a custom header (X-Site-Key), and /chat declares a JSON body (Content-Type: application/json). For these, the browser first sends a preflight: an OPTIONS request asking "may I send you this?". Here are the real preflight request and Sitechat's real answer:

OPTIONS /chat HTTP/1.1
Origin: https://www.pyramidyogshala.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-site-key

HTTP/1.1 200 OK
access-control-allow-origin: *
access-control-allow-methods: GET, POST, OPTIONS
access-control-allow-headers: Accept, Accept-Language, Content-Language, Content-Type, X-Site-Key
access-control-max-age: 600

OK
  • The browser says which method and which headers it wants to use.
  • The server answers: any origin is fine, these methods are fine, these headers are fine.
  • access-control-max-age: 600: the browser may remember this permission for 600 seconds (10 minutes) and skip the preflight for later messages in that time. So a chat's first message costs two round trips (preflight plus the real request) and the next few cost one.

Only after a yes does the browser send the real POST /chat. If the answer had been no, the real request would never have left the browser.

CORS headers only appear when there's something to decide: the browser sends an Origin header with cross-origin requests, and our server answers with access-control-allow-origin only then. The smoke test and curl send no Origin, so the live 401 in section 13 has no CORS header at all. It also carries vary: Origin, which tells any cache along the way that the answer can differ depending on the Origin header.

How Sitechat sets it up, and why "*"

app/main.py

# The widget runs on customer websites, so the browser needs permission
# to call us. Which domains are actually allowed is enforced per tenant
# in get_tenant(); this layer only keeps the browser from blocking us.
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=False,
    allow_methods=["GET", "POST", "OPTIONS"],
    allow_headers=["Content-Type", "X-Site-Key"],
)

Middleware is code that wraps every request and response on its way in and out, before and after the route itself. This one answers preflights and adds the CORS headers to every response.

Why allow every origin (*) instead of listing the schools' domains? You'd think listing them would be safer. Three reasons it isn't possible or useful here:

  1. The preflight doesn't say which school it's for. Look at the real preflight above: it lists the names of the headers the browser wants to send (x-site-key), but not their values. At that moment the server can't tell whether this is Pyramid Yogshala's widget or another school's, so it can't look up that school's domains.
  2. Every school has different domains, and they change. The list lives in each tenant's record in the database (allowed_domains), not in the code. A fixed list in main.py would mean a deploy for every new customer.
  3. The real check happens anyway, one step later, on the real request, where the site key is known. That's get_tenant, below.

allow_credentials=False means "don't send cookies with these requests". Sitechat uses none (section 2), and browsers don't allow * together with credentials, precisely because of the bank example: "any website may read responses made with your cookies" is the danger itself.

The per-school check: the Origin header

app/api/dependencies.py

def _host_from(url: str) -> str:
    """Pull the hostname out of an Origin or Referer header."""
    without_scheme = url.split("://", 1)[-1]           # "www.pyramidyogshala.com"
    host_and_port = without_scheme.split("/", 1)[0]    # drop any path
    return host_and_port.split(":", 1)[0].lower()      # drop any port; lower-case

def _origin_allowed(tenant: Tenant, origin: str | None) -> bool:
    if not origin:
        # No Origin header means a same-origin or non-browser request.
        # We allow it here; the rate limit is what protects us.
        return True

    host = _host_from(origin)
    for allowed in tenant.allowed_domains:
        allowed = allowed.lower()
        if host == allowed or host.endswith("." + allowed):
            return True
    return False

CORS lets the browser hand the refusal to the widget, so the widget can read the status code and print "This site key is not allowed on evil.example..." in the console. The refusal itself comes from get_tenant.

So what does the Origin check actually protect?

Be precise about this, because it's a favourite interview question. JavaScript in a web page can't change the Origin header; the browser always writes the true one. So:

  • It stops: another website copying Pyramid Yogshala's script tag (the site key is public, in their page source) and running the chat on its own site, spending the school's AI budget through its own visitors' browsers. The browsers will send the true origin, and the server will refuse.
  • It doesn't stop: someone with a script (curl, Python) sending requests directly. A script isn't a browser: it can leave Origin out, or write any value it likes. The code knows this; the comment says "the rate limit is what protects us".

What protects the server against scripts, then? Limits on how much anyone can use it: 5 messages a minute per visitor, an hourly limit per school, a daily AI-token budget per school (Phase 4), and a separate limit on refused requests so guessing keys gets you blocked (section 10). The site key is an identifier, like a shop's name, not a password; notes/install-guide.md says so to customers in those words.

Analogy

The same-origin policy is a careful parent (the browser) who won't hand their child (the page) a letter addressed from a stranger unless the letter says "OK for anyone to read". CORS is that note on the letter. The preflight is the parent phoning first: "my child wants to send you a parcel with a custom label. Is that all right?". The Origin check is the call centre looking at the caller's verified return address. None of it stops someone who isn't using the parent at all: they can just write the letter themselves. For them, the call centre has a limit on how many calls it takes.

Say it in an interview

"CORS is open at the middleware layer, allow_origins='*' with no credentials, because the preflight carries header names but not the site key's value, so we can't know the tenant at that point. Domain enforcement is per tenant in a FastAPI dependency that checks the Origin header against the tenant's allowed domains, with a dot-boundary match so lookalike domains fail. That stops other sites from embedding a tenant's public key in browsers. It doesn't stop non-browser clients, which can forge Origin, so abuse is bounded by per-visitor and per-tenant rate limits and a daily token budget."

10. Who is asking: IP addresses, proxies, rate limits

To limit "5 messages a minute per visitor", the server has to tell visitors apart. There are no accounts and no cookies, so the only thing available is the visitor's IP address. And on Cloud Run, even that takes care to get.

The problem: every request seems to come from Google

Remember from section 3: the browser connects to Google's front end, and Google's front end connects to our container. So from our server's point of view, every request's connection comes from the same Google machine. request.client.host, the address of whatever connected to us, is Google's internal address for every visitor. Limit on that, and all visitors in the world would share one limit of 5 messages a minute.

The fix: X-Forwarded-For

A server that receives a request and passes it on is a proxy. By convention, a proxy adds the address it received the request from to the end of a header called X-Forwarded-For. So Google's front end writes the visitor's real address there before forwarding.

But there's a trap: the visitor can also send an X-Forwarded-For header, with any made-up value, and proxies add to it rather than replace it. A visitor trying to dodge the limit sends a fake address every time:

Visitor sends:            X-Forwarded-For: 1.2.3.4                      (made up)
Google's front end adds:  X-Forwarded-For: 1.2.3.4, 203.0.113.7         (the real one, at the end)

Only the entries added by proxies we trust are real. The rest is whatever the visitor typed. So the code counts from the end:

app/rate_limit.py

def client_ip(request: Request) -> str:
    hops = get_settings().trusted_proxy_hops                     # 1 on Cloud Run
    header = request.headers.get("x-forwarded-for", "")
    entries = [e.strip() for e in header.split(",") if e.strip()]  # ["1.2.3.4", "203.0.113.7"]

    if hops > 0 and len(entries) >= hops:
        return _bucket(entries[-hops])                           # entries[-1]: "203.0.113.7"

    # No proxy in front (local development), or a header too short to
    # have come through the proxies we expect.
    return _bucket(request.client.host if request.client else "unknown")

entries[-1] in Python means "the last item". With one trusted proxy (Google's front end), the last entry is the one Google wrote, and nothing the visitor sends can change it. The setting's comment in app/config.py records how the number was chosen: "Measured 2026-10-15: direct *.run.app traffic arrives with one entry appended by Google's front end, so 1. Behind an external HTTPS load balancer it would be 2." Get it wrong in one direction (trusting too many entries) and visitors can fake their address; get it wrong in the other, and you limit Google instead of the visitor.

_bucket handles one more detail. A home internet connection with IPv6 is usually given a whole block of addresses (a "/64": 18 billion billion of them), and the devices in it can switch between them freely. Counting each IPv6 address separately would let one person use a fresh address for every message. So IPv6 addresses are grouped by their /64 block, and each block counts as one visitor.

The limits themselves

app/config.py

rate_limit_per_visitor: str = "5/minute"
rate_limit_per_tenant: str = "60/hour"
rate_limit_config_per_visitor: str = "30/minute"
rate_limit_feedback_per_visitor: str = "30/minute"
rate_limit_rejected_per_visitor: str = "20/minute"

The sixth message within a minute gets this real response:

429  {"error":"Rate limit exceeded: 5 per 1 minute"}
  • Per visitor stops one person flooding the bot.
  • Per tenant caps a whole school's traffic (each school can have its own, Tenant.rate_limit), so a flood from many addresses still has a ceiling.
  • Rejected per visitor counts refusals (bad key, wrong domain). After 20 in a minute, that visitor's requests are refused before the database is even asked. Without it, someone trying made-up keys would cost a database read per guess.

Two more details that save database reads. Tenant lookups are cached for 60 seconds (tenant_cache_seconds), including unknown keys, so a repeated bad key costs one read a minute, not one per request. The side effect: when a school's allowed domains change, it can take up to a minute to apply. And the counters live in each server instance's memory, so if Cloud Run ran two copies of the server, each would count separately (the comment in app/config.py notes this and what to do if it ever matters).

11. HTTPS: why nobody else can read it

Look back at the raw request in section 5. It's plain text. On its way from the visitor's phone to Google it passes through the café's Wi-Fi router, the internet provider, and several networks in between. Over plain HTTP, any of them could read it, including the email address a visitor types into the chat, and could even change the reply on its way back.

HTTPS is HTTP sent inside an encrypted connection, made with TLS (Transport Layer Security). Before any HTTP is sent:

  1. The server proves who it is. It presents a certificate: a document saying "this is *.run.app", digitally signed by a certificate authority, an organisation the browser already trusts. The browser checks the signature and that the name matches the URL. An impostor can't produce a valid certificate for our name, so the browser would show a full-page warning instead.

  2. They agree on a secret key that only the two of them know, using maths designed so that someone watching the whole exchange still can't work out the key.

  3. Everything after that is encrypted with that key: the request line, every header (the site key included) and the body.

Real timings from this laptop to the live server, measured with curl:

connected:       0.024 s    (the network connection is open)
TLS finished:    0.073 s    (identity checked, keys agreed)
response done:   0.337 s    (request sent, server answered)

Setting up the encryption took about 50 ms. The browser keeps the connection open and reuses it for later requests, so that cost is paid once per visit, not once per message.

What can someone in between still see? The IP addresses, roughly how much data flows, and usually the host name (sitechat-api-...run.app, which the browser sends at the start so the front end knows which certificate to show). Not the path, headers or body: not the message, not the site key.

Where the encryption ends

TLS runs from the browser to Google's front end. Google manages the certificate for *.run.app, which is why Sitechat's code contains nothing about certificates. From the front end to our container, the request travels inside Google's own network, and uvicorn receives ordinary HTTP on port 8080.

HTTPS isn't optional for a widget. A page loaded over https:// isn't allowed to load scripts from http:// addresses (that's called mixed content, and browsers block it), because one unencrypted script could rewrite the whole secure page. Nearly every school's site is HTTPS, so our script and API must be too. The one exception browsers make is localhost, treated as safe because nothing leaves the machine. That's why local testing works over plain http://localhost:8080.

12. One message, start to finish

Now everything together. A visitor on https://www.pyramidyogshala.com asks "How much is the 200-hour course?". Every step names the code that runs.

When the page loads

  1. The script loads. The browser reads the <script src=...widget.js> tag, looks up our host in DNS, opens a TLS connection to Google's front end, and sends GET /widget/widget.js. FastAPI serves the file from the static/ folder (app.mount("/widget", StaticFiles(directory="static")) in app/main.py).

  2. The widget starts. It reads its own tag: site key from data-site-key, our origin from src. It checks localStorage for a saved conversation_id under "sitechat:" + siteKey.

  3. It fetches its settings. fetch(API + "/config", { headers: { "X-Site-Key": siteKey } }). Because of the custom header, the browser first sends the OPTIONS preflight; CORSMiddleware answers it. Then the real GET /config: get_tenant finds the school and checks the origin; the route returns the name, greeting and suggested questions as JSON. The widget draws the bubble with them. If this fails with 401 or 403, the widget disables itself and explains why in the console.

When the visitor sends the message

  1. The widget builds the request. In ask(): shows the message and the waiting dots, makes { message: text, conversation_id: ... }, and calls fetch(API + "/chat", { method: "POST", headers: {...}, body: JSON.stringify(body) }). The browser remembers preflight answers per address, so the one for /config doesn't cover /chat: the first message sends its own OPTIONS /chat preflight, and messages in the next 10 minutes skip it.

  2. The browser sends it. It adds Origin: https://www.pyramidyogshala.com itself, encrypts everything, and sends it over the open connection.

  3. Google's front end receives it, decrypts it, adds the visitor's address to X-Forwarded-For, picks a running copy of our container (or starts one), and forwards the request to port 8080.

  4. uvicorn reads the HTTP and hands it to the FastAPI app.

  5. The middleware runs, outermost first. RequestContextMiddleware gives the request a fresh 12-character request id, so every log line it produces can be found together later. CORSMiddleware will add access-control-allow-origin: * to the response on the way out.

  6. Routing. FastAPI matches POST + /chat to the chat function.

  7. The dependency runs: get_tenant. Too many refusals from this visitor already → 429. Key too long or unknown → 401. School switched off → 403. Origin not on the school's list → 403. Otherwise it returns the Tenant.

  8. The body is checked. FastAPI parses the JSON into a ChatRequest. Not JSON, empty message, over 2000 characters, malformed id → 422.

  9. The rate limits are checked. The @limiter.limit decorators: over 5 a minute for this visitor, or over the school's hourly limit → 429.

  10. The route runs. It picks the conversation id (or makes a new UUID), makes a reply_id, and calls generate_reply(...), which builds the answer (Phases 3 and 4: find the school's information, ask OpenAI). If OpenAI fails or the daily budget is spent, LLMError becomes a 503 with a message for the visitor.

  11. The slow, unhurried work is queued, not done.

    app/api/routes.py (shortened)

    # Storing the turn, summarizing and emailing the team do not affect
# this reply, so they run after it has been sent.
background.add_task(after_reply, tenant, conversation_id, stored_message, reply, ...)

return ChatResponse(reply=reply, conversation_id=conversation_id,
                    confirmation=..., reply_id=reply_id)

  12. The response goes out. FastAPI turns the ChatResponse into JSON; the middleware adds its headers; uvicorn writes HTTP/1.1 200 OK, the headers, and the body; Google's front end encrypts it and sends it to the browser.

  13. Then the background task runs on our server: saving the turn to the database, summarising long conversations, emailing the school if the visitor asked to be contacted. The visitor is already reading the answer.

  14. The browser checks CORS. The response says access-control-allow-origin: *, so it hands the response to the widget.

  15. The widget shows the reply. Status 200, so r.json(); then saveConversationId(data.conversation_id) (so the next message, or a visit next week, continues this conversation) and showReply(data.reply, data.confirmation, data.reply_id). The text is put on the page as plain text, never as HTML, so nothing in a reply can run as code on the school's site (Phase 5).

In Sitechat

Every refusal in that list happens before generate_reply, which is the only step that costs money (AI calls). Cheap checks first, expensive work last: that ordering is deliberate, and it's why a flood of bad requests costs us almost nothing.

Say it in an interview: the request path in one breath

"The widget is a script tag on the customer's site. It reads its site key, fetches per-tenant config, then posts JSON to /chat on Cloud Run. Google's front end terminates TLS and forwards to uvicorn. Middleware assigns a request id and handles CORS. A dependency resolves the tenant and checks the Origin, Pydantic validates the body, rate limits run, and only then does the orchestrator call the model. The response is returned immediately, and persistence and lead emails run as background tasks after it's sent."

Challenges we faced

Real problems from the project's history that come down to how the web works. Each is told in full in the phase named.

1. Google's 404, not ours

The health route was called /healthz and returned 404 on Cloud Run. The clue was whose error page it was: Google's HTML, not FastAPI's JSON {"detail":"Not Found"}, so the request never reached the container. Cloud Run's front end reserves that path. Renamed to /health. Phase 4a, challenge 3.

2. Every visitor looked like the same visitor

Section 10 of this phase explains X-Forwarded-For. Before that code existed, the rate limiter used the connection's address, which on Cloud Run is Google's front end (169.254.169.126) for everyone: five messages a minute for the whole world. The real headers were logged in production first, then the entry one hop from the end was chosen. Phase 4a, challenge 4.

3. A slash that broke a path

The conversation_id a browser sends back ended up inside a Firestore document path. A / in it split the path and caused a 500. Anything a client sends that becomes part of a key or path must be validated at the edge: the pattern ^[A-Za-z0-9-]{1,64}$ (section 8) now returns a 422 instead. Phase 4a, challenge 5.

4. A silent 403

When a site's domain wasn't on the allowed list, the widget just said "not available" and the person installing it had no idea why. Now the widget prints the reason to the browser console with a [sitechat] prefix, and the install guide explains each message. Phase 5, challenge 5.

5. Refused requests that cost money

Route rate limits run after FastAPI dependencies, so requests refused for a bad site key were never counted, and each made-up key cost a database read. Fixed by caching "not found", limiting /config, and counting refusals per visitor before the lookup. Real output in Phase 4a: 20 refusals, then 429s even with a valid key. Phase 4a, §8.3.

6. The first request timed out

The post-deploy smoke test's very first call to /health timed out. That led to measuring a 43-second cold start after the service scaled to zero, which the 5-minute scheduler job later removed. Phase 6, §4.

7. The API's own documentation was public

FastAPI publishes /docs and /openapi.json by default, and in production they listed the internal endpoint to anyone. Not exploitable alone, but it published the attack surface; they're now off in production. Phase 4a, challenge 8.

Glossary

Client, server
The program that asks; the program that answers.
Request, response
One message from client to server; the one reply that comes back.
Stateless
The server remembers nothing between requests; the client must send what identifies it (the conversation_id).
IP address
A machine's number on the internet. IPv4 is short (34.143.72.2), IPv6 is long.
DNS
The internet's phone book: turns a host name into IP addresses.
Port
Which program on a machine: 443 for HTTPS, 8080 for uvicorn.
localhost
This same computer (127.0.0.1).
URL
A full web address: scheme, host, port, path, and maybe query and fragment.
Origin
Scheme + host + port. What the browser compares to decide "same site or not".
Cross-origin request
A page on one origin calling another, like the widget calling our server.
HTTP
The format of requests and responses: request or status line, headers, blank line, body.
Method
The kind of request: GET (read), POST (act on data), OPTIONS (ask permission).
Header
A Name: value line of information about a request or response.
Body
The content of a request or response; in Sitechat, JSON.
JSON
A text format for data: objects, arrays, strings, numbers, true/false, null.
Status code
The response's three-digit verdict: 2xx success, 4xx client's problem, 5xx server's problem.
API
The requests a program promises to accept and the responses it promises to give.
Endpoint, route
One method and path the API offers (POST /chat), and the function behind it.
Dependency (FastAPI)
A function FastAPI runs before the route, like get_tenant; it can refuse the request.
Validator
Extra checking code Pydantic runs on a field.
Middleware
Code wrapped around every request and response, like the CORS layer.
Same-origin policy
The browser rule: a page may not read responses from another origin unless that origin allows it.
CORS
The response headers by which a server allows other origins to read its responses.
Preflight
The OPTIONS request a browser sends first, to ask whether a non-simple cross-origin request is allowed.
Cookie, third-party cookie
Data a site stores in the browser and gets back with every request; one set by a site other than the page you're on.
localStorage
A small store in the browser, belonging to the page's origin. Holds the widget's conversation id.
Proxy
A server that receives requests and passes them on, like Google's front end.
X-Forwarded-For
The header proxies add the client's address to. Only the entries added by trusted proxies can be believed.
Rate limit
A cap on requests per time window, like 5 a minute per visitor.
HTTPS, TLS
HTTP inside an encrypted connection; the protocol that makes the encryption.
Certificate
A signed document proving a server owns a name, checked by the browser.
Mixed content
An http:// resource on an https:// page. Browsers block scripts like that.
Background task
Work FastAPI runs after the response has been sent.
UUID
A random id so long that two are never the same, like 0cbf3d1f-5267-....

Check yourself

Does the school's own web server ever see a chat message?

No. It only serves the page with the script tag. The browser then loads the widget from our server and sends every message straight to our server.

Why can't the bot send a message to the visitor by itself, five minutes after they go quiet?

In HTTP the server only ever responds to requests; it can't start one. The widget would have to ask first. For the same reason, our server's timed lead-digest emails are triggered by Cloud Scheduler sending it a request every 5 minutes.

Are https://pyramidyogshala.com and https://www.pyramidyogshala.com the same origin? What practical difference does it make in Sitechat?

No: the host differs. The widget's localStorage is separate on each, so a visitor who switches between them starts a new conversation. For the domain check, though, both pass: www.pyramidyogshala.com ends with .pyramidyogshala.com.

The widget sends a chat with a made-up site key and an empty message. Which status comes back, and why that one?

401. FastAPI runs the get_tenant dependency before validating the body, so the unknown key is refused before the empty message is noticed. Checked for real.

Why does an AI failure return 503 instead of 200 with an apology?

The visitor sees the same words either way, but the code is for machines. A 503 lets monitoring count it as a failure and lets the widget know to show the server's message as a notice. A 200 would make an OpenAI outage look like normal traffic.

Why does the browser send an OPTIONS request before POST /chat?

The request is cross-origin and not "simple": it has a custom header (X-Site-Key) and a JSON content type. The browser asks permission first (the preflight). Our CORS middleware answers yes, and the browser remembers that for 10 minutes.

Why can't the CORS layer only allow the school's own domains?

The preflight carries the names of the headers the browser will send but not their values, so at that point the server doesn't know which school it is. The list of domains is also per school, in the database. So CORS allows all origins, and get_tenant checks the real request's Origin against that school's list.

Someone runs a Python script that sends Origin: https://pyramidyogshala.com with the school's site key. Does the Origin check stop them? What does?

No. Only browsers guarantee the Origin header is true; a script can write anything. What limits them is the rate limits (5 a minute per visitor, the school's hourly limit), the limit on refused requests, and the school's daily AI budget.

Why does client_ip take the last entry of X-Forwarded-For, not the first?

The visitor can send their own X-Forwarded-For with any value, and proxies add to the end of it. Only the entry Google's front end added (the last one, with one trusted proxy) is real. The first entry could be anything the visitor typed.

What can someone on the same café Wi-Fi learn about a visitor's chat?

That the visitor is talking to our host (the IP address, and usually the host name), and roughly how much data. Not the message, the site key, the path or the reply: TLS encrypts everything inside the request.
