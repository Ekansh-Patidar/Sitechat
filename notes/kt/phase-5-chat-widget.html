Sitechat knowledge transfer · Phase 5 of 10

The chat widget: one JavaScript file inside someone else's website

static/widget.js is about 1,250 lines of plain JavaScript, with no framework and no build step. It runs on a school's page that we don't control, so it must not break the page, must not be broken by the page's styles, must never let text from the server become code, and must still be pleasant to use on a phone, with a keyboard, or with a screen reader. This phase reads the file from top to bottom.

1. Starting up: the wrapper, the guard, the script tag

(function () {
  "use strict";

  if (window.__sitechat) return;
  window.__sitechat = true;

  var script = document.currentScript;
  var siteKey = script && script.getAttribute("data-site-key");
  var teaserAllowed = !(script && script.getAttribute("data-teaser") === "off");
  var API = new URL(script.src).origin;

  if (!siteKey) {
    console.error("[sitechat] The script tag needs a data-site-key attribute.");
    return;
  }
  ...
})();
  • (function () { ... })(); is an immediately invoked function expression: define a function and call it at once. Everything declared inside stays private to it. Without this, our variables (config, busy, log) would be globals on the school's page and could clash with theirs.
  • "use strict" turns on stricter JavaScript rules, so mistakes like assigning to an undeclared variable raise errors instead of silently creating globals.
  • The guard. If the snippet is pasted twice (it happens with page builders), the second copy sees window.__sitechat and stops, instead of drawing two chat buttons.
  • document.currentScript is the <script> tag currently running. The widget reads its own tag's data-site-key and data-teaser attributes, and works out the API's address from where it was loaded (Phase 1, §4), so the address is written in exactly one place: the tag the school pasted. This is also why the install guide says not to add type="module": for module scripts, currentScript is null, so the widget couldn't find its own tag (the guide also rules out async, to keep the tag in its simplest, tested form).
  • var declares a variable (older style; works in every browser). && is "and": script && script.getAttribute(...) only calls the method if script exists.

2. Isolation: the shadow root

var host = document.createElement("div");
host.setAttribute("data-sitechat", "");
var shadow = host.attachShadow({ mode: "open" });

var style = document.createElement("style");
style.textContent = CSS;
shadow.appendChild(style);

var root = document.createElement("div");
root.className = "root";
shadow.appendChild(root);

The biggest problem with a widget is that it lives in someone else's page. Their CSS rules (button { text-transform: uppercase }, * { box-sizing: content-box !important }) would apply to our buttons too, and our rules could leak out and restyle their page.

A shadow root solves both. attachShadow gives the host div a separate, hidden DOM tree. CSS from the page doesn't reach into it, and CSS inside it doesn't reach out. The opening comment of the file: "Everything lives inside a shadow root, so the host page's CSS cannot reach in and ours cannot leak out." The repo's test page (static/test-page.html) is "deliberately hostile": dashed red buttons, yellow textareas, forced box sizing, a serif body; and a browser test checks none of it reaches the widget, even with !important.

One property crosses on purpose: the font family, through font-family: inherit on the host. "A widget that imports its own typeface looks like something bolted on." That's why the screenshots use the page's serif font.

Analogy

A glass display case in someone else's shop. The shop can repaint its walls any colour and the case's contents stay as they are; the case's lighting doesn't change the shop. The only thing shared is the ambient light (the font), which makes the case look like it belongs.

3. Styles: tokens, dark mode, motion, phones

:host { all: initial; font-family: inherit; }

.root {
  --accent: #1f6f5c;
  --accent-ink: #ffffff;
  --ink: #1a1c1b;
  --paper: #ffffff;
  --raised: #f6f8f7;
  ...
}

@media (prefers-color-scheme: dark) {
  .root { --ink: #e8eceb; --paper: #161918; --raised: #1f2423; ... }
}

@media (prefers-reduced-motion: reduce) {
  .panel { animation: none; }
  .launcher, .launch-text { transition: none; }
}

@media (max-width: 520px) {
  .panel { inset: 0; width: 100%; height: 100%; border-radius: 0; border: none; }
}
  • :host { all: initial } resets every inherited property on the host element to its default (then brings back the font), a belt-and-braces addition to the shadow root.
  • CSS custom properties (--accent, --ink...) are named values used everywhere with var(--accent). Change one and everything using it changes: the widget sets --accent to the school's colour from /config, and the whole widget re-themes.
  • Dark mode follows the visitor's system setting: only the colour tokens change.
  • Reduced motion: visitors who ask their system for less animation get no panel animation, no launcher teaser, and all reply bubbles at once.
  • Phones: under 520 pixels wide, the panel fills the whole screen (inset: 0 means top, right, bottom and left are all 0).
  • z-index: 2147483000 on the launcher and panel: close to the largest value browsers allow, so the chat sits above the school's own menus and pop-ups.

4. Markup built without innerHTML

// Built with DOM calls rather than innerHTML, so the habit holds
// everywhere and there is no template that someone later interpolates into.

var launcher = el("button", "launcher");
launcher.type = "button";
launcher.appendChild(icon("M21 11.5a8.4 8.4 0 0 1-9 8.4 ...", 17));
var launchText = el("span", "launch-text");
launchText.textContent = LAUNCHER_TEXT;            // "Chat with us"
launcher.appendChild(launchText);

var panel = el("div", "panel");
panel.hidden = true;
panel.setAttribute("role", "dialog");
panel.setAttribute("aria-label", "Chat");
...

function el(tag, className) {
  var node = document.createElement(tag);
  if (className) node.className = className;
  return node;
}

There are two ways to put content in a page. element.innerHTML = "<b>" + text + "</b>" parses a string as HTML, so if text contains <img src=x onerror="...">, that becomes a real element and its code runs, on the school's page, with access to everything there. That's cross-site scripting (XSS). The other way, document.createElement plus textContent, treats text as text, always.

The widget uses only the second way, everywhere, even for its own fixed markup. The comment explains: "so the habit holds everywhere and there is no template that someone later interpolates into". If the safe way is the only way in the file, nobody can later paste model output into a template by accident. Icons are built the same way, as SVG elements with createElementNS (SVG needs its own namespace).

The structure: a launcher button, and a panel (a dialog) holding a header (name and close button), a log (the messages, role="log" with aria-live="polite" so screen readers announce new messages), and a footer with the "Talk to the team" button, the text box and send button, "Start a new chat", and the disclosure line "AI assistant · Answers can be wrong".

5. Remembering the conversation

var STORAGE_KEY = "sitechat:" + siteKey;
var MAX_AGE_MS = 30 * 24 * 60 * 60 * 1000;           // 30 days in milliseconds

function loadConversationId() {
  try {
    var raw = localStorage.getItem(STORAGE_KEY);
    if (!raw) return null;
    var saved = JSON.parse(raw);
    if (Date.now() - saved.at > MAX_AGE_MS) {
      localStorage.removeItem(STORAGE_KEY);
      return null;
    }
    return saved.id;
  } catch (e) {
    // Private browsing or storage disabled. The chat still works, it just
    // will not resume on a later visit.
    return null;
  }
}

function saveConversationId(id) {
  conversationId = id;
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify({ id: id, at: Date.now() }));
  } catch (e) {}
}

localStorage is a small key-value store the browser keeps per website (per origin, Phase 1, §4). The widget stores {"id": "...", "at": <time>} under sitechat:<site key>, so a returning visitor within 30 days continues the same conversation, and the server finds their history. try/catch is JavaScript's try/except: in private browsing or with storage blocked, reading throws, and the widget just starts fresh. Every write refreshes the date, so the 30 days count from the last message.

Why not a cookie? Cookies set by our server on the school's page are third-party cookies, which browsers increasingly block, and they'd be sent with every request automatically. localStorage belongs to the page, is read only when the widget asks, and keeps the server stateless.

6. Rendering replies safely, with bold

function renderReply(bubble, text) {
  text = String(text).replace(/^#{1,6}[ \t]+/gm, "");
  var parts = text.split(/\*\*([^*\n]+)\*\*/);
  for (var i = 0; i < parts.length; i++) {
    if (!parts[i]) continue;
    if (i % 2 === 1) {
      var strong = document.createElement("strong");
      strong.textContent = parts[i];
      bubble.appendChild(strong);
    } else {
      bubble.appendChild(document.createTextNode(parts[i].replace(/\*\*/g, "")));
    }
  }
}

The model sometimes writes Markdown bold (**Ravi Nagar**, copying the teachers list in the source document). Inserted as text, visitors saw the asterisks. Rendering Markdown with a library would mean producing HTML, which is exactly what must never happen with model output. So this does the one thing needed, safely:

  1. Remove heading markers (### ) at the start of any line (/gm: global, multi-line).
  2. split with a capturing group (...) returns the pieces between matches and the captured text: "Our founder is **Ravi Nagar**." → ["Our founder is ", "Ravi Nagar", "."]. Odd positions are the bold parts.
  3. Bold parts become <strong> elements with textContent; the rest become text nodes, with any unmatched ** removed.

A browser test sends a reply containing <img src=x onerror="window.__pwned = 1"> <b>bold?</b> and checks that __pwned is never set and the tags show as literal text. Visitor messages are always plain textContent.

7. Reply bubbles

var MAX_BUBBLES = 4;

function isListItem(line) {
  return /^\s*([-*•]|\d+[.)])\s/.test(line);
}

function splitReply(text) {
  var bubbles = [];
  String(text).split(/\n[ \t]*\n/).forEach(function (block) {
    block = block.trim();
    if (!block) return;
    var previous = bubbles[bubbles.length - 1];
    var lastLine = previous ? previous.split("\n").pop() : "";
    // A list stays together, and with the line that introduces it.
    if (previous && isListItem(block) && (/:\s*$/.test(lastLine) || isListItem(lastLine))) {
      bubbles[bubbles.length - 1] = previous + "\n" + block;
    } else {
      bubbles.push(block);
    }
  });
  while (bubbles.length > MAX_BUBBLES) {
    var last = bubbles.pop();
    bubbles[bubbles.length - 1] += "\n\n" + last;
  }
  return bubbles.length ? bubbles : [String(text)];
}

function gapBefore(text) {
  return Math.min(1500, 500 + text.length * 8);
}

Each reply is split at blank lines into separate bubbles, shown one after another with typing dots in between, "the way a person sends several short messages". Rules: a list stays with the line introducing it (one ending in a colon) and with other list items; at most 4 bubbles (extras are merged into the last); the gap before each is 0.5 to 1.5 seconds depending on its length. forEach(function (block) {...}) is JavaScript's way of looping with a function, like Python's for block in ....

function showReply(text, confirmation, replyId) {
  showQueued();
  var bubbles = splitReply(text);
  addTurn("them", bubbles[0]);
  queued = bubbles.slice(1);
  if (replyId) queued.push({ rate: replyId });
  if (confirmation) queued.push({ confirm: confirmation });
  if (reducedMotion()) showQueued();
  else showNext();
}

The first bubble shows at once; the rest wait in a queue, followed by the thumbs row and (if any) the confirmation card. showNext uses setTimeout (run a function after a delay) to reveal each item after its gap. If the visitor starts typing or sends another message, showQueued reveals everything left at once: "they should not wait on the animation". Only the display changes: the reply is stored and emailed as one message.

8. Thumbs up and down

function sendRating(replyId, rating, reason) {
  if (!conversationId) return;
  var body = { conversation_id: conversationId, reply_id: replyId, rating: rating };
  if (reason) body.reason = reason;
  fetch(API + "/feedback", {
    method: "POST",
    headers: { "Content-Type": "application/json", "X-Site-Key": siteKey },
    body: JSON.stringify(body),
  }).catch(function () {});
}

A thumbs row appears after each reply's last bubble (not after the greeting, notices or the card). A tap sends immediately and can be changed; a thumbs-down offers "Wrong information", "Didn't answer my question" or "Other", each sending again with the reason. aria-pressed tells screen readers which is selected. Sending is "best effort": .catch(function () {}) swallows a network error, because "a lost rating is not worth troubling the visitor about". Each reply's row carries its own reply_id, so ratings attach to the right reply.

9. The confirmation card and notices

function addConfirmation(text) {
  var card = el("div", "confirm");
  card.setAttribute("role", "status");
  card.appendChild(icon("M20 6 9 17l-5-5", 16));     // a tick
  var words = el("span");
  words.textContent = text;
  card.appendChild(words);
  log.appendChild(card);
  toEnd();
}

function noteEmailUse(text) {
  if (emailNoticeShown || !/\S+@\S+\.\S+/.test(text)) return;
  emailNoticeShown = true;
  var business = config ? config.display_name : "the business";
  addNotice("Your email goes only to " + business + "'s team, so they can reply to you.");
}

The card shows the server's confirmation text ("Request received. Pyramid Yogshala will reply to the email address you gave, usually within 24 hours.") in a bordered box, visually separate from the bot's own words, because it's a fact from the system, not something the AI said. role="status" makes screen readers announce it. The email notice appears the first time a visitor types something that looks like an email, "so they know where it goes before relying on it". Its wording changed when visitors stopped being copied on emails (it used to say they'd be copied).

10. Talking to the server

function loadConfig() {
  return fetch(API + "/config", { headers: { "X-Site-Key": siteKey } })
    .then(function (r) {
      if (!r.ok) { explainRefusal(r.status); throw new Error(String(r.status)); }
      return r.json();
    })
    .then(function (data) {
      config = data;
      name.textContent = data.display_name;
      if (data.accent_colour) root.style.setProperty("--accent", data.accent_colour);
      addPrivacyLink(data.privacy_url);
      addTurn("them", data.greeting);
      addPrompts(data.suggested_questions);
      startTeaser(data.suggested_questions);
    })
    .catch(function () {
      disable("This chat is not available right now. Please try again later.");
    });
}

fetch sends an HTTP request and returns a promise: an object standing for a result that will arrive later. .then(f) says "when it arrives, run f with it", and each .then receives what the previous one returned; .catch handles any error thrown anywhere in the chain. (Python's equivalent is async/await.) On success, the widget names itself, takes the school's colour, adds the privacy link (only if it starts with http(s)), shows the greeting and up to four suggested questions, and starts the teaser. On any failure: "not available" for the visitor, and the reason in the console for the site owner (next section).

function ask(text) {
  text = (text || "").trim();
  if (!text || busy) return;
  showQueued();
  busy = true;
  send.disabled = true;
  addTurn("you", text);
  noteEmailUse(text);
  addWaiting();

  var body = { message: text };
  if (conversationId) body.conversation_id = conversationId;

  fetch(API + "/chat", { method: "POST",
      headers: { "Content-Type": "application/json", "X-Site-Key": siteKey },
      body: JSON.stringify(body) })
    .then(function (r) {
      if (r.status === 429) throw new Error("rate");
      if (r.status === 503) {
        return r.json().then(function (data) {
          var error = new Error("503");
          if (data && typeof data.detail === "string") error.detail = data.detail;
          throw error;
        }, function () { throw new Error("503"); });
      }
      if (!r.ok) throw new Error(String(r.status));
      return r.json();
    })
    .then(function (data) {
      clearWaiting();
      saveConversationId(data.conversation_id);
      showReply(data.reply, data.confirmation, data.reply_id);
      if (data.confirmation) { handoffUsed = true; handoff.hidden = true; }
      if (!handoffUsed && handoff.hidden) {
        handoff.hidden = false;
        handoff.classList.add("arrive");
        toEnd();
      }
    })
    .catch(function (err) {
      clearWaiting();
      if (err.message === "rate") addNotice("That is a lot of questions at once. Wait a moment, then try again.");
      else if (err.detail) addNotice(err.detail);
      else addNotice("That message did not get through. Try again in a moment.");
    })
    .finally(function () {
      busy = false;
      send.disabled = false;
      input.focus();
    });
}
  • busy prevents a second message while one is in flight (double-clicks, Enter held down).
  • Optimistic display: the visitor's bubble and the typing dots appear before the server answers.
  • The status codes mapped (Phase 1, §7): 429 → a friendly "a lot of questions at once"; 503 → the server's own message, which is written for visitors (including "taking a break until tomorrow" from the token budget); anything else → a generic notice. In every case the chat carries on.
  • After success: save the conversation id the server issued, show the reply, and reveal "Talk to the team" (with a short pulse) unless a confirmation retired it.
  • .finally runs whether it succeeded or failed: re-enable sending and put the cursor back in the box.

11. Errors the site owner can fix

function explainRefusal(status) {
  if (status === 401) {
    console.error("[sitechat] The site key in the script tag is not recognised. " +
                  "Check the data-site-key attribute.");
  } else if (status === 403) {
    console.error("[sitechat] This site key is not allowed on " + location.hostname +
                  ", or the chat is switched off. Ask for " + location.hostname +
                  " to be added to the allowed domains.");
  }
}

Visitors only ever see "This chat is not available right now". The person installing the widget needs the reason, so it goes to the browser's developer console, prefixed [sitechat]. The install guide (notes/install-guide.md) has a table of these messages and what to do about each. Before this, a wrong domain was a silent 403 and the widget just didn't work. Browser tests check both messages appear.

12. The launcher teaser

var TEASER_FIRST_MS = 3000;       // first round 3 s after load
var TEASER_STEP_MS = 2000;        // each question shown for 2 s
var TEASER_PER_ROUND = 3;
var TEASER_REST_MS = 30 * 1000;   // rest between rounds
var TEASER_MAX_CHARS = 32;

The launcher reads "Chat with us". Three seconds after load it widens to show a suggested question, changes every 2 seconds through up to three, settles back, rests 30 seconds, and repeats. Only questions of 32 characters or fewer that fit completely at the launcher's width are used (fitsLauncher measures by temporarily putting the text in and comparing scrollWidth with clientWidth), so nothing is ever shown cut off. Clicking while a question is showing opens the chat and asks it.

The details that make it polite:

  • Pointing at it, or keyboard focus on it, holds it still; it resumes when the pointer leaves. Only keyboard focus holds it (:focus-visible), because closing the chat moves focus to the launcher, and that shouldn't freeze it for a mouse user.
  • Paused while the chat is open, restarted 3 seconds after it closes.
  • Never with reduced motion, or with data-teaser="off" on the script tag.
  • One chain of timers at a time: later() clears any pending step before scheduling the next, and a teaserGeneration counter makes stale fade-outs do nothing after a reset. Without these, overlapping timers would make text flicker.
  • Width animation: to animate from one width to another, the code sets the old width in pixels, forces the browser to apply it (reading launcher.offsetWidth does that), then sets the new width, and a CSS transition animates between them.

The timings were trials: the step was 1 second (too fast to read), the rest was 5 minutes, and clicking once stopped the teaser for good; on 17 to 18 Oct the step became 2 seconds, the rest 30 seconds, and it keeps running after a click. Both trial changes are separate commits, so either can be reverted alone (recorded in the backlog).

13. Events, keyboard and accessibility

input.addEventListener("keydown", function (e) {
  if (e.key === "Enter" && !e.shiftKey) {
    e.preventDefault();
    send.click();
  }
});

shadow.addEventListener("keydown", function (e) {
  if (e.key === "Escape" && isOpen) close();
});

function close() {
  isOpen = false;
  panel.hidden = true;
  launcher.hidden = false;
  launcher.focus();
  if (teaserRestart) teaserRestart();
}

var lastLogHeight = 0;
if (typeof ResizeObserver !== "undefined") {
  new ResizeObserver(function () {
    var wasAtEnd = log.scrollHeight - log.scrollTop - (lastLogHeight || log.clientHeight) < 24;
    lastLogHeight = log.clientHeight;
    if (wasAtEnd) toEnd();
  }).observe(log);
}
  • Enter sends, Shift+Enter makes a new line. preventDefault() stops Enter inserting a line break.
  • Escape closes the panel, "which people expect of anything dialog-shaped", and focus returns to the launcher, so keyboard users aren't lost.
  • Labels for screen readers: the panel is role="dialog" labelled "Chat"; the log is a live region; the input, send, close and thumbs buttons all have aria-labels; the launcher's label names the school ("Chat with Pyramid Yogshala") or the teased question ("Ask: What food is provided?").
  • Keeping the newest message in view. When "Talk to the team" appears or the input grows, the message area shrinks but keeps its scroll position, so a short last reply slid out of view. A ResizeObserver (a browser API that calls a function when an element's size changes) scrolls back to the end, but only if the visitor was already at the end before the change: someone who scrolled up to reread is left alone. It compares against the height before the change, because by the time the observer runs, the area has already shrunk.
  • The text box grows with its content up to 120 pixels, then scrolls.
  • "Start a new chat" forgets the stored conversation id, clears the log, and shows the greeting again.
  • Mounting: the host element is added to document.body once the page has loaded (DOMContentLoaded), or at once if it already has.

15. Challenges we faced

1. Asterisks in replies

The model wrote **Name**; the widget, correctly inserting text as text, showed the asterisks. Rendering Markdown properly would mean HTML from model output. Fix (16 Oct): a tiny bold-only renderer built from DOM calls; checked with Node.js against a minimal DOM, then by a browser test with an HTML payload inside bold markers.

2. Sources longer than the answers

Each reply listed its source passages, often longer than the reply itself. Removed from the widget (and the API); chunk ids are logged instead.

3. Streaming felt robotic

Word-by-word streaming (POST /chat/stream with server-sent events, the widget reading the stream as it arrived) was built and reverted the same day. Replaced by bubbles; the reverted commit is kept in history in case streaming one bubble at a time is wanted later.

4. Bubbles that never appeared

Measured on 40 real replies: 29 would be a single bubble, because the model mostly wrote one paragraph. The widget change alone did little; the prompt was changed to write chat-style short paragraphs (paragraphs per reply 1.95 → 2.62 on the evaluation, with no loss in grounding).

5. A silent install failure

A wrong domain gave a silent 403: the chat just said "not available" and the installer had no idea why. Fix: [sitechat] console messages, the install guide table, and browser tests for both cases.

6. The newest message slid out of view

When "Talk to the team" appeared, the chat area got shorter but kept its scroll position. Fix (17 Oct): the ResizeObserver, with care not to pull down a visitor reading back. Three browser tests cover it.

7. Making the way to a person hard to miss

A visitor who skims replies might never see the bot's offer to involve the team. Fix: a full-width "Talk to the team" button in the school's colour, with a person icon and two pulses when it first appears (not with reduced motion), which sends "I'd like someone from the team to contact me." as a visitor message, so the normal tool flow records the request and asks for an email.

8. Tuning the teaser by trial

One-second steps were too fast to read; a 5-minute rest and stop-on-click were changed to 30 seconds and keep-running, as trials in separate commits so each can be reverted alone. The decisions and how to undo them are written in the backlog (item 98).

Glossary

IIFE
Immediately invoked function expression: a function defined and called at once, keeping its variables private.
DOM
Document Object Model: the browser's tree of elements for a page, which JavaScript reads and changes.
Shadow root / shadow DOM
A separate, encapsulated element tree attached to an element; page CSS doesn't cross into it.
innerHTML vs textContent
Parse a string as HTML / set it as plain text.
XSS
Cross-site scripting: getting your code to run on someone else's page, usually by injecting HTML.
CSS custom property
A named value (--accent) reused with var().
Media query
CSS that applies only in some conditions (dark mode, reduced motion, narrow screens).
localStorage
A small per-website key-value store in the browser.
Promise
An object for a result that arrives later; .then, .catch, .finally attach what happens next.
fetch
The browser's function for sending HTTP requests.
setTimeout
Run a function after a delay in milliseconds.
ARIA attributes
role, aria-label, aria-live, aria-pressed: information for screen readers.
ResizeObserver
A browser API that reports when an element's size changes.
Playwright
A library that drives real browsers for testing.
WebKit
The browser engine behind Safari.

Check yourself

The snippet is pasted twice on a page. What happens?

The second copy sees window.__sitechat already set and stops, so only one chat appears.

Why can't the school's CSS turn our buttons red, and what one style is allowed through?

The widget lives in a shadow root, which page CSS can't enter. The font family is inherited on purpose, so the widget matches the site.

Why does the widget never use innerHTML, even for its own fixed markup?

Model output inserted as HTML could run code on the school's page (XSS). Using only safe DOM calls everywhere means nobody can later interpolate text into a template by accident.

How does "Our founder is **Ravi Nagar**." become bold safely?

split with a capturing group gives ["Our founder is ", "Ravi Nagar", "."]; the odd piece becomes a <strong> with textContent; nothing is parsed as HTML.

The server returns 503 with "This chat has answered a lot of questions today...". What does the visitor see?

That exact message as a notice, because the server's 503 messages are written for visitors. The chat stays usable.

Why does the conversation id live in localStorage rather than a cookie?

A cookie from our server on the school's page is third-party and often blocked; localStorage belongs to the page, is read only when needed, and keeps the server stateless.

Why are browser tests served from localhost while the widget comes from 127.0.0.1?

To make every request cross-origin, as on a real school's site, so the Origin check and CORS behave exactly as in production.
