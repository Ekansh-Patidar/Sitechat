Quality has three layers in Sitechat: tests (does the code do what we intend?), checks (linting, types, security scans, secrets, dependencies, run on every push), and evaluations (does the AI answer well and resist misuse?). Safety is a map of defences against the OWASP Top 10 for LLM applications, plus privacy and abuse controls. This phase explains each layer with real numbers from running them on this laptop today.

1. Why tests, and what makes a good one

A test is code that runs your code with known inputs and checks the result. Its value is that it runs every time anything changes, so a mistake in one place that breaks something elsewhere is caught in a minute, not by a visitor. Three properties make tests worth having, and Sitechat's history has examples of each going wrong:

  • It can fail. A test that always passes is worse than none, because it gives false confidence. Sitechat had one (Phase 4b, challenge 8): it patched the wrong name, so its assertion could never fail. Proven by removing the guard it was meant to protect: still green.
  • It's fast and offline. Tests that need the internet or keys fail in CI, cost money, and get skipped. Sitechat's tests made real API calls three separate times early on; each time they passed locally (where .env has keys) and failed on GitHub.
  • It tests behaviour, not wiring. "A visitor with an email and a contact request gets one email to the team with Reply-To set" survives refactoring; "function X calls function Y" doesn't.

2. pytest in five ideas

  1. Test functions. Any function named test_* in a file named test_*.py is collected and run. It passes unless an assert fails or an exception escapes. 
    def test_lookalike_domain_is_rejected(client):
    r = client.get("/config", headers={"X-Site-Key": "pk_valid", "Origin": "https://evil-yogaschool.com"})
    assert r.status_code == 403
  2. Fixtures. A function marked @pytest.fixture builds something tests need; a test asks for it by naming it as a parameter (client above). The fixture in test_api_security.py builds an app with in-memory stores and a test tenant. yield in a fixture splits set-up from clean-up.
  3. Parametrize. @pytest.mark.parametrize("hops, xff, expected", [...]) runs one test with many inputs: test_client_ip checks several X-Forwarded-For headers in one function.
  4. Mocks and patching. unittest.mock.patch("app.agent.orchestrator.complete_with_tools", fake) temporarily replaces a function where it's looked up. MagicMock() is an object that accepts any attribute or call, and can record how it was used (assert_called_once()). monkeypatch (a pytest fixture) changes settings or attributes for one test and restores them after.
  5. Expected failures. @pytest.mark.xfail(strict=True, reason="backlog 97") marks a known bug: the test is expected to fail. Strict means that if it starts passing, pytest reports an error, so when the bug is fixed you're forced to remove the marker. Sitechat used this for two known gaps (a failed summary skipping the email; a lead store outage failing the turn); both were later fixed and the markers removed.

FastAPI's TestClient sends HTTP requests to the app in the same process, without a network or a server: client.post("/chat", headers=..., json=...) returns a real response with status, headers and JSON. Every API test uses it.

5. Failure injection: breaking things on purpose

tests/test_failure_injection.py "breaks one thing (the model API, a tool call, a store, the lead summary) and checks the failure is contained: a polite message rather than a stack trace, nothing half-stored, and the lead email still going out where it can." Every test, by name:

  • test_model_api_failure_is_a_503_with_a_readable_message (rate limit, timeout, connection and server errors)
  • test_model_failure_after_a_tool_call_keeps_the_recorded_request
  • test_tool_arguments_that_are_not_json_still_record_the_request
  • test_unknown_tool_is_reported_back_and_the_turn_continues
  • test_a_model_that_keeps_calling_tools_is_stopped
  • test_tool_arguments_of_the_wrong_type_are_ignored
  • test_lead_summary_failure_still_sends_the_email
  • test_running_summary_failure_does_not_skip_the_lead_email (was a strict xfail)
  • test_a_failed_turn_write_still_emails_and_flags
  • test_store_outage_is_a_plain_500_without_details, test_tenant_store_outage_is_a_plain_500
  • test_facts_outage_still_gets_a_reply
  • test_lead_store_outage_still_gets_a_reply (was a strict xfail), test_lead_store_outage_during_a_contact_request

Writing these found a real gap before any test was written: nothing caught retrieval errors, so an embedding or Pinecone outage turned every message into a 500. It was fixed first (reply without documents), and the two remaining gaps were recorded as strict xfails with their backlog numbers until fixed. That's the method: list the dependencies, break each one, decide what should happen, and make it a test.

6. Coverage: what the numbers say

Coverage is the share of lines of code that ran during the tests. CI requires at least 80% of app/ (it was 85% when the floor was added; today 85.66%). Coverage tells you what is definitely not tested; high coverage doesn't prove the tests check the right things.

The pattern is clear and honest: logic is covered; the thin layers that talk to real cloud services aren't. Those are exactly where Firestore-only bugs lived (the field-wiping set). Emulator tests (backlog 25) are the fix.

9. The safety map: OWASP Top 10 for LLM applications

The OWASP Top 10 for LLM Applications is the industry checklist of security risks specific to AI apps. Sitechat's safety phase (17 Oct) mapped every one, from notes/backlog.md:

RiskWhat could happen hereDefences in Sitechat
Prompt injectionA visitor or a planted line makes the bot ignore its rules.Prompt rules (only the system message instructs; no role changes); reference material labelled as such; invisible Unicode stripped; facts and documents screened; attack eval.
Sensitive information disclosureVisitor details leak to the model, logs, Sentry or other visitors.Contact details removed before the model; Sentry with no locals or bodies; namespace isolation; the data attacks in the eval.
Supply chain / data poisoningA bad dependency or poisoned content.Pinned dependencies, pip-audit, Dependabot, hashed gitleaks download; ingested content screened; we prepare documents ourselves.
Improper output handlingModel text becomes HTML on the school's page or in the email.Widget renders text only (bold via DOM); email escapes everything; links defanged; the output attacks.
Excessive agencyThe model is given power to do damage.Two tools: one records a request (fixed recipient: the school), one reports details (capped, filtered). No tool sends, deletes or browses.
System prompt leakageThe rules or hidden context are read out.Rule against revealing instructions; nothing secret in the prompt; install guide: treat documents and facts as public; leak markers checked in the attack eval.
Vector and embedding weaknessesOne tenant's documents reached from another's query.Pinecone namespace per tenant, enforced by the database.
MisinformationConfident wrong answers.Grounding; facts verbatim; "don't know" and near-miss rules; faithfulness eval; thumbs-down review.
Unbounded consumptionRunning up the AI bill or using the bot as a free chatbot.Daily token budget per tenant; 600-token reply cap; scope rule; rate limits; consumption attacks.

Not done (by decision): a separate moderation or classifier call before each reply. Backlog 110: "an extra call and ~0.5 s per message. Only if the attack eval shows the prompt rules are not enough."

10. Privacy

  • Minimisation: contact details are extracted once and kept only on the lead; messages hold [email provided].
  • Separation: leads in their own collection, apart from conversations.
  • Retention: everything personal expires 365 days after last activity (TTL); a test enforces the stamp on every write.
  • Deletion on request: delete_tenant <tenant> --conversation <id> (finding a visitor's conversations by email alone isn't built yet).
  • Error reports: no personal data to Sentry, proven with the real SDK.
  • Transparency: "AI assistant · Answers can be wrong" in the widget, a privacy link when the school provides one, and a note where the email goes when typed.
  • No email to visitor-typed addresses: only the school's team receives email.
  • Exports: lead CSVs and conversation dumps are gitignored.

Open business items: each school's privacy policy, a data processing agreement listing sub-processors (OpenAI, Pinecone, Google Cloud, Resend, Sentry), and data residency terms (backlog 33, 63, 75).

12. Known gaps

  • No Firestore emulator tests (transactions only tested in memory).
  • No load, stress, spike or soak tests; no concurrency test of two messages at once.
  • No alerting.
  • No automated security scan of the live API (OWASP ZAP), no real-device or screen-reader passes.
  • The post-deploy smoke test isn't a pipeline step yet.
  • The date-as-phone false positive found while writing Phase 4d.

Knowing your gaps precisely is itself a quality signal. In an interview, "here's what I'd test next and why" lands better than "it's fully tested".

13. Challenges we faced

1. Tests that called real APIs (three times)

Each time, new code called an outside service and the test didn't stub it; it passed locally with keys in .env and failed on GitHub without them. The first led to store injection into create_app; later ones to stubbing the model in the security tests and embeddings in failure tests (with an autouse fixture: "No test here may reach a real API"). Lesson recorded: "when adding anything that calls out, ask what the test does when that service is absent."

2. A test that could never fail

Patched the definition site instead of the lookup site, so its mock was never used. Found by deliberately breaking the code it guarded. Lesson: make each new test fail once on purpose.

3. A test that needed a local .env

One test passed only because the developer's .env supplied a value; it would fail on a clean machine. Fixed when the requirements were split (17 Oct); Settings(_env_file=None, ...) is the pattern for tests that must ignore local configuration.

4. Sentry leaked an email, confirmed before fixing

Rather than trusting send_default_pii=False, the team triggered an error with Sentry's defaults and found the visitor's email in the report, from a local variable. Then turned off locals and bodies, and wrote a test with the real SDK proving the email no longer appears.

5. The secrets scanner failed on Dependabot

gitleaks-action calls GitHub's API on pull requests and failed on Dependabot's PRs (which run with restricted permissions). Fix: download the gitleaks program itself at a pinned version, verify its hash, and scan the full history the same way on every push and PR.

6. The type checker's 30 errors

Adding mypy surfaced 30 type errors, mostly from treating Firestore's optional to_dict() as always a dict. None crashed in practice (missing documents were checked first), but making it explicit (or {}) means the next change can't break that assumption silently.

Glossary

Unit / integration / end-to-end test
One function / several parts together / the whole system as a user sees it (the browser tests).
Fixture
A pytest function that prepares something a test needs.
Mock / stub / fake
Stand-ins for real dependencies, recording calls or returning fixed answers.
Strict xfail
A test expected to fail; if it passes, pytest errors, forcing the marker's removal.
Coverage
The percentage of code lines executed by tests.
Linter
A tool that flags likely bugs and bad patterns without running the code.
Static type checking
Checking type annotations for consistency without running the code (mypy).
SAST
Static application security testing: scanning code for insecure patterns (bandit).
Dependency audit
Checking installed packages against vulnerability databases (pip-audit).
Failure injection
Deliberately breaking a dependency to check the system degrades gracefully.
Graceful degradation
Doing something useful (a reply without documents) when part of the system fails.
Data minimisation
Collecting and keeping only the personal data you need.

Check yourself

Why is a test that can't fail worse than no test?

It gives false confidence: the protected behaviour can break with the suite still green.

Name four outside services and how tests replace each.

Firestore → in-memory stores injected into create_app; Pinecone → in-memory/no-op vector store; OpenAI chat → patched complete_with_tools; embeddings → patched embed_query; Resend → patched Emails.send.

What does a strict xfail give you that a comment "known bug" doesn't?

The test runs every time; when the bug is fixed the test passes, and strict mode fails the run until the marker is removed, so the record stays true.

Coverage is 85.66%. Where are the gaps and why?

In the Firestore and Pinecone store classes and the reranker: tests use in-memory stores and the reranker is off. Emulator tests would close the store gap.

What do ruff, mypy, bandit, gitleaks, hadolint and pip-audit each catch?

Likely bugs and unused code; type errors; insecure code patterns; committed secrets; Dockerfile mistakes; vulnerable dependencies.

Which OWASP risk does the daily token budget address, and why aren't rate limits enough?

Unbounded consumption. Rate limits count requests; cost is tokens, and one long conversation costs far more than many short ones.

Why isn't there a moderation call before each reply?

It would add a call and about half a second per message; the attack evaluation shows the prompt rules hold (29/29), so it's deferred until they don't.
