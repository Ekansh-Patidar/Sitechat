1. Sitechat in one paragraph

Sitechat is a chat assistant that a business puts on its website. A visitor clicks a small chat bubble and types a question, like "How much is the 200-hour course?". Our server finds the right information in that business's own documents and price sheet, asks an AI model to write a short answer using only that information, and sends the answer back to the bubble. If the visitor leaves an email address or asks to be contacted, the server emails the business with everything the visitor asked. One copy of Sitechat serves many businesses at once; each business is called a tenant. The first tenant is a yoga school, Pyramid Yogshala.

Visitor types a question→ Chat bubble sends it to our server→ Server finds the school's information→ AI writes an answer from it→ Answer shown in the bubble

Phases 1 to 3 explain each arrow in that picture. This phase covers the ground they stand on.

2. What a program is

A computer only does exactly what it is told, one small step at a time. A program is a written list of those steps. The text we write is called source code (or just "code"), and it lives in ordinary text files.

Analogy

A program is a recipe. The recipe (code) is written once; cooking it (running the program) can happen many times. A recipe that says "add salt" without saying how much leaves the cook guessing; computers never guess, so code must be exact.

There are many programming languages. Sitechat's server is written in Python, and the chat bubble that runs inside the visitor's browser is written in JavaScript, because browsers only run JavaScript.

Python is interpreted: a program called the Python interpreter reads your code and carries it out line by line. You run a Python file by asking the interpreter to read it:

python hello.py

If hello.py contains print("Hello"), the screen shows Hello. That is the whole idea; everything else is detail.

A server is a program that waits

Most programs start, do their job and stop. A server starts and then waits, sometimes for months, listening for requests. When one arrives, it does the work and replies, then waits again. Sitechat's backend is a server: it waits for chat messages.

3. Files, folders and paths

A file holds content (text, an image). A folder (also called a directory) holds files and other folders. A path is the address of a file, listing the folders you go through to reach it.

In Sitechat

The whole project lives in one folder on your computer: D:\projects\sitechat. Inside it, the chat logic is in D:\projects\sitechat\app\agent\orchestrator.py. Inside the project we usually write paths relative to the project folder, with forward slashes: app/agent/orchestrator.py.

The last part of a file name after the dot is its extension; it tells you (and programs) what kind of file it is.

4. The terminal

The terminal (also called the command line or shell) is a window where you type commands instead of clicking. Developers use it because it is precise, repeatable and can be written down: "run this command" is easier to share than "click here, then there".

Analogy

Clicking around a file browser is like pointing at things in a shop. The terminal is like handing the shopkeeper a written list: exact, fast, and you can reuse the list next time.

On Windows you have two common shells: PowerShell (Windows' own) and Git Bash (installed with Git, uses Linux-style commands). The project's commands work in both, with small differences.

Each is a program, started with some arguments (the words after the command name) that tell it what to work on.

5. Python and its versions

Python is released in numbered versions: 3.12, 3.13, 3.14 and so on. Newer versions add features and occasionally remove old ones, so the same code can behave differently on two versions.

In Sitechat

Your laptop runs Python 3.14 (in the project's .venv folder). The live server and the automatic checks on GitHub run Python 3.12, fixed in the Dockerfile (FROM python:3.12-slim) and in .github/workflows/tests.yml. Fixing one version for production means a Python update on your laptop can never surprise the live server.

6. Virtual environments

Python projects use packages: code written by other people that you download (next section). Different projects may need different versions of the same package. A virtual environment is a private folder of packages for one project, so projects don't interfere with each other.

Analogy

A virtual environment is a separate toolbox for each job. The plumbing job's box never gets mixed up with the electrical job's box, even if both contain a "screwdriver" of different sizes.

# create it once, in the project folder
python -m venv .venv

# use it: either "activate" it, or call its Python directly
.venv\Scripts\activate            # PowerShell / cmd
.venv/Scripts/python.exe -m pytest  # call it directly (what I use in this project)
In Sitechat

The folder .venv/ in the project is the virtual environment. It is listed in .gitignore, so it is never uploaded: anyone can recreate it from the requirements files.

7. Packages and requirements files

A package (or library) is ready-made code you install instead of writing yourself, for example a package that knows how to talk to OpenAI. Packages are published on PyPI (the Python Package Index) and installed with pip, Python's installer.

A project lists the packages it needs in a requirements file, so anyone can install exactly the same set with one command:

pip install -r requirements-dev.txt

Each line pins an exact version with ==, such as fastapi==0.142.4. Pinning means the live server and your laptop run the same code; without it, a package update could change behaviour without anyone touching Sitechat.

Two files, two audiences

  • requirements.txt: what the live server needs to run.
  • requirements-dev.txt: everything in the first file, plus tools only developers need (tests, code checkers). The live server does not install these, which keeps it smaller.

8. Python: the parts this project uses

You don't need all of Python to read Sitechat. These are the pieces it actually uses, each shown with real code from the project.

8.1 Values, types and variables

A value is a piece of data. Its type says what kind: text, a whole number, true/false. A variable is a name you give a value so you can use it later.

MAX_SKIP_LENGTH = 25          # a whole number (int)
display_name = "Pyramid Yogshala"  # text (str, "string")
is_active = True              # True or False (bool)
score = 0.86                  # a decimal number (float)
privacy_url = None            # "nothing here yet" (None)

Everything after # is a comment: a note for humans that Python ignores. Sitechat's code has many comments explaining why something is done.

Names written in CAPITALS, like MAX_SKIP_LENGTH, are constants by convention: values meant never to change while the program runs. Names starting with an underscore, like _digits, mean "for use inside this file only".

8.2 Text (strings) and f-strings

Text goes in quotes. An f-string (a string with f before the quote) lets you drop variables into text with curly braces:

tenant_id = "pyramid-yogshala"
namespace = f"tenant-{tenant_id}"     # "tenant-pyramid-yogshala"
In Sitechat

That exact pattern names each school's private section in the search database (app/retrieval/vector_store.py), so one school's documents can never appear in another school's answers.

Text in three quotes ("""…""") can span many lines. At the top of a file or function it is a docstring: the built-in explanation of what that file or function is for. Nearly every Sitechat file starts with one.

8.4 Decisions and repetition

if not first_name:
    greeting = "Hi,"

    greeting = f"Hi {first_name},"

Indentation matters in Python. The lines pushed in under if or for belong to it; when the indentation ends, so does the block. Other languages use braces { } for this; Python uses spaces.

A comprehension builds a list in one line. Sitechat uses them often:

# "every question whose status needs an answer"

8.5 Functions

A function is a named, reusable piece of code. You give it inputs (parameters), it does its job and gives back a result (return). This real one, from app/leads/extraction.py, keeps only the digits in some text:

app/leads/extraction.py

def _digits(text: str) -> str:
    return re.sub(r"\D", "", text)
  • def starts a function; _digits is its name (the underscore: only used in this file).
  • text: str is a parameter called text, and : str is a type hint saying "this should be a string". Hints don't change what Python does; they help people and checking tools (mypy) catch mistakes.
  • -> str says the function returns a string.
  • re.sub(r"\D", "", text) replaces every non-digit (\D) with nothing. So _digits("+91 98765-43210") returns "919876543210".

A bigger one from the same file. It finds an email address in a visitor's message and hides it, before the AI ever sees the message:

app/leads/extraction.py (shortened)

EMAIL_PLACEHOLDER = "[email provided]"

def extract_contact(message: str) -> tuple[str, str, str]:
    """Find an email and phone number, and return the message with them removed."""
    email = ""
    phone = ""
    redacted = message

    email_match = EMAIL_RE.search(redacted)
    if email_match:
        typed = email_match.group(0)
        redacted = redacted.replace(typed, EMAIL_PLACEHOLDER)
        email = typed.lower()
    ...
    return email, phone, redacted
  1. It starts with empty results, and a copy of the message to edit.
  2. EMAIL_RE.search(...) looks for something shaped like an email (explained next).
  3. If found, it swaps the address in the text for [email provided], and keeps the address, in lowercase, to store separately.
  4. It returns three things at once, as a tuple: the email, the phone, and the cleaned message.
In Sitechat

Why bother? The cleaned message is what goes to the AI model and into the chat history. The visitor's address is kept in one place (the lead record) that can be deleted, instead of being re-sent to OpenAI with every later message.

8.6 Regular expressions

A regular expression ("regex") is a tiny pattern language for finding text shapes. re is Python's built-in regex module.

EMAIL_RE = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")

Read it as: some letters, digits or . + -, then @, then a domain name, then a dot and more letters. You don't need to write these fluently; know that they find patterns, and that Sitechat uses them to spot emails and phone numbers, to recognise "hi"/"thanks" messages (app/retrieval/triage.py), and to match course names.

8.7 Files of code: modules, packages and imports

Every .py file is a module. A folder of modules with an __init__.py file in it is a package. One module uses another's code by importing it:

import re                                    # Python's own regex module
from app.config import get_settings          # one function from app/config.py
from app.tenants.models import Tenant        # one class from app/tenants/models.py

The dotted name follows the folders: app.tenants.models is the file app/tenants/models.py. That is how the 65 files in app/ fit together into one program.

Scripts are run the same way, as modules, from the project folder:

python -m scripts.ingest pyramid-yogshala docs/pyramid-yogshala

Inside a script you will see this at the bottom:

if __name__ == "__main__":
    main()

It means "only run main() when this file is started directly, not when another file imports it". Tests import scripts to check them, without running them for real.

8.8 Classes and objects

A class is a blueprint for a kind of thing; an object is one thing made from it. The blueprint lists the thing's fields (its data) and methods (functions that belong to it).

Analogy

The class is the blank admission form; each filled-in form is an object. Every form has the same boxes; each has different answers.

app/tenants/models.py (shortened)

from pydantic import BaseModel, Field

class Tenant(BaseModel):
    tenant_id: str                      # e.g. "pyramid-yogshala"; required
    site_key: str                       # the public key in the website snippet
    display_name: str                   # shown in the chat header
    allowed_domains: list[str] = Field(default_factory=list)
    greeting: str = "Hi! Ask me anything about our courses."
    is_active: bool = True
    team_email: str = ""

school = Tenant(tenant_id="pyramid-yogshala",
                site_key="pk_pyramid_yogshala_001",
                display_name="Pyramid Yogshala")
school.display_name     # "Pyramid Yogshala"
school.is_active        # True (the default)
  • class Tenant(BaseModel) makes a class called Tenant, built on Pydantic's BaseModel.
  • Each line name: type is a field. Fields with = something have a default; fields without one must be given.
  • Field(default_factory=list) means "start with a new empty list for each tenant". Writing = [] would make all tenants share one list, a classic Python trap.

Why Pydantic

Pydantic checks the data whenever an object is made. If a tenant record arrives from the database with is_active="maybe" or no site_key, Pydantic refuses it immediately with a clear error, instead of the server failing confusingly later, in the middle of a visitor's chat. The same idea checks every chat message that arrives from the internet (app/api/schemas.py).

Say it in an interview

"Every piece of data that crosses a boundary, from the browser, the database or an environment variable, goes through a Pydantic model, so bad data fails at the edge with a clear message instead of deep inside the request."

8.9 Errors: try, except, raise

When something goes wrong, Python raises an exception: it stops what it was doing and passes an error upwards. Code can catch it and decide what to do instead.

try:
    results = search_documents(question)
except Exception:
    logger.exception("Retrieval failed")   # record the full error for us
    results = []                           # carry on without documents
In Sitechat

This is how the bot survives an outage: if the search database is down, app/agent/orchestrator.py catches the error and still answers, saying it doesn't have the details, instead of showing the visitor a crash. If OpenAI itself fails, app/agent/llm.py turns the error into a polite "Please try again in a moment".

8.10 Decorators

A line starting with @ just above a function is a decorator: it wraps the function with extra behaviour, without changing the function's own code.

@router.post("/chat")      # FastAPI: "when a request arrives at /chat, run this function"
def chat(...):
    ...

@lru_cache                 # "remember the result; don't compute it twice"
def get_settings():
    return Settings()

You'll meet @router.post in Phase 4 (it is how web addresses map to code) and @patch in Phase 7 (tests use it to swap the real AI for a fake one).

8.11 The with statement

with opens something and guarantees it is closed afterwards, even if an error happens in between:

with open("leads.csv", "w", encoding="utf-8-sig") as f:
    f.write("...")
# the file is closed here, whatever happened

8.12 Abstract classes: promising a shape

This is the hardest idea in this phase, so we go slowly, in six steps, using one real example: how Sitechat keeps its list of tenants (the businesses using it).

Step 1: the problem

When a chat message arrives, the server must find out which business it belongs to. The message carries a site key (like pk_pyramid_yogshala_001), and the server looks up the tenant with that key. But where are tenants kept?

  • On the live server: in Firestore, Google's database in the cloud. Using it needs internet, a Google account and passwords.
  • When running tests on your laptop: we don't want any of that. Tests should run in seconds, offline, cost nothing, and never touch real customer data. So there we keep tenants in a plain Python dictionary in memory, which disappears when the test ends.

So there are two very different storage places. The code that answers chats should not have to say "if we are testing, look in the dictionary, otherwise ask Firestore" everywhere. We want it to just say "store, give me the tenant with this key", and not care which store it is.

Analogy

A company writes a job description for a "receptionist": must be able to (1) find a visitor's booking, (2) record a new booking. It doesn't say how. One receptionist uses a paper notebook; another uses a computer. The manager just says "find the booking for Mr Rao" and doesn't care which receptionist is on shift today.

In Sitechat: the job description is TenantStore. The notebook receptionist is InMemoryTenantStore (tests). The computer receptionist is FirestoreTenantStore (live). The manager is the code that handles chats.

Step 2: writing the promise (the abstract class)

An abstract base class (ABC) is that job description, written in Python. It lists the methods every store must have, but does no work itself. Here is the real one, complete:

app/tenants/store.py

from abc import ABC, abstractmethod

class TenantStore(ABC):
    @abstractmethod
    def get_by_site_key(self, site_key: str) -> Tenant | None:
        """Return the tenant owning this site key, or None."""
        raise NotImplementedError

    @abstractmethod
    def get_by_id(self, tenant_id: str) -> Tenant | None:
        """Return a tenant by internal id, or None."""
        raise NotImplementedError

    @abstractmethod
    def save(self, tenant: Tenant) -> None:
        """Create or overwrite a tenant."""
        raise NotImplementedError

    @abstractmethod
    def with_facts_sheet(self) -> list[Tenant]:
        """Active tenants with a facts sheet, for the scheduled sync."""
        raise NotImplementedError

Line by line:

  • from abc import ABC, abstractmethod: abc is a module built into Python (nothing to install). Its name stands for "abstract base classes".
  • class TenantStore(ABC): a class built on ABC. That marks it as a promise only: Python will not let anyone make a TenantStore object directly.
  • @abstractmethod: a decorator (8.10). It marks the method below as a duty: "every real store must write its own version of this".
  • def get_by_site_key(self, site_key: str) -> Tenant | None: the method's name, its input and its result. self is the store object itself; Python fills it in automatically, so callers write just store.get_by_site_key("pk_abc"). site_key: str means the input is text. -> Tenant | None means "gives back a Tenant, or None if no tenant has that key".
  • The text in """triple quotes""" is a docstring (8.2): a note for people saying what the method must do.
  • raise NotImplementedError: the body of the promise does nothing useful; it is just a placeholder that complains if somehow run.

So the promise says: "Any tenant store can find a tenant by site key, find one by id, save one, and list the tenants that have a facts sheet." Nothing about dictionaries or databases.

Step 3: keeping the promise, two different ways

Each real store is a class that says (TenantStore) after its name, meaning "I am a kind of TenantStore", and then writes every promised method its own way.

app/tenants/store.py: the test version, a dictionary

class InMemoryTenantStore(TenantStore):
    """Holds tenants in a dict. Used by tests."""

    def __init__(self) -> None:
        self._by_id: dict[str, Tenant] = {}      # starts empty

    def get_by_site_key(self, site_key: str) -> Tenant | None:
        for tenant in self._by_id.values():      # look at each tenant
            if tenant.site_key == site_key:
                return tenant                    # found it
        return None                              # nobody has this key

    def get_by_id(self, tenant_id: str) -> Tenant | None:
        return self._by_id.get(tenant_id)

    def save(self, tenant: Tenant) -> None:
        self._by_id[tenant.tenant_id] = tenant   # put it in the dict

    def with_facts_sheet(self) -> list[Tenant]:
        return [t for t in self._by_id.values() if t.is_active and t.facts_sheet_id]

__init__ is the method Python runs when the object is first made; here it creates an empty dictionary. The underscore in _by_id is a convention meaning "private: only this class touches it".

app/tenants/store.py: the live version, Firestore (shortened)

class FirestoreTenantStore(TenantStore):
    """Stores tenants in Firestore, one document per tenant."""

    def __init__(self, project_id: str) -> None:
        self._db = firestore.Client(project=project_id)   # connect to Google

    def get_by_site_key(self, site_key: str) -> Tenant | None:
        query = (
            self._db.collection("tenants")
            .where(filter=firestore.FieldFilter("site_key", "==", site_key))
            .limit(1)
        )
        for doc in query.stream():
            return Tenant(**(doc.to_dict() or {}))
        return None

    def save(self, tenant: Tenant) -> None:
        data = tenant.model_dump(mode="json")
        self._db.collection("tenants").document(tenant.tenant_id).set(data)

    # ... get_by_id and with_facts_sheet, also written for Firestore

You don't need to understand the Firestore lines yet (Phase 6 covers them). In plain words, get_by_site_key asks the database: "in the tenants collection, find one record whose site_key equals this one", and turns what comes back into a Tenant object.

Compare the two side by side:

Step 4: Python checks the promise is kept

Suppose someone writes a new store and forgets save. The moment they try to make one, Python refuses:

class ForgetfulStore(TenantStore):
    def get_by_site_key(self, site_key): ...
    def get_by_id(self, tenant_id): ...
    def with_facts_sheet(self): ...
    # no save!

ForgetfulStore()
# TypeError: Can't instantiate abstract class ForgetfulStore
#            without an implementation for abstract method 'save'

TenantStore()
# also refused: the promise itself can't be used as a store

That is the point of @abstractmethod: a missing method is caught at once, when the store is made, not weeks later when a visitor's chat happens to need it.

Step 5: the code that uses a store doesn't know which one it has

Here is the "manager": the code that checks every chat request's site key.

app/api/dependencies.py (shortened)

store: TenantStore = request.app.state.tenant_store
...
tenant = store.get_by_site_key(site_key)

The type hint says only TenantStore: "some store that keeps the promise". This code calls get_by_site_key and gets a Tenant or None. It never says the word Firestore or dictionary. The same line works in tests and live, unchanged.

Step 6: choosing which store, once, at the start

The decision is made in exactly one place: when the app is built (app/main.py). The app takes stores as inputs; if none is given, it makes the real Firestore one.

app/main.py (shortened)

def create_app(tenant_store=None, conversation_store=None, ...):
    app = FastAPI(...)
    if tenant_store is not None:
        app.state.tenant_store = tenant_store      # use the one we were given
    ...

# later, when the server starts up:
    if not hasattr(app.state, "tenant_store"):     # nobody gave us one?
        app.state.tenant_store = FirestoreTenantStore(settings.gcp_project_id)

So the live server calls create_app() with nothing, and gets Firestore. A test hands in the dictionary version:

tests/test_api_security.py (shortened)

store = InMemoryTenantStore()
store.save(Tenant(tenant_id="t1", site_key="pk_valid",
                  display_name="Test School", allowed_domains=["example.com"]))

app = create_app(tenant_store=store,
                 conversation_store=InMemoryConversationStore(), ...)

Now when the test sends a chat with site key pk_valid, the same Step 5 line runs, but it is talking to the dictionary. No internet, no Google account, and the test controls exactly which tenants exist.

Handing a piece of code the things it needs from outside, instead of letting it build them itself, has a name: dependency injection. "Dependency" = the store it depends on; "injection" = we pass it in.

Live: create_app()→FirestoreTenantStore→store.get_by_site_key(...)
Test: create_app(tenant_store=InMemory...)→InMemoryTenantStore→store.get_by_site_key(...)

Why this matters

  • Fast, free, offline tests. Every data area in Sitechat (tenants, conversations, leads, facts, documents, usage, feedback) has this same pair: a promise class, an InMemory… version and a Firestore… version. Together with fake AI calls, that is why the 490+ tests run in about half a minute with no internet.
  • Easy to change the database later. If Sitechat ever moved from Firestore to another database, you would write one new class per area that keeps the same promise. The chat code, the lead code and the tests wouldn't change.
  • Safety rules live in the promise. Most store methods take a tenant_id, so it is impossible to ask for "a conversation" without saying whose. That keeps one business's data away from another's (Phase 7).
In Sitechat

Open app/conversations/store.py or app/leads/store.py and you'll see the same shape: an ABC at the top, then InMemory…, then Firestore…. Once you can read app/tenants/store.py, you can read all of them.

Say it in an interview

"Each storage area is an interface, an abstract base class, with two implementations: in-memory for tests and Firestore for production. The app receives its stores through create_app, which is dependency injection, so the request code depends only on the interface. Tests inject the in-memory stores and fake the AI calls, so the whole suite runs offline in about 30 seconds, and switching databases would mean writing new implementations, not touching business logic."

9. Git and GitHub

Git is a program that records the history of a project's files. Each saved snapshot is a commit, with a message saying what changed and why. You can look at any past version, compare versions, and undo changes.

Analogy

Git is a save-game system for code. Each commit is a save point with a label. GitHub is the cloud copy of all the save points, so they survive your laptop and others can see them.

WordMeaning
repository (repo)A project folder whose history Git tracks. D:\projects\sitechat is one; Git keeps its history in a hidden .git folder.
commitOne saved snapshot with a message. Sitechat has about 150. Each has a short id like fc39ee8.
branchA line of history. Sitechat works on one branch, main.
pushUpload your new commits to GitHub. In this project, a push also starts an automatic deploy (Phase 6).
revertMake a new commit that undoes earlier ones. You did this today: commit c7c0d84 undid four commits, without erasing them from history.
.gitignoreA list of files Git must never record.

What Sitechat keeps out of Git, and why

.env                     # secret keys
.venv/                   # the virtual environment: rebuildable, large
__pycache__/  *.pyc      # Python's own speed-up files: rebuildable
.pytest_cache/           # test tool's scratch files
service-account.json     # a Google secret key file
docs/                    # the school's source documents: their content, not code
evaluation/history/      # saved test-run results: local records
chat.txt  leads-*.csv    # exports containing visitors' personal details

The rule: secrets, personal data, and anything that can be rebuilt stay out. A check on GitHub (gitleaks, Phase 7) scans every commit ever made for leaked keys.

10. Settings and secrets

A secret is something that grants access, like a password: the OpenAI key lets anyone spend money on your account. Secrets must never be written into code, because code is copied, shared and uploaded.

Instead, programs read them from environment variables: named values the operating system hands to a program when it starts. Locally, a file called .env holds them, one per line, and is never committed. Sitechat's .env has these names (values hidden):

ENVIRONMENT=…                 # "development" on your laptop, "production" live
LOG_LEVEL=…                   # how much detail to log
GCP_PROJECT_ID=…              # which Google Cloud project holds the database
OPENAI_API_KEY=…              # the AI model
PINECONE_API_KEY=…            # the search database
PINECONE_INDEX_NAME=…
COHERE_API_KEY=…              # reranking (off by default)
RESEND_API_KEY=…              # sending lead emails
NOTIFICATION_FROM_EMAIL=…     # the address lead emails come from
SENTRY_DSN=…                  # error reporting
GOOGLE_SERVICE_ACCOUNT_FILE=… # the key file used to read Google Sheets locally

The file app/config.py describes every setting the app understands, with a default, and Pydantic fills them from the environment:

app/config.py (shortened)

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    environment: Literal["development", "production"] = "development"
    log_level: str = "INFO"
    gcp_project_id: str = ""
    openai_api_key: SecretStr = SecretStr("")
    openai_model: str = "gpt-4o-mini"
  • BaseSettings reads each field from an environment variable of the same name, ignoring capitals: OPENAI_API_KEY fills openai_api_key.
  • Literal["development", "production"] allows only those two words; a typo stops the app at start-up with a clear message.
  • SecretStr hides the value when printed or logged, so a key never ends up in a log by accident.
In Sitechat

On your laptop the values come from .env. On the live server there is no .env: Google Cloud's Secret Manager stores the keys and hands them to the server as environment variables when it starts (set up in cloudbuild.yaml, Phase 6). Same code, different source, no secret ever in Git.

Say it in an interview

"Configuration is twelve-factor style: all settings come from environment variables, validated by Pydantic at start-up. Locally that's a git-ignored .env; in production, Secret Manager injects them into Cloud Run, and the service account can read only those five secrets."

12. Starting a project like this from nothing

This is the order you would follow on day one, with what each step is for. Phase 8 repeats it with the full detail, up to a deployed bot.

  1. Install the tools: Python, Git, a code editor (VS Code), and later the Google Cloud command-line tool (gcloud).

  2. Make the folder and start Git:

    mkdir D:\projects\sitechat
cd D:\projects\sitechat
git init

  3. Make a virtual environment and install the first packages:

    python -m venv .venv
.venv\Scripts\activate
pip install fastapi uvicorn

  4. Write .gitignore first, so secrets and .venv never get committed by accident.

  5. Write the smallest server, in app/main.py:

    from fastapi import FastAPI

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

    Run it with uvicorn app.main:app --reload --port 8080, then open http://localhost:8080/health in a browser: it shows {"status":"ok"}. Sitechat's real /health still does exactly this; it is how Google Cloud checks the server is alive.

  6. Save the package list (pip freeze into requirements.txt, as UTF-8) and make the first commit:

    git add .
git commit -m "A first server with /health"

  7. Grow it one piece at a time, with a commit for each: settings, the chat endpoint, the AI call, the database, the chat bubble, tests, deployment. Sitechat's ~150 commits are exactly that, in order. Phases 1 to 7 explain each piece; Phase 8 rebuilds them in sequence.

Challenges we faced

Real problems from the project's history that come down to the first principles in this phase. Each is told in full in the phase named.

1. Two modules importing each other

main.py imported the routes, and routes.py imported the rate limiter from main.py. Python runs a module top to bottom when it's imported, so one of them was half-loaded when the other asked it for a name, and the name didn't exist yet. The fix was to move the shared object into a third module that both import (app/rate_limit.py). Phase 4a, challenge 1.

2. from x import y makes a new name

A test replaced app.leads.notify.send_lead_email with a fake, but the orchestrator had done from app.leads.notify import send_lead_email, which copies the reference into the orchestrator's own namespace at import time. The orchestrator kept calling the real function, so the test could never fail. Patch where a name is used: app.agent.orchestrator.send_lead_email. Phase 4b, challenge 8.

3. A list kept for later kept changing

While writing Phase 8's mini project, a test saved the list of messages passed to a fake model, then checked it afterwards. The code kept appending to that same list, so the saved "first call" had grown. Python passes lists by reference; anything you keep for later should be a copy (list(messages)). Sitechat's tool loop copies for the same reason. Phase 8, step 9.

4. A value that is sometimes None

Firestore's to_dict() returns a dictionary, or None for a missing document. The code passed it straight into Tenant(**...). It never crashed, because missing documents were checked first, but when the type checker (mypy) was added it found 30 such places. The fix, to_dict() or {}, makes the assumption explicit. Phase 4e, challenge 6.

5. Two versions of Python

This laptop runs Python 3.14; CI, the build and the container run 3.12. Code using a 3.14-only feature would pass here and fail on deploy. The build now runs the tests on 3.12 before anything ships. Phase 6, challenge 6.

6. A text file in the wrong encoding

Regenerating requirements.txt with PowerShell's pip freeze > requirements.txt wrote it as UTF-16, which pip can't read. Text files have an encoding (how characters become bytes); the project keeps them UTF-8 and the file says so in its first comment. Phase 10, troubleshooting.

7. Editing a file many times, and unsaved files

During one edit, the routes and the static files were registered twice in create_app; while removing the duplicates, the line app = create_app() was deleted too, giving Attribute "app" not found in module "app.main". It took three commits to fix. The project notes record two habits from this: for a file edited many times, look at the whole file rather than a description of the change; and check for unsaved files before testing (that cost about an hour, more than once). Phase 4a, challenge 2.

Check yourself

Why does Sitechat use two requirements files?

requirements.txt lists what the live server needs. requirements-dev.txt adds tools only developers need (tests, checkers). The live server installs the first only, so it is smaller and has fewer packages that could have security problems.

What would go wrong if .env were committed to Git?

The API keys in it would be in the project's history forever, visible to anyone with access to the repository. Anyone holding the OpenAI key could spend money on your account. Removing the file later doesn't remove it from history; the keys would have to be replaced.

What does python -m scripts.ingest pyramid-yogshala docs/pyramid-yogshala mean, word by word?

Run Python; -m run a module; scripts.ingest the file scripts/ingest.py; then two arguments: the tenant id, and the folder of documents to load.

What does extract_contact return for "my email is Sam@x.com"?

A tuple of three: the email in lowercase ("sam@x.com"), an empty phone (""), and the cleaned message "my email is [email provided]".

Why does Tenant use Field(default_factory=list) instead of = []?

With = [], every Tenant would share one list, so adding a domain to one school would add it to all of them. default_factory=list makes a fresh empty list for each tenant.

Why do the tests run without internet?

Every storage area has an in-memory version with the same methods as the real database version, and tests replace the AI calls with fakes. The app is built with whichever stores it is given, so tests hand it the in-memory ones.

Someone writes a new tenant store but forgets the save method. When do they find out?

As soon as they try to create one: Python raises TypeError: Can't instantiate abstract class ... without an implementation for abstract method 'save'. Because save is marked @abstractmethod in TenantStore, the mistake can't slip through to a live chat.

Where is the choice between the dictionary store and Firestore made, and why only there?

In app/main.py: create_app uses whatever stores it is given, and at startup builds Firestore ones for any not given. Everything else only talks to "a TenantStore", so making the choice in one place means the rest of the code works the same in tests and live.

Where do secrets come from on the live server?

From Google Cloud Secret Manager, which passes them to the server as environment variables when it starts. There is no .env file on the server.

Say it in an interview: the tooling in one breath

"It's a Python 3.12 FastAPI service. Dependencies are pinned in a runtime requirements file and a separate dev file for test and lint tools. Configuration comes from environment variables validated by Pydantic, with secrets in Secret Manager in production. Every storage area sits behind an interface with in-memory and Firestore implementations, which keeps the test suite offline and fast. Everything is in Git, and a push runs the tests and deploys."
