Data stores, file by file: what is saved, in what shape, and how it stays correct

Every domain in Sitechat has a model (the shape of its data, a Pydantic class) and a store (how it's saved: an abstract interface, an in-memory version for tests, a Firestore version for production). This phase opens the remaining ones: tenants, conversations, facts, usage, feedback and the programme store, and shows how they're laid out in Firestore, how concurrent writes are kept safe, and how data expires.

1. Firestore in five minutes

Firestore is Google's hosted document database. It isn't made of tables and rows like a spreadsheet-style (SQL) database; it's made of:

  • Collections: named groups, like conversations.
  • Documents: inside a collection, each with an id you choose (like pyramid-yogshala__1f1a1dca-...) and contents that look like JSON: fields holding strings, numbers, dates, lists and nested maps. A document can be up to 1 MiB.

The operations Sitechat uses:

OperationCodeMeaning
Read onecollection(C).document(id).get()Fetch by id; .exists says whether it's there; .to_dict() gives the contents (or None).
Write whole.set(data)Replace the document entirely. Fields not in data are deleted.
Write some fields.set(data, merge=True)Change only the fields given; keep the rest.
Query.where(filter=FieldFilter("tenant_id", "==", t)).stream()All documents matching a condition. A single-field equality query uses an index Firestore builds automatically.
Transaction@firestore.transactionalRead, decide, write; if the document changed in between, Firestore re-runs the function.
Batchdb.batch() ... .commit()Many writes sent together (up to 500).
Server incrementfirestore.Increment(n)The database adds n itself, safe under concurrency.

The free tier (50,000 reads, 20,000 writes and 20,000 deletes a day) shapes several decisions in this phase: caches, writing the digest flag only when it changes, and filtering dates in Python instead of creating paid-for composite indexes.

Analogy

A filing cabinet (the database) with labelled drawers (collections). Each folder (document) has a name on its tab (the id) and can hold any papers you like (fields). You can pull a folder by its name instantly, or ask the clerk for "every folder whose tenant is Pyramid Yogshala". A transaction is pulling a folder, reading it, and only putting your changes in if nobody touched it while you were reading.

4. Tenants: store.py

class TenantStore(ABC):
    @abstractmethod
    def get_by_site_key(self, site_key: str) -> Tenant | None: ...
    @abstractmethod
    def get_by_id(self, tenant_id: str) -> Tenant | None: ...
    @abstractmethod
    def save(self, tenant: Tenant) -> None: ...
    @abstractmethod
    def with_facts_sheet(self) -> list[Tenant]: ...


class FirestoreTenantStore(TenantStore):
    def get_by_site_key(self, site_key):
        query = (self._db.collection(COLLECTION)
                 .where(filter=firestore.FieldFilter("site_key", "==", site_key)).limit(1))
        for doc in query.stream():
            return Tenant(**(doc.to_dict() or {}))
        return None

    def get_by_id(self, tenant_id):
        doc = self._db.collection(COLLECTION).document(tenant_id).get()
        ...

    def save(self, tenant):
        self._db.collection(COLLECTION).document(tenant.tenant_id).set(tenant.model_dump(mode="json"))

    def with_facts_sheet(self):
        tenants = [Tenant(**(d.to_dict() or {})) for d in self._db.collection(COLLECTION).stream()]
        return [t for t in tenants if t.is_active and t.facts_sheet_id]

Phase 0 walked through this class in detail. Two details worth adding: get_by_site_key is a query (site keys aren't the document id), limited to 1; and Tenant(**(doc.to_dict() or {})) turns the stored dictionary back into a validated Tenant (** unpacks a dictionary into keyword arguments; or {} keeps the type checker happy when to_dict() could be None). model_dump(mode="json") does the reverse, turning dates and URLs into plain strings Firestore can store. with_facts_sheet reads every tenant and filters in Python: one read per tenant, "fine for tens of tenants every few minutes".

5. Conversations: the model

class Message(BaseModel):
    role: str          # "user" or "assistant"
    content: str
    id: str = ""       # an assistant reply's id, for feedback
    created_at: datetime = ...

class Question(BaseModel):
    text: str          # the visitor's message, contact details removed
    reply: str         # the assistant's reply, cut to REPLY_LIMIT (500)
    asked_at: datetime = ...
    reply_id: str = ""
    status: str = ""   # set when emailed: answered / partly / not_answered / comment / unchecked

class Conversation(BaseModel):
    conversation_id: str
    tenant_id: str
    messages: list[Message] = Field(default_factory=list)
    summary: str = ""
    questions: list[Question] = Field(default_factory=list)
    questions_emailed: int = 0
    focus: list[str] = Field(default_factory=list)
    digest_due: bool = False
    digest_claimed_at: datetime | None = None
    created_at: datetime = ...
    updated_at: datetime = ...

One document holds a whole conversation. Each field exists for a reason you've met already:

  • messages and summary: the recent history and the running summary of older messages (Phase 4b, §12).
  • questions: every visitor question with the reply, "never summarised or trimmed: the lead email is built from this". questions_emailed counts how many have gone out, so the next email lists only new ones. status keeps each question's label after emailing, so scripts.unanswered needs no model calls.
  • focus: the programme(s) the conversation is about.
  • digest_due, digest_claimed_at: the digest flag and the sweep's lease.
  • updated_at: last activity, which the digest's 15-minute idle check reads.
  • tenant_id is required: "That field is the data boundary this product depends on, so it is required, not optional."

6.1 append_turn and the size caps

MAX_QUESTIONS = 100
MAX_MESSAGES = 100

def _add_turn(convo, user_text, reply_text, is_question, reply_id="") -> None:
    convo.messages.append(Message(role="user", content=user_text))
    convo.messages.append(Message(role="assistant", content=reply_text, id=reply_id))
    del convo.messages[:-MAX_MESSAGES]
    convo.updated_at = datetime.now(timezone.utc)
    if is_question:
        if len(convo.questions) >= MAX_QUESTIONS:
            logger.warning("Question cap reached for %s; not recording", convo.conversation_id)
            return
        convo.questions.append(Question(text=user_text, reply=reply_text[:REPLY_LIMIT], reply_id=reply_id))


def append_turn(self, tenant_id, conversation_id, user_text, reply_text, is_question=False, reply_id=""):
    doc_ref = self._db.collection(COLLECTION).document(self._doc_id(tenant_id, conversation_id))

    @firestore.transactional
    def update_in_transaction(transaction):
        snapshot = doc_ref.get(transaction=transaction)
        data = snapshot.to_dict() if snapshot.exists else {}
        convo = Conversation(**data) if data else Conversation(conversation_id=conversation_id, tenant_id=tenant_id)
        _add_turn(convo, user_text, reply_text, is_question, reply_id)
        convo.updated_at = datetime.now(timezone.utc)
        transaction.set(doc_ref, with_expiry(convo.model_dump(mode="json")))

    update_in_transaction(self._db.transaction())
  • One write for the pair. "Two separate appends means two round trips and two transactions. The pair always happens together, so they belong in one write." This was part of the latency work.
  • _add_turn is shared by the in-memory and Firestore stores, so both behave identically. The difference between them is only how the conversation is loaded and saved.
  • The caps. Firestore refuses a document over 1 MiB, "and a conversation that cannot be written loses every later turn". A message is at most about 2,000 characters and a question about 2,500 with its reply, so 100 of each keeps a conversation well under half that. Summaries normally keep messages near 16; the message cap only bites if summarising keeps failing. del convo.messages[:-100] deletes everything except the last 100. Past 100 questions, it's a script, not a person, so further questions aren't recorded.
  • with_expiry on every full write. tests/test_retention.py checks: a full transaction.set without it would make that document permanent.

6.2 apply_summary: the race-safe replace

@firestore.transactional
def update_in_transaction(transaction) -> bool:
    snapshot = doc_ref.get(transaction=transaction)
    if not snapshot.exists:
        return False
    convo = Conversation(**(snapshot.to_dict() or {}))
    if convo.messages[: len(summarized)] != summarized:
        return False
    convo.summary = summary
    convo.messages = convo.messages[len(summarized) :]
    convo.updated_at = datetime.now(timezone.utc)
    transaction.set(doc_ref, with_expiry(convo.model_dump(mode="json")))
    return True

The summary call takes seconds, and new turns can be stored meanwhile. So this doesn't overwrite the message list with an old copy; it checks the list still starts with the exact messages that were summarised (Pydantic models compare field by field), and if so removes only those from the front, keeping everything after. If not (another summary got there first), it changes nothing and returns False; those messages are summarised next time. It never touches questions.

6.3 Merge writes, and claims

def set_focus(self, tenant_id, conversation_id, focus):
    self._db.collection(COLLECTION).document(doc_id).set(
        with_expiry({"conversation_id": conversation_id, "tenant_id": tenant_id, "focus": list(focus)}),
        merge=True)

def claim_for_digest(self, tenant_id, conversation_id, now, lease) -> bool:
    @firestore.transactional
    def claim_in_transaction(transaction) -> bool:
        snapshot = doc_ref.get(transaction=transaction)
        if not snapshot.exists:
            return False
        if not _claimable(Conversation(**(snapshot.to_dict() or {})), now, lease):
            return False
        transaction.update(doc_ref, {"digest_claimed_at": now})
        return True
    return claim_in_transaction(self._db.transaction())

set_focus is a merge write: it changes one field without reading or rewriting the rest, and works even before the first turn exists (the focus is worked out before the reply; the turn is stored after). The ids are included because a stored conversation must have them. claim_for_digest uses a transaction "so two sweeps reading the same unclaimed document cannot both claim it: the second one's commit fails and is retried against the first one's claim", where _claimable then returns False.

due_for_digest is a single-field equality query, which Firestore indexes automatically: no composite index to create. "Few conversations are due at any time, since the flag is cleared once they are sent." Known gap: it has no ordering, so with more than 40 flagged conversations at once, some could wait; ordering needs a composite index.

7. Facts: the model and the store's cache

class Fact(BaseModel):
    label: str              # "200hr course fee"
    value: str              # "USD 1,450 including accommodation"
    category: str = "general"

class FactSheet(BaseModel):
    tenant_id: str
    facts: list[Fact] = Field(default_factory=list)
    updated_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))

"Deliberately simple key/value entries rather than a rigid schema. Different customers care about different things, and a fixed set of columns would mean a code change every time one of them needs a new field." One document per tenant. updated_at is when the facts were last synced, which the daily sync reads.

_cache: dict[str, tuple[FactSheet | None, float]] = {}

def get_cached_facts(store: FactStore, tenant_id: str) -> FactSheet | None:
    ttl = get_settings().tenant_cache_seconds
    now = time.monotonic()
    entry = _cache.get(tenant_id)
    if entry and (now - entry[1]) < ttl:
        return entry[0]
    sheet = store.get(tenant_id)
    _cache[tenant_id] = (sheet, now)
    return sheet

Facts are sent with every message, so they're cached per server for 60 seconds. A changed price reaches the bot within a minute of the sync.

8. Facts: reading the Google Sheet (facts/sheets.py)

SCOPES = ["https://www.googleapis.com/auth/spreadsheets.readonly"]
RANGE = "A1:C1000"

def _get_service():
    settings = get_settings()
    if os.path.exists(settings.google_service_account_file):
        credentials = service_account.Credentials.from_service_account_file(
            settings.google_service_account_file, scopes=SCOPES)
    else:
        credentials, _ = google.auth.default(scopes=SCOPES)
    return build("sheets", "v4", credentials=credentials)
  • Read-only scope. "The service account can never modify a customer's sheet."
  • Two ways to authenticate. Locally, a service account key file (service-account.json, a secret, never committed). On Cloud Run there's no file, so google.auth.default uses the service's own identity, sitechat-runtime. Either way, a sheet is only readable if the school shares it (as Viewer) with that account's email: sharing, not a permission role, is the gate.
  • The range has no tab name, "so this works whatever the customer named their first tab".
def read_facts(sheet_id: str) -> tuple[list[Fact], list[str]]:
    try:
        service = _get_service()
        result = service.spreadsheets().values().get(spreadsheetId=sheet_id, range=RANGE).execute()
    except Exception as exc:
        raise SheetError(f"Could not read sheet {sheet_id}: {exc}") from exc
    rows = result.get("values", [])
    if not rows:
        raise SheetError("The sheet is empty.")
    header = [cell.strip().lower() for cell in rows[0]]
    if header[:3] != ["category", "label", "value"]:
        raise SheetError(f"Expected columns ['category', 'label', 'value'] in row 1, found {header[:3]}.")
    facts, problems = [], []
    for index, row in enumerate(rows[1:], start=2):
        category = row[0].strip() if len(row) > 0 else ""
        label = row[1].strip() if len(row) > 1 else ""
        value = row[2].strip() if len(row) > 2 else ""
        if not label and not value and not category:
            continue
        if not label:
            problems.append(f"Row {index}: missing Label, skipped."); continue
        if not value:
            problems.append(f"Row {index}: '{label}' has no Value, skipped."); continue
        found = instruction_like(" ".join((category, label, value)))
        if found:
            problems.append(f"Row {index}: '{label}' reads like an instruction to the assistant ({found!r}), skipped.")
            continue
        facts.append(Fact(category=category or "General", label=label, value=value))
    return facts, problems

"Customers edit these sheets themselves, so malformed rows are normal." Each problem becomes a sentence the operator can forward to the school, with the row number as the school sees it (start=2, because row 1 is the header). A row with a label but no value is skipped, not imported blank: "a fact with an empty value is worse than a missing fact: the model would state it confidently." Rows can be short (the Sheets API omits trailing empty cells), hence the length checks.

9. Facts: syncing, with a diff and a safety hold (facts/sync.py)

def _diff(old: list[Fact], new: list[Fact]) -> SyncResult:
    result = SyncResult(total=len(new))
    # Keyed by category and label: the same label ("Private room") appears
    # under several categories, one per course.
    old_by_key = {(f.category, f.label): f.value for f in old}
    new_by_key = {(f.category, f.label): f.value for f in new}
    for key, value in new_by_key.items():
        name = _name(key)
        if key not in old_by_key:
            result.added.append(f"{name}: {value}")
        elif old_by_key[key] != value:
            result.changed.append(f"{name}: '{old_by_key[key]}' -> '{value}'")
    for key in old_by_key:
        if key not in new_by_key:
            result.removed.append(_name(key))
    return result

def _looks_emptied(old, result) -> bool:
    if not old:
        return False
    return result.total == 0 or len(result.removed) > len(old) / 2

Real output: a stored sheet with "Private room" at USD 320 (200-hour) and USD 300 (Mysore), synced from a sheet where the 200-hour price became USD 350, a deposit row has no value, one row tries to instruct the bot, and a location was added:

added    ['General / Location: Rishikesh']

removed  ['Old / Gone']
problems ["Row 4: 'Deposit' has no Value, skipped.",
          "Row 6: 'Tip' reads like an instruction to the assistant ('Ignore all previous instructions'), skipped."]

And the safety hold, with a sheet that suddenly has 1 fact where there were 3:

Facts sync for t held: the sheet has 1 facts, 3 removed of 3. Keeping the old facts;

"A customer changing a price is normal; a price changing unexpectedly needs to be traceable." Every sync logs what changed. And because the scheduled sync runs with nobody watching (careful=True), a sheet that's empty or lost more than half its facts is held: probably an accidental clear or a bad paste, so the bot keeps the old facts and an error is logged. Running sync_facts by hand accepts it.

Run by the same 5-minute call as the lead digest (one free scheduler job for both): tenants whose facts are over 24 hours old are re-read, at most 2 per call, and a sheet that can't be read (most often: not shared with sitechat-runtime) is retried after an hour, not every 5 minutes. It "never raises: the digest it runs alongside matters more".

10. Usage and feedback stores

class FirestoreUsageStore(UsageStore):
    def _doc(self, tenant_id, day):
        return self._db.collection(COLLECTION).document(f"{tenant_id}__{day}")

    def tokens_on(self, tenant_id, day) -> int:
        doc = self._doc(tenant_id, day).get()
        return int((doc.to_dict() or {}).get("tokens", 0)) if doc.exists else 0

    def add_tokens(self, tenant_id, day, tokens) -> None:
        self._doc(tenant_id, day).set(
            {"tenant_id": tenant_id, "day": day, "tokens": firestore.Increment(tokens)}, merge=True)

One small document per tenant per day, incremented on the server "so two instances adding at once both count". The logic that uses it (caching, fail-open) is in Phase 4b, §2.

def _key(f: Feedback) -> str:
    return f"{f.tenant_id}__{f.conversation_id}__{f.reply_id}"

class FirestoreFeedbackStore(FeedbackStore):
    def save(self, feedback):
        self._db.collection(COLLECTION).document(_key(feedback)).set(with_expiry(feedback.model_dump(mode="json")))

    def since(self, tenant_id, when):
        query = self._db.collection(COLLECTION).where(filter=firestore.FieldFilter("tenant_id", "==", tenant_id))
        found = [Feedback(**(d.to_dict() or {})) for d in query.stream()]
        found = [f for f in found if f.updated_at >= when]
        return sorted(found, key=lambda f: f.updated_at, reverse=True)

One record per reply (the id includes the reply id), so "changing the rating replaces it rather than adding a second vote". Only ids are stored: the reply is written in the background, so a fast tap can arrive first; the review script looks up the text later. since filters dates in Python after an equality query, avoiding a composite index (the same choice as LeadStore.since).

11. Four caches, one pattern

Each is a module-level dictionary from key to (value, time stored), checked with time.monotonic(). They live inside one server process, so each Cloud Run instance has its own, and a change takes up to a minute to be seen everywhere. They hold one entry per tenant, so they grow with the number of tenants, not over time (the site-key cache, which could grow with made-up keys, is cleared at 10,000 entries). This is a deliberately simple design: no Redis, no invalidation messages, a bounded staleness.

13. Challenges we faced

1. A full write silently wiped fields

An early append_message wrote the whole conversation with set, deleting fields (todos, facts) that a tool had written moments earlier. Only visible against real Firestore; the in-memory store has no such behaviour. Fix: every read-modify-write is a transaction that reads the latest document first, and single-field updates use merge=True. Lesson (from the notes): this is exactly the gap emulator tests would close, and they're still not built.

2. The facts change log reported a change that didn't happen

The diff keyed facts by label only. With one "Private room" per course, it paired the 200-hour price with the Mysore one and reported a price change. The stored facts were always correct; only the report was wrong, which is still dangerous, because the change log is how unexpected price changes are traced. Fix (16 Oct): keyed and shown as "Category / Label".

3. An emptied sheet would have wiped the bot's facts

Once syncing became automatic and daily (18 Oct), a school clearing its sheet by accident would have left the bot with no prices. Fix: the scheduled sync holds a sheet with no facts or more than half removed, keeping the old facts and logging an error.

4. The production sync needed a different identity

Locally, sheets were read with service-account.json. Production has no such file (and shouldn't), so it reads as the service's own account, sitechat-runtime, and every school's sheet must be shared with that address. Until shared, the sync logs an error hourly and the bot keeps its facts. This is an operational step (and on your open list), not a code change.

5. A conversation could grow until it couldn't be saved

Review finding L1: questions grew without limit against Firestore's 1 MiB cap, so a scripted visitor could make a conversation unwritable. Fix (17 Oct): 100 messages and 100 questions; model-supplied visitor details capped at 200 characters.

6. Thirty type errors, mostly from one optional

When mypy was added to CI (18 Oct), it found 30 type errors, mostly because Firestore's to_dict() can return None and the code passed it straight to Tenant(**...). Fix: to_dict() or {} everywhere. A missing document is already handled by .exists, so it never failed in practice; the type checker made the assumption explicit.

Glossary

Collection / document
A named group in Firestore / one record in it, with an id and JSON-like fields.
Merge write
set(data, merge=True): change only the given fields.
Composite index
A Firestore index on several fields together, needed for some queries and created by hand.
Compound key
An id built from several parts, like tenant__conversation.
Service account
A Google identity for a program rather than a person.
OAuth scope
What an access token is allowed to do, e.g. read-only spreadsheets.
Diff
The list of what was added, changed and removed between two versions.
Emulator
A local program that imitates a cloud service for testing.
Staleness
How out of date cached data can be.
1 MiB
1,048,576 bytes: Firestore's maximum document size.
HttpUrl
A Pydantic type accepting only valid http(s) URLs.

Check yourself

Why does a conversation's document id include the tenant?

So a lookup needs both the tenant and the conversation id; another tenant's valid conversation id names a document that doesn't exist. Isolation by construction.

What's the difference between set(data) and set(data, merge=True), and which bug came from it?

The first replaces the whole document, deleting fields not in data; the second changes only the given fields. A full set once wiped fields a tool had just written.

Why does apply_summary compare the start of the message list before writing?

Turns may have been stored during the slow summary call; it removes only the summarised messages if they're still at the front, and keeps everything after. Otherwise new turns would be lost.

Why are facts with no value skipped instead of stored empty?

The model would state an empty fact confidently; a missing fact makes it say it doesn't know.

The scheduled sync sees a sheet with 2 facts where there were 40. What happens?

It's held: more than half were removed, so the old facts stay and an error is logged. Running sync_facts by hand accepts it.

Why can't the tests catch a missing merge=True?

They use in-memory stores, which don't imitate Firestore's write semantics. Emulator tests would.

Why is "Private room" a problem for a label-only diff?

Several courses each have a "Private room" fact; keyed by label alone, different courses' prices get compared with each other. The key must be category plus label.
