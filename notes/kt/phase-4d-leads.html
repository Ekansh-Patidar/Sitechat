Leads, file by file: capturing a visitor and telling the team

app/leads/ is where Sitechat earns its keep: it pulls contact details out of messages, keeps one lead record per conversation, decides what counts as "something to send", builds the lead email in plain text and HTML, makes visitor-typed links harmless, and drafts a reply for the team. Every file here was shaped by a specific way things went wrong, so this phase is as much about abuse and reliability as about code.

1. extraction.py: finding emails and phone numbers

The file's docstring gives two reasons to extract before the model sees a message: personal data would otherwise sit in the history and be re-sent on every turn (and appear in any log of it); and visitors volunteer details unprompted, mid-sentence, so a rule that only works when the bot asked would miss most of them.

# Deliberately permissive. The aim is to catch what a person would recognise
# as an email, not to enforce RFC 5322. A false positive costs a redaction;
# a false negative costs a lead.
EMAIL_RE = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b")

# International numbers, written however people write them. Requires at least
# 8 digits to avoid matching prices, dates and course hours.
PHONE_RE = re.compile(r"(?:\+\d{1,3}[\s-]?)?(?:\(?\d{2,4}\)?[\s-]?){2,5}\d{2,4}")
MIN_PHONE_DIGITS = 8

EMAIL_PLACEHOLDER = "[email provided]"
PHONE_PLACEHOLDER = "[phone provided]"

Reading the email pattern piece by piece: \b a word boundary; [\w.+-]+ one or more letters, digits, underscores, dots, plus or minus signs (the part before @); @; [\w-]+ the domain name; \. a literal dot; [\w.-]+ the rest (com, co.uk). The phone pattern allows an optional country code (+44), then two to five groups of 2 to 4 digits separated by spaces or hyphens, possibly in brackets, then a final group.

def extract_contact(message: str) -> tuple[str, str, str]:
    email, phone, redacted = "", "", message
    email_match = EMAIL_RE.search(redacted)
    if email_match:
        typed = email_match.group(0)
        redacted = redacted.replace(typed, EMAIL_PLACEHOLDER)
        email = typed.lower()
    for match in PHONE_RE.finditer(redacted):
        candidate = match.group(0)
        if len(_digits(candidate)) >= MIN_PHONE_DIGITS:
            phone = candidate.strip()
            redacted = redacted.replace(phone, PHONE_PLACEHOLDER)
            break
    return email, phone, redacted

The email is removed first, so its digits can't be mistaken for a phone number. Each candidate phone match must have at least 8 digits. The email is stored lowercase (challenge 2). Real output:

'Call me on 9876543210'           -> ('', '9876543210', 'Call me on [phone provided]')
'+91 98765 43210 is my number'    -> ('', '+91 98765 43210', '[phone provided] is my number')
'Price 1,450'                     -> ('', '', 'Price 1,450')
'dates 2027-03-02 to 2027-03-28'  -> ('', '2027-03-02', 'dates [phone provided] to 2027-03-28')
A limitation found while writing this phase

The last line is a real false positive: a date written as 2027-03-02 has 8 digits in groups the pattern accepts, so it's taken as a phone number. The date is redacted from the message, and stored as the lead's "phone", which makes has_contact true and could let a lead email go out with a bogus number. The file's trade-off ("a false positive costs a redaction") assumed the only cost was a redaction; here it also creates a fake contact. Visitors rarely write ISO dates, which is why it hasn't shown up, but it's worth a test and a fix (for example, refusing candidates shaped like YYYY-MM-DD). Not changed in the code: noted here and for the backlog.

def looks_like_valid_email(email: str) -> bool:
    if not email or len(email) > 254: return False
    if email.count("@") != 1: return False
    local, _, domain = email.partition("@")
    if not local or not domain: return False
    if "." not in domain: return False
    if domain.startswith(".") or domain.endswith("."): return False
    if ".." in email: return False
    return True

Two-stage design: extraction is permissive so nothing is missed (and anything email-like is removed from the message either way); this stricter check is the gate before an address is kept, because a malformed one is a lead the team can't reach. Real output: a@b False, a..b@x.com False, sam@x.com True.

looks_like_throwaway checks the domain against 20 disposable-inbox services (Mailinator, 10minutemail, Yopmail...). It's a flag in the email ("throwaway address, may not be real"), not a block, since a real visitor may use one for privacy. Real output: x@mailinator.com → valid True, throwaway True.

2. models.py: the lead

class Lead(BaseModel):
    tenant_id: str
    conversation_id: str
    email: str = ""
    phone: str = ""
    name: str = ""
    country: str = ""
    intended_month: str = ""
    course_interest: str = ""
    items: list[PendingItem] = Field(default_factory=list)
    last_notified_at: datetime | None = None
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    updated_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))

    @property
    def has_contact(self) -> bool:
        return bool(self.email or self.phone)

    @property
    def unsent_items(self) -> list[PendingItem]:
        return [item for item in self.items if item.is_waiting]

    @property
    def has_unsent_items(self) -> bool:
        return bool(self.unsent_items)


class AskedQuestion(BaseModel):
    text: str
    status: str = "unchecked"    # not_answered / partly / answered / comment / unchecked

Two decisions in the docstring: leads are stored separately from conversations ("conversations are operational data; leads are personal data") so they can have their own access rules and retention; and every field is optional except the ids: "A lead with only an email is still a lead, and holding out for a complete record would mean losing most of them." One lead per conversation, filling up over time.

last_notified_at replaced an earlier notified_at that blocked any further email once one was sent. Now whether to send is decided by unsent items and new questions; the time is used only for the cooldown and the "been in touch before" banner.

3. pending.py: items that trigger emails

class ItemKind(str, Enum):
    CONTACT_REQUEST = "contact_request"    # the visitor asked to speak to someone
    UNANSWERED = "unanswered"              # only on older leads

class PendingItem(BaseModel):
    kind: ItemKind
    detail: str
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    sent_at: datetime | None = None
    failed_at: datetime | None = None

    @property
    def is_sent(self) -> bool:
        return self.sent_at is not None

    @property
    def is_waiting(self) -> bool:
        return self.sent_at is None and self.failed_at is None

An Enum is a fixed set of named values; inheriting from str as well makes each value a plain string too, so it saves to Firestore as "contact_request". The docstring separates two purposes: memory for the bot (the server holds the outstanding request and reminds the model each turn, because the model drops intentions when the subject changes), and deciding what goes in an email (unsent items are exactly what's new for a returning visitor).

The key distinction: items trigger emails; lead fields never do. The visitor's country, month and course interest travel with whatever email goes out, but mentioning your country doesn't email the school. An item's life: waiting → sent (it was in an email, or folded into one minutes earlier) or failed (its email failed and retries are off).

4. store.py: merging, transactions, and failing softly

The abstract LeadStore lists what any implementation must do: get, since (for the export script), upsert_fields, add_item, mark_items_sent, mark_items_failed, emails_sent_on and count_email_sent (the daily cap). Two implementations, in memory and Firestore, as everywhere.

4.1 Merging without losing anything

def _merge(lead: Lead, fields: dict) -> Lead:
    """Apply only non-empty values, so nothing already captured is lost."""
    for key, value in fields.items():
        if value and hasattr(lead, key):
            setattr(lead, key, value)
    lead.updated_at = datetime.now(timezone.utc)
    return lead

A later message adding a phone number must not wipe the email captured earlier. Only non-empty values are applied, and only to fields the lead actually has (hasattr), so a stray key from the model can't create new fields. setattr(obj, name, value) sets an attribute whose name is in a variable.

4.2 Every write is a transaction

def upsert_fields(self, tenant_id, conversation_id, fields) -> Lead:
    doc_ref = self._db.collection(COLLECTION).document(self._doc_id(tenant_id, conversation_id))

    @firestore.transactional
    def update_in_transaction(transaction):
        snapshot = doc_ref.get(transaction=transaction)
        lead = (Lead(**(snapshot.to_dict() or {})) if snapshot.exists
                else Lead(tenant_id=tenant_id, conversation_id=conversation_id))
        lead = _merge(lead, fields)
        transaction.set(doc_ref, with_expiry(lead.model_dump(mode="json")))
        return lead

    return update_in_transaction(self._db.transaction())

This is the read-modify-write pattern, made safe. Two things can update a lead at nearly the same moment (the reply path captures an email while the background step marks items sent). Without a transaction, both read the old lead, both change their part, and the second write erases the first's change. With @firestore.transactional, Firestore checks at commit time that the document hasn't changed since it was read; if it has, it re-runs the function on the fresh data. with_expiry stamps the one-year deletion date (Phase 4a, §6). The document id is tenant__conversation: tenant isolation by construction.

4.3 Marking exactly what was sent

def _same_item(a: PendingItem, b: PendingItem) -> bool:
    return (a.kind, a.detail, a.created_at) == (b.kind, b.detail, b.created_at)

def _mark(lead, items, sent: bool, emailed: bool = True) -> None:
    now = datetime.now(timezone.utc)
    for item in lead.items:
        if item.is_waiting and any(_same_item(item, done) for done in items):
            if sent:
                item.sent_at = now
            else:
                item.failed_at = now
    if sent and emailed:
        lead.last_notified_at = now

Only the items passed in are marked, matched by kind, detail and creation time. "The email goes out in the background, and an item added while it was being sent was not in it." emailed=False is for items folded into an earlier email during the cooldown: they count as sent, but last_notified_at stays the time of the real email.

4.4 The daily counter

def count_email_sent(self, tenant_id: str, day: str) -> None:
    # Increment is applied by the server, so two sends at once both count.
    self._db.collection(EMAIL_COUNTS).document(f"{tenant_id}__{day}").set(
        {"tenant_id": tenant_id, "day": day, "count": firestore.Increment(1)}, merge=True)

firestore.Increment(1) asks the database to add one itself, instead of reading the count, adding one in Python and writing it back (which two simultaneous sends would both do from the same starting value, losing one). One small document per tenant per day.

4.5 FailSoftLeadStore

class FailSoftLeadStore:
    def __init__(self, store: LeadStore) -> None:
        self._store = store

    def __getattr__(self, name):
        method = getattr(self._store, name)
        def call(*args, **kwargs):
            try:
                return method(*args, **kwargs)
            except Exception:
                logger.exception("Lead store %s failed; answering without it", name)
                return None
        return call

Leads are secondary to the reply. This wrapper is used on the reply path: any lead-store call that raises is logged (Sentry sees it) and returns None, which callers treat as "no lead". __getattr__ is a Python special method called when an attribute isn't found normally; here it fetches the real store's method and returns a protected version of it, so the wrapper works for every method without listing them. The background step uses the real store, so its failures stay visible and aren't swallowed. A contact request that can't be saved makes contact_team tell the bot to give the business's direct contact details instead.

5. notify.py: sending, to the team only

def can_send(tenant: Tenant) -> bool:
    if not get_settings().resend_api_key.get_secret_value():
        logger.warning("No Resend key configured, skipping lead email")
        return False
    if not tenant.team_email:
        logger.warning("Tenant %s has no team_email set", tenant.tenant_id)
        return False
    return True


def send_lead_email(lead, tenant, summary, questions=()) -> bool:
    if not can_send(tenant):
        return False
    lead, summary, questions, links = _without_live_links(lead, summary, questions)
    settings = get_settings()
    resend.api_key = settings.resend_api_key.get_secret_value()
    params: resend.Emails.SendParams = {
        "from": settings.notification_from_email,
        "to": [tenant.team_email],
        "subject": "New enquiry from your website",
        "text": _format_body(lead, tenant, summary, questions, links),
        "html": render_lead_email(lead, tenant, summary, questions, links),
    }
    # The team's reply goes to the visitor. Never "to" or "cc": see the module docstring.
    if lead.email:
        params["reply_to"] = lead.email.lower()
    try:
        resend.Emails.send(params)
        logger.info("Lead email sent for %s", lead.conversation_id)
        return True
    except Exception:
        logger.exception("Could not send lead email")
        return False
  • Resend is the email-sending service (an API: you send it a dictionary, it delivers the email).
  • can_send is also called by the orchestrator before paying for a summary, so a school without email set up never costs a model call.
  • Two bodies: text (plain, the fallback for email programs that don't show HTML) and html.
  • Recipient is always the school's own team; the visitor is reply_to. The module docstring: "we never send to it ourselves: anyone can type anyone's address into a chat, and copying it in would let a stranger make us email someone, with text they wrote."
  • Returns True or False rather than raising, so the caller decides what a failure means (mark failed, or leave for retry).
  • Leads are copied, not changed, when defanging links (next section): model_copy(update=...) makes an altered copy for display, leaving the stored lead untouched.

6. links.py: links made unclickable

_LINK = re.compile(
    r"\b(?:https?://|www\.)[^\s<>\"']+"
    rf"|\b(?:[a-z0-9-]+\.)+(?:{_TLDS})\b(?:/[^\s<>\"']*)?",
    re.IGNORECASE,
)

def _defang_one(match: re.Match) -> str:
    link = match.group(0)
    link = re.sub(r"^https?(?=://)", lambda m: "hxxp" + m.group(0)[4:].lower(), link, flags=re.IGNORECASE)
    scheme, sep, rest = link.partition("://")
    if not sep:
        scheme, rest = "", link
    host, slash, path = rest.partition("/")
    return f"{scheme}{sep}{host.replace('.', '[.]')}{slash}{path}"

The lead email shows the visitor's own words, so a link they type reaches the team inside an email from us, where it looks more trustworthy than it is: "a way to phish the business through its own chat". Links are defanged, the security-industry convention: http becomes hxxp and dots in the host become [.], so it's still readable but no email program turns it back into a link. Real output:

see https://evil.example/login or www.bad.co and Hatha.Ashtanga
->
see hxxps://evil[.]example/login or www[.]bad[.]co and Hatha.Ashtanga

Bare domains match only with common endings (com, net, in, io...), so "Hatha.Ashtanga" is untouched. Applied to every visitor-written field and the model's summary, not to the contact email and phone (extracted by the server, not free text). When any link was found, the email adds an amber caution note.

7. reply_draft.py: a reply the team finishes

ANSWER_GAP = "[your answer]"
_TO_ANSWER = {"not_answered", "partly", "unchecked"}
MAILTO_LIMIT = 1900

def draft_body(lead, tenant, questions) -> str:
    from app.leads.email_html import questions_for_email      # imported here: email_html imports this module
    first_name = lead.name.split()[0] if lead.name.strip() else ""
    to_answer = [q for q in questions_for_email(lead, questions) if q.status in _TO_ANSWER]
    lines = [f"Hi {first_name}," if first_name else "Hi,", "",
             f"Thank you for getting in touch with {tenant.display_name} through our website."]
    if to_answer:
        lines += ["", "You asked:"]
        for question in to_answer:
            lines += ["", f"- {question.text}", f"  {ANSWER_GAP}"]
    lines += ["", "If you have any other questions, just reply to this email.", "",
              "Warm regards,", tenant.display_name]
    return "\n".join(lines)


def mailto_link(lead, tenant, body) -> str:
    address = quote(lead.email, safe="@")
    subject = quote(draft_subject(tenant))
    with_body = f"mailto:{address}?subject={subject}&body={quote(body.replace(chr(10), chr(13) + chr(10)))}"
    if len(with_body) <= MAILTO_LIMIT:
        return with_body
    return f"mailto:{address}?subject={subject}"

A template, not the model: "A model-written draft would be tempted to fill those gaps, and an invented answer sent under the school's name is the worst outcome." Nothing reaches the visitor without a person checking it, and we never email a visitor-typed address ourselves.

A mailto: link opens a new email in the reader's own program with the address, subject and body filled in. Everything must be URL-encoded (quote: a space becomes %20), and line breaks must be \r\n (chr(13) + chr(10)) for email programs. Real output (start): mailto:sam@example.com?subject=Your%20enquiry%20to%20Pyramid%20Yogshala&body=Hi%20Sam%2C%0D%0A.... Programs cut mailto: links somewhere past 2,000 characters, so a long draft gets a link with just the subject, and the email shows the draft as text to copy.

The import inside the function avoids a circular import: email_html imports this module at the top, so this module can't import email_html at the top too.

8. email_html.py: an email that survives Gmail and Outlook

"Email clients are not browsers: Gmail and Outlook drop <style> blocks, external CSS and most layout features, so this uses nested tables and inline styles only, at the usual 600px width." Every box is a <table> with style="..." written on each element; that's how professional email templates are built, because it's what every email program renders the same way.

def _e(text: str) -> str:
    return escape(str(text), quote=True)

def _accent(tenant: Tenant) -> str:
    colour = tenant.accent_colour or ""
    return colour if re.fullmatch(r"#[0-9a-fA-F]{6}", colour) else DEFAULT_ACCENT

def _text_on(hex_colour: str) -> str:
    r, g, b = (int(hex_colour[i : i + 2], 16) / 255 for i in (1, 3, 5))
    def channel(c):
        return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4
    luminance = 0.2126 * channel(r) + 0.7152 * channel(g) + 0.0722 * channel(b)
    return "#ffffff" if luminance < 0.45 else INK
  • Escaping everything. html.escape turns < into &lt; and quotes into entities, so a visitor who types <img src=x onerror=...> sees it as text in the email; it can never become markup. Every value from a visitor or the model goes through _e.
  • The accent colour is used only if it's exactly # plus six hex digits. Anything else could break out of the style="..." attribute it's written into.
  • Readable button text: _text_on computes the colour's relative luminance (the WCAG formula: each channel corrected for how screens display brightness, weighted by how sensitive eyes are to red, green and blue) and picks white text on dark accents, near-black on light ones.
  • A hidden preview line: the first, invisible <div> is what inboxes show next to the subject ("They asked the team to get in touch. Not answered: Do I need a visa?"), so the team sees what's needed before opening it.
  • Status pills in a colour per status, amber for "Not answered" (gaps in the school's material).

questions_for_email merges the recorded questions with any old-style UNANSWERED items still on leads created before questions were recorded per turn, then sorts by need. request_note writes the green line, repeating the reply time the visitor was shown.

10. Challenges we faced

1. Copying the visitor turned the product into a relay (the biggest one)

Found in the 16 Oct review as finding H1: "Any visitor can make us email any address." With the digest, no contact request was even needed: type a victim's address, ask a question, leave, and 15 to 20 minutes later the victim gets an email from our sender containing the stranger's text. Scripted, a spam or phishing relay, limited only by the rate limit, which would get the email account suspended or the sender blocklisted, killing lead email for every school. (Also, in Resend's test mode the CC couldn't reach real visitors anyway.) Fix (17 Oct): to the team only, reply_to the visitor; a suggested reply the team sends from their own address; an in-chat confirmation card instead of a visitor email; a daily cap per school. An optional automatic receipt to the visitor is planned only after a verified domain and bot protection exist, with a fixed template and strict per-address limits.

2. One capital letter failed a whole email

A visitor typed Sandeep.dot4@... with a capital S. It was stored and CC'd as typed, and Resend's test mode rejected it as "not the account owner's address" (it compares exactly), so the whole lead email failed. Fix: addresses stored lowercase at extraction, and lowercased again when used, so leads stored earlier also send. Mail providers ignore case; APIs may not.

3. Failed emails retried on every message

An unsent item meant every later message retried: another summary call, another Resend call, another error, even for failures that can never succeed. Fix: failed_at on items; retry only behind retry_failed_lead_emails.

4. Designing for email clients

The first email was plain text. The HTML version had to work in Gmail and Outlook, which drop style blocks: tables and inline styles only, escaped content, a validated accent colour, a plain-text fallback. Thirteen tests in test_email_html.py check escaping, ordering, banners and buttons.

5. The follow-up box showed one question of three

A box showed the contact request's reason, written by the model. Only the first request per visit is kept, so a visitor who asked the team about three things saw one there, while all three were already listed under "What they asked". Fix: a one-line "They asked the team to get in touch" and the complete list below; the inbox preview names the first question needing an answer.

6. Links as a phishing channel

Visitor-typed links arrived clickable inside an email from us. Fix (18 Oct): defanged everywhere visitor text appears, with a caution note.

7. A lead store outage failed the visitor's reply

Known gap, written as a strict expected-failure test: if the leads collection was down, the whole turn failed. Fix (18 Oct): FailSoftLeadStore on the reply path.

8. Background emails on throttled CPU

With Cloud Run's request-based billing, CPU is only fully allocated while a request is in flight; the immediate lead email runs after the response, so it ran slowly: emails arrived 12 to 24 seconds after the turn. The digest isn't affected (it sends inside a request). Option recorded in the backlog: instance-based billing, at higher cost. Accepted for now, to confirm before relying on it for a customer.

9. A fake email flood could exhaust the quota for everyone

Resend's free plan allows 100 emails a day across all schools. Fix: 50 per school per day; over that, emails are held for the next day's digest, with no model call while held.

Glossary

Redaction
Replacing sensitive text with a placeholder, like [email provided].
False positive / negative
Wrongly matching something / wrongly missing it.
Disposable (throwaway) email
A temporary inbox from services like Mailinator.
Enum
A fixed set of named values.
Read-modify-write
Reading data, changing it in code and writing it back; needs a transaction when others may write at the same time.
Server-side increment
Asking the database to add to a number itself, so simultaneous adds aren't lost.
__getattr__
A Python method called for attributes not found normally; used to wrap every method of another object.
Reply-To
The address replies go to, different from the sender.
Defanging
Making a link unclickable but readable (hxxp, [.]).
Phishing
Tricking someone into clicking a malicious link or giving details.
mailto: link
A link that opens a new email with address, subject and body filled in.
URL encoding
Writing special characters as %XX so they're safe inside a URL.
HTML escaping
Turning <, >, & and quotes into entities so text can't become markup.
Relative luminance
A standard measure of a colour's perceived brightness, used to pick readable text colours.

Check yourself

Why is the email removed from a message before looking for a phone number?

So digits in the address can't be mistaken for a phone number, and so the email is redacted once, cleanly.

A visitor mentions they're from Germany. Does the school get an email?

No. Country is a lead field: it travels with any email but never triggers one. Only pending items (contact requests) and, via the digest, unemailed questions do.

Why does _merge skip empty values?

So a later update that doesn't mention the email (empty) can't wipe the email captured earlier.

Why does count_email_sent use firestore.Increment(1)?

Two simultaneous sends would both read the same count and both write count + 1, losing one. The server-side increment adds each one.

Where is FailSoftLeadStore used, and why not in the background step too?

On the reply path, so a lead-store outage doesn't stop the visitor getting an answer. In the background, failures should stay visible and be handled by _isolated, not turned into "no lead".

Why is the suggested reply a template?

An AI draft would be tempted to fill in answers; an invented answer under the school's name is the worst outcome.

Why are links in the email written as hxxp://evil[.]example?

So a link a visitor typed can't be clicked from an email that looks like it comes from a trusted source; it stays readable for the team to judge.

Why does the HTML email use tables and inline styles?

Gmail and Outlook drop style blocks and most layout CSS; nested tables with inline styles render the same everywhere.
