How to read this phase

Two journeys run through these files. Ingest happens once per document, when you run scripts/ingest.py: file → text → chunks → programme tags → Firestore and Pinecone. Retrieve happens on every message that needs it: question → embedding → Pinecone search → (optional keyword search, fusion, rerank) → focus blend → top 5. The sections follow those journeys. Real outputs come from running these functions on the school's real documents on this laptop (no paid calls).

1. The shape of a chunk (documents/models.py)

class Chunk(BaseModel):
    chunk_id: str                 # "course-200hr__4": document id + position
    tenant_id: str
    document_id: str
    document_title: str
    heading_path: list[str] = Field(default_factory=list)
    text: str
    position: int
    programme: str = ""           # from programmes.yaml; "" for general sections

    @property
    def heading(self) -> str:
        return self.heading_path[-1] if self.heading_path else self.document_title

    def to_searchable_text(self) -> str:
        if not self.heading_path:
            return self.text
        return " > ".join(self.heading_path) + "\n\n" + self.text


class Document(BaseModel):
    document_id: str
    tenant_id: str
    title: str
    source: str                   # filename it came from
    chunk_count: int = 0
    ingested_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))

The comment at the top of the file states the principle: "A chunk ... carries enough context to be understood alone, because at retrieval time it will be read without the surrounding document." Three fields serve that: the heading path (every heading above it, outermost first), the document title, and the programme tag.

  • Stable ids. chunk_id is the document id plus position, so re-ingesting a document overwrites its chunks instead of duplicating them.
  • to_searchable_text is what gets embedded: heading path, blank line, text. A chunk about anatomy is findable by "anatomy" even if its text never says it.
  • Field(default_factory=...): a fresh empty list (or the current time) for each new object. Writing = [] would share one list between all chunks, a classic Python trap Pydantic protects against.

2. Reading files (documents/loaders.py)

SUPPORTED_SUFFIXES = {".md", ".txt"}

def load_text_file(path: Path) -> tuple[str, str]:
    if path.suffix.lower() not in SUPPORTED_SUFFIXES:
        raise LoaderError(f"{path.name}: unsupported type. ...")
    try:
        text = path.read_text(encoding="utf-8")
    except UnicodeDecodeError as exc:
        raise LoaderError(f"{path.name}: not valid UTF-8 text") from exc
    except OSError as exc:
        raise LoaderError(f"{path.name}: could not read ({exc})") from exc
    if not text.strip():
        raise LoaderError(f"{path.name}: file is empty")

    title = path.stem.replace("-", " ").replace("_", " ").title()
    for line in text.split("\n"):
        if line.startswith("# "):
            title = line[2:].strip()
            break
    return title, text

Only this layer knows about file formats: "adding PDF or website support later means adding a function here and nothing else". Every failure becomes one kind of error, LoaderError, with a human-readable message, so the ingest script can print "Skipped: ..." and carry on with the other files. The title is the first # Heading, else the filename made readable (course-200hr.md → "Course 200Hr").

In Sitechat

Turning a school's website into clean Markdown is deliberately not part of the product. It needs site-specific rules about 20% of the time, which would pile up in the codebase one per customer. The plan is a separate tool producing reviewable Markdown plus a report of contradictions between pages; the product only ingests Markdown.

3. Splitting along headings (documents/chunker.py)

HEADING_RE = re.compile(r"^(#{1,6})\s+(.*)$")
MAX_CHUNK_CHARS = 1800
MIN_CHUNK_CHARS = 200

def chunk_markdown(text, tenant_id, document_id, document_title) -> list[Chunk]:
    lines = text.split("\n")
    heading_stack: list[tuple[int, str]] = []
    buffer: list[str] = []
    sections: list[tuple[list[str], str]] = []

    def flush() -> None:
        body = "\n".join(buffer).strip()
        if body:
            sections.append(([h[1] for h in heading_stack], body))
        buffer.clear()

    for line in lines:
        match = HEADING_RE.match(line)
        if match:
            flush()
            level = len(match.group(1))
            title = match.group(2).strip()
            while heading_stack and heading_stack[-1][0] >= level:
                heading_stack.pop()
            heading_stack.append((level, title))
        else:
            buffer.append(line)
    flush()
    ...   # each section's body goes through _split_long_text, then becomes Chunk(s)

How the heading stack works, using the 200-hour document's structure:

Line readStack after it (level, title)
# 200-Hour ... Teacher Training[(1, 200-Hour ...)]
## Curriculum[(1, 200-Hour ...), (2, Curriculum)]
### Pranayama[(1, ...), (2, Curriculum), (3, Pranayama)]
### Bandhaspop level ≥ 3 → [(1, ...), (2, Curriculum), (3, Bandhas)]
## Daily Schedulepop level ≥ 2 → [(1, ...), (2, Daily Schedule)]

When a heading arrives, everything collected so far is flushed as a section labelled with the current stack; then any headings at the same or deeper level are popped (we've left them), and the new heading is pushed. Text lines go into the buffer. The result: every section knows its full path.

def _split_long_text(text: str) -> list[str]:
    paragraphs = [p.strip() for p in text.split("\n\n") if p.strip()]
    pieces, current = [], ""
    for paragraph in paragraphs:
        candidate = f"{current}\n\n{paragraph}" if current else paragraph
        if len(candidate) > MAX_CHUNK_CHARS and current:
            pieces.append(current)
            current = paragraph
        else:
            current = candidate
    if current:
        if pieces and len(current) < MIN_CHUNK_CHARS:
            pieces[-1] = pieces[-1] + "\n\n" + current
        else:
            pieces.append(current)
    return pieces

Sections over 1,800 characters are split at paragraph breaks, never mid-sentence; a leftover under 200 characters is merged into the piece before it. Every piece keeps the section's heading path. Real output on the 200-hour document: 18 chunks, from 110 to 1,362 characters (none needed splitting). Across the school's three documents: 18 + 58 + 19 = 95.

4. Section keys (documents/sections.py)

def section_key(document_id: str, heading_path: list[str]) -> str:
    return f"{document_id} | {' > '.join(heading_path[1:])}"

def matches(key: str, label: str) -> bool:
    if label.startswith("="):
        return key == label[1:]                 # exactly that section
    if label.endswith("|"):
        return key.startswith(label)            # anywhere in that document
    return key == label or key.startswith(label + " > ")   # that section or below

A section key names a section by its document and headings (minus the title, which is the first heading): pyramid-yogshala-website | 300-Hour ... (Rishikesh) > Fees. Keys come from headings, so they survive re-chunking, unlike chunk ids. They're used twice: to tag chunks with programmes (next section), and by the evaluation to label correct answers (Phase 4f). Note the " > " in the third rule: "Fees" must not match "Fees and discounts", only "Fees" or "Fees > ...".

6. Ingest (documents/ingest.py) and the chunk store

def make_document_id(filename: str) -> str:
    stem = Path(filename).stem.lower()
    return re.sub(r"[^a-z0-9]+", "-", stem).strip("-")

def ingest_file(path, tenant_id, store, vector_store=None, catalogue=None) -> IngestResult:
    title, text = load_text_file(path)
    text = strip_invisible(text)
    document_id = make_document_id(path.name)
    chunks = chunk_markdown(text=text, tenant_id=tenant_id, document_id=document_id, document_title=title)
    if not chunks:
        raise LoaderError(f"{path.name}: produced no usable text")
    if catalogue is not None:
        for chunk in chunks:
            chunk.programme = catalogue.programme_for(section_key(chunk.document_id, chunk.heading_path))
    document = Document(document_id=document_id, tenant_id=tenant_id, title=title,
                        source=path.name, chunk_count=len(chunks))
    store.save_document(document, chunks)
    if vector_store is not None:
        vector_store.delete_document(tenant_id, document_id)
        vector_store.upsert_chunks(tenant_id, chunks)
    warnings = []
    for chunk in chunks:
        found = instruction_like(chunk.text)
        if found:
            warnings.append(f"{' > '.join(chunk.heading_path)}: {found!r}")
    return IngestResult(document_id=document_id, title=title, chunk_count=len(chunks), warnings=warnings)
  1. Stable document id from the filename (Course 200hr.md → course-200hr): ingesting the same file twice replaces it.
  2. Invisible characters stripped (hidden instructions have no place in documents).
  3. Chunk, then tag each chunk with its programme.
  4. Save text to Firestore (FirestoreChunkStore.save_document first deletes the document's old chunks, so a re-ingest producing fewer chunks leaves no stale ones, then writes all in one batch).
  5. Replace vectors: delete the document's old vectors in Pinecone, then embed and upsert the new ones.
  6. Screen every chunk for text addressed to a model; matches are returned as warnings and printed by the script as "CHECK, reads like an instruction to the bot". Ingested anyway, because we prepare these files ourselves; the warning is for a human to look.

Why keep chunk text in Firestore as well as Pinecone? Pinecone holds it for fast retrieval; Firestore holds the source of truth, "so the text survives re-indexing", and it's what inspect_chunks, the evaluation's label check and (when enabled) BM25 read.

7. Embeddings (retrieval/embeddings.py)

def _get_client() -> OpenAI:
    global _client
    if _client is None:
        settings = get_settings()
        # Short timeout: an embedding takes well under a second, and the
        # SDK default (600 s, two retries) would outlast the request.
        _client = OpenAI(api_key=settings.openai_api_key.get_secret_value(),
                         timeout=settings.embedding_timeout_seconds,     # 5 s
                         max_retries=settings.openai_max_retries)        # 1
    return _client

def embed_texts(texts: list[str]) -> list[list[float]]:
    if not texts:
        return []
    response = _get_client().embeddings.create(model=get_settings().embedding_model, input=texts)
    return [item.embedding for item in response.data]

def embed_query(text: str) -> list[float]:
    return embed_texts([text])[0]

Batching: embed_texts sends many texts in one call, so ingesting 58 chunks is one round trip, not 58. A separate client from the chat one, with its own short timeout: the SDK's default of 600 seconds with two retries would outlast Cloud Run's whole request. The model is text-embedding-3-small (1,536 numbers); the opening comment warns that changing it means re-embedding everything, because vectors from different models can't be compared.

8. Pinecone (retrieval/vector_store.py)

The same interface-and-implementations pattern as every store: an abstract VectorStore with upsert_chunks, search and delete_document; an InMemoryVectorStore for tests (dot product over a list); and PineconeVectorStore.

@dataclass

    text: str
    document_title: str

citation_title is the label each passage carries into the prompt: its full heading path, document title included. The docstring explains why: "a section called 'Fees' exists once per programme, and its text does not name the programme, so '7-Day Yoga Retreat (Rishikesh) > Fees' is what stops the model reading one programme's prices as another's."

  • Lazy index handle. pc.index() makes a network call. Doing it at start-up would add seconds before the container can serve, paid on every cold start, so it's done on first use (a @property that fills a hidden field once).

  • The document API. The index was created with a document schema (a field named embedding of type dense vector, scripts/create_index.py), so writes, searches and deletes must go through index.documents. The heading path is stored as one string ("A > B > C") and split back on read.
  • Deleting a document uses a filter on the stored document_id field. On a first ingest the namespace doesn't exist yet, which Pinecone reports as "not found": expected, so logged at debug level, not as an error.

9. Triage (retrieval/triage.py)

MAX_SKIP_LENGTH = 25
CONVERSATIONAL = re.compile(
    r"^(?:"
    r"hi|hey|hello|yo|namaste|"
    r"ok|okay|k|sure|right|fine|got it|understood|i see|"
    r"thanks|thank you|thanks a lot|ty|cheers|"
    r"bye|goodbye|see you|take care|"
    r"yes|yeah|yep|no|nope|"
    r"good morning|good afternoon|good evening|"
    r"great|nice|cool|perfect|awesome|lovely"
    r")"
    r"[\s!.,?]*$",
    re.IGNORECASE,
)

def needs_retrieval(message: str) -> bool:
    text = message.strip()
    if not text:
        return False
    if len(text) > MAX_SKIP_LENGTH:
        return True
    return not CONVERSATIONAL.match(text)

Skips retrieval (about two seconds from outside the database's region) only when a message is short and is entirely a conversational phrase, with optional punctuation. The ^ and $ anchor the pattern to the whole message, so "thanks, but what about the fees?" still retrieves. Deliberately conservative: "a missed retrieval produces a wrong answer while an unnecessary one only costs time." Real output: hi, thanks!, ok, namaste skip; yes please retrieves (not in the list, so it errs safe).

RRF_K = 60

def reciprocal_rank_fusion(result_lists, top_k, weights=None):
    if weights is None:
        weights = [1.0] * len(result_lists)
    if len(weights) != len(result_lists):
        raise ValueError("weights must have one entry per result list")
    scores, by_id = {}, {}
    for results, weight in zip(result_lists, weights):

            by_id.setdefault(result.chunk_id, result)
    ordered = sorted(scores.items(), key=lambda pair: pair[1], reverse=True)

reranker.py

_MIN_SECONDS_BETWEEN_CALLS = 6.5

def rerank(query, candidates, top_k):
    settings = get_settings()
    if not candidates or not settings.cohere_api_key.get_secret_value():
        return candidates[:top_k]
    documents = [c.to_searchable_text_for_rerank() for c in candidates]
    if settings.throttle_rerank:
        wait = _MIN_SECONDS_BETWEEN_CALLS - (time.monotonic() - _last_call_at)
        if wait > 0:
            time.sleep(wait)
        ...
    try:
        response = _get_client().rerank(model=settings.rerank_model, query=query,
                                        documents=documents, top_n=min(top_k, len(documents)))
    except Exception:
        logger.exception("Reranking failed, falling back to fusion order")
        return candidates[:top_k]
    ...

Three safety behaviours: no key → return the candidates unchanged; any error → fall back to the first stage's order ("a degraded answer beats no answer"); and a throttle for Cohere's trial keys (10 calls a minute), so evaluation runs measure real reranking instead of silently falling back. The throttle sleeps the whole process, so it must be off in production (THROTTLE_RERANK=false is set in cloudbuild.yaml).

Challenge we faced: a reranker that isn't running looks like a reranker that changes nothing

In the latest saved evaluation (18 Oct), "vector + rerank" scored exactly the same as "vector only" on every metric. Because rerank quietly returns the candidates unchanged when no Cohere key is set, identical numbers most likely mean the reranker wasn't active in that run, not that it's neutral. The 10 Oct measurement, with a working key, showed it hurting (MRR 0.96 → 0.90). Lesson: a silent fallback protects production but can fool a measurement; check the configuration actually ran.

11. Which programme? (programmes/focus.py)

Decided "by matching names, never by a model call: it runs on every message". Three rules, in order (from the file's docstring):

  1. Programmes named in this message become the focus. If the message compares ("vs", "or", "compare", "difference", "which", "better", "between"...), the earlier focus is kept alongside them.
  2. A family word ("retreat", "teacher training") keeps the earlier focus if it's within that family; otherwise the focus becomes the family, or nothing if the family is too large.
  3. Otherwise the earlier focus carries over.

A focus of more than 3 programmes (MAX_FOCUS) counts as no focus: retrieval searches everything.

Normalising text

def normalise(text: str) -> str:
    text = unicodedata.normalize("NFKD", text)
    text = "".join(c for c in text if not unicodedata.combining(c))     # drop accents
    text = text.lower().replace("-", " ").replace("_", " ")
    text = re.sub(r"(\d+)\s*(h|hr|hrs|hour|hours)\b", r"\1 hour", text)
    text = re.sub(r"(\d+)\s*(d|day|days)\b", r"\1 day", text)
    text = re.sub(rf"(\d+)\s*({OTHER_HOURS})(?![a-z])", r"\1 hour", text)  # horas, Stunden, घंटे...
    text = re.sub(rf"(\d+)\s*({OTHER_DAYS})(?![a-z])", r"\1 day", text)    # dias, Tage, दिन...
    text = re.sub(r"[^a-z0-9 ]+", " ", text)
    return " ".join(text.split())

Real output: normalise("300-HRS Course, 7-days") → "300 hour course 7 day". NFKD splits "á" into "a" plus an accent mark, and the next line drops the marks, so "días" becomes "dias". Unit words in about fifteen languages are spelled one way, so "¿Cuánto cuesta el curso de 300 horas?" finds the 300-hour course. The lists are sorted longest first, so "horas" isn't read as "hora" plus "s".

The matcher (_find) looks for each alias surrounded by spaces in the normalised message (padded with a space at each end), longest aliases first, and removes each match from the text, so "havelock teacher training" isn't also counted as "teacher training". The "teacher training on Havelock" case shows family narrowing: "teacher training" names 7 programmes and "havelock" names 2; the programmes in both are just 200-havelock.

wants_overview returns True when a message names a group too large to focus on, or compares within a group ("the 200-hour in Rishikesh or on Havelock?"): then the "Programmes at a glance" section is added, so the bot doesn't give one course's length or location for all of them.

12. The pipeline (retrieval/pipeline.py): retrieve and blend

def retrieve(tenant_id, query, vector_store, chunk_store=None, config=None,
             programmes=None, overview=False) -> list[SearchResult]:
    settings = get_settings()
    config = config or RetrievalConfig.from_settings(settings)
    candidates = config.candidates

    query_vector = embed_query(query)
    vector_results = vector_store.search(tenant_id, query_vector, candidates)

    keyword_results = []
    if config.use_keyword and chunk_store is not None:
        keyword_results = keyword_search(tenant_id, query, chunk_store, candidates)

    if keyword_results:
        fused = reciprocal_rank_fusion([vector_results, keyword_results], candidates,
                                       weights=[settings.vector_weight, config.keyword_weight])
    else:
        fused = vector_results[:candidates]

    if config.use_rerank:
        final = rerank(query, fused, settings.retrieval_top_k)
    else:
        final = fused[: settings.retrieval_top_k]

    if programmes:
        focused = [result for programme in programmes
                   for result in vector_store.search(tenant_id, query_vector, FOCUS_POOL,
                                                     programmes=[programme])]
        general = vector_store.search(tenant_id, query_vector, GENERAL_POOL)
        final = blend(focused, general, settings.retrieval_top_k, programmes, settings.focus_boost)

    if overview:
        table = vector_store.search(tenant_id, query_vector, 1, programmes=[OVERVIEW])
        present = {r.chunk_id for r in final}
        final = final + [t for t in table if t.chunk_id not in present]

    logger.info("Retrieved for %s (focus %s): ... %s", ..., [r.chunk_id for r in final])
    return final

"The one retrieval path, used by production and the eval." With today's settings, the active steps are: embed once; vector search for 5; if there's a focus, search each focused programme's top 3 (a Pinecone filter on programme) and the top 20 overall, and blend; if a group was named, add the overview section. The chunk ids chosen are logged, which is where sources went when they were removed from the widget.

KEEP_ONE, KEEP_EACH, FOCUS_POOL, GENERAL_POOL = 1, 2, 3, 20

def blend(focused, general, top_k, programmes, boost) -> list[SearchResult]:
    best = {}
    for result in focused + general:
        score = result.score + (boost if result.programme in programmes else 0.0)
        if result.chunk_id not in best or score > best[result.chunk_id][0]:
            best[result.chunk_id] = (score, result)
    ranked = sorted(best.values(), key=lambda pair: pair[0], reverse=True)

    keep = KEEP_ONE if len(programmes) == 1 else KEEP_EACH
    chosen = {}
    for programme in programmes:
        mine = [pair for pair in ranked if pair[1].programme == programme]
        for pair in mine[:keep]:
            chosen[pair[1].chunk_id] = pair
    for pair in ranked:
        if len(chosen) >= top_k:
            break
        chosen.setdefault(pair[1].chunk_id, pair)
    return [r for _, r in sorted(chosen.values(), key=lambda pair: pair[0], reverse=True)]

How blending decides, step by step: merge both lists without duplicates; add focus_boost (0.08) to the similarity of sections belonging to the focused programme; rank everything; guarantee a minimum per focused programme (1 for a single focus, 2 for each side of a comparison); fill the rest by rank. Real output, with the 300-hour course in focus and a laundry question where the school-wide Laundry section is genuinely the best match:

focused: 300>Fees 0.50, 300>Dates 0.48            (+0.08 each → 0.58, 0.56)
general: About>Laundry 0.61, 300>Fees 0.50, Booking 0.49, Rooms 0.47
blend(top_k=3) -> [('About>Laundry', 0.61), ('300>Fees', 0.5), ('300>Dates', 0.48)]

The school-wide section wins on merit, and the focused course still gets its places. That balance took three iterations to find (challenge 4 below).

13. Configurations (evaluation_config.py)

@dataclass
class RetrievalConfig:
    name: str
    use_keyword: bool = True
    use_rerank: bool = True
    keyword_weight: float = 1.0
    candidates: int = 20

    @classmethod
    def from_settings(cls, settings: Settings) -> "RetrievalConfig":
        return cls("production", use_keyword=settings.use_keyword_search,
                   use_rerank=settings.use_rerank, keyword_weight=settings.keyword_weight,
                   candidates=settings.retrieval_candidates)

VECTOR_ONLY = RetrievalConfig("vector only", use_keyword=False, use_rerank=False)
VECTOR_RERANK = RetrievalConfig("vector + rerank", use_keyword=False, use_rerank=True)
HYBRID_EQUAL = RetrievalConfig("hybrid, equal weights", use_keyword=True, use_rerank=False, keyword_weight=1.0)
HYBRID_WEIGHTED = RetrievalConfig("hybrid, keyword at 0.3", use_keyword=True, use_rerank=False, keyword_weight=0.3)
FULL = RetrievalConfig("hybrid 0.3 + rerank", use_keyword=True, use_rerank=True, keyword_weight=0.3)

A @dataclass is a lightweight class whose fields and constructor are generated from the annotations. A @classmethod receives the class (cls) instead of an instance, a common way to write alternative constructors: RetrievalConfig.from_settings(settings) builds exactly what production runs. The presets keep 20 candidates because that's what the original comparison used; production uses 5. Kept in app/ rather than evaluation/ because it describes the pipeline, which production may one day switch per tenant.

14. Challenges we faced

1. Standard advice made retrieval worse

Hybrid search and reranking, measured on 10 Oct: vector-only MRR 0.96 against 0.70 to 0.90 for the others. Both switched off with the numbers in the config. Re-measured on 18 Oct with 95 chunks and 82 questions: vector-only 0.86, hybrid 0.78 to 0.81. The details are the strongest interview story in the project (Phase 3, §10 to 11).

2. BM25's IDF collapsed to zero

A score > 0 filter discarded correct matches whenever a word appeared in half the chunks. Fixed by filtering on shared words. Only measurement could see it (Phase 3, §10).

3. The evaluation ran different code from production

evaluation/run.py had its own copy of the retrieval steps that always ran fusion and read the candidate count from settings, which had since dropped from 20 to 5. Re-running it would have silently changed the comparison. Fix (15 Oct): retrieve takes an optional RetrievalConfig; the evaluation calls the production function; re-run, every config matched the recorded numbers. A "production" row built from settings was added, so the eval measures exactly what ships. Lesson: an evaluation must exercise the real code path, or it measures something else.

4. Getting programme focus right took three tries
  1. Fixed slots (three sections from the focused programme, then the rest from everything): from a real chat, with the 300-hour in focus, all five passages were the 300-hour's, so "is there laundry?" (asked twice) got "I don't have details", although the school's About section says a laundry machine is free to use. Two causes: a carried-over focus put the programme's name into the search text, pulling even the general search towards it; and the remaining slots could also come from the focused programme.
  2. Dropped the name from the search text; filled the rest only from outside the focus, from a wider pool of 20. Then "how many halls?" still got three 300-hour sections and no Campus section, and "what about 200h yttc?" (five courses, too many to focus on) got no side-by-side view, so the bot gave the Rishikesh course length to Havelock too.
  3. Rank everything by relevance with a small boost for the focus, a minimum of one section per focused programme (two per side of a comparison), and an overview section for broad groups. The boost was tuned against the evaluation: 0.0 / 0.05 / 0.08 / 0.12 / 0.2 gave overall MRR 0.82 / 0.85 / 0.87 / 0.86 / 0.85; 0.08 kept follow-up questions at 1.00 and general questions at 0.96, while higher values started losing general ones.

And putting the overview first pushed better matches down for any question naming a group ("what will I learn on the 200-hour course?"): semantic MRR 0.86 → 0.69. It's now added after the ranked results. Lesson: every rule of thumb ("give the focus 3 slots") failed on a real conversation; a tuned score with a measured parameter held up.

5. "Fees" chunks were indistinguishable

Labels showed only the last heading, so every programme's fee section read "... — Fees". Fixed by labelling with the full heading path including the document title (§8).

6. Re-ingesting failed after the first time

delete_document used Pinecone's plain vectors endpoint, which returns 400 once a namespace exists on an index with a document schema. So re-ingesting any document, or ingesting a second one, failed after the first ingest. delete_tenant's namespace delete had the same bug. Fix (16 Oct): deletes go through index.documents; confirmed against the live index that the document_id filter matches all of a document's chunks.

7. General questions failed until the documents were restructured

School-wide facts (rooms, Wi-Fi, laundry, food, travel) were scattered through programme sections. They were moved into their own "school-general" document, one sub-topic per section; general-question retrieval went from MRR 0.46 to 0.90 (backlog 80). The evaluation's labels listed both the old and new places, so one question set measured before and after. Lesson: retrieval quality is often a content-structure problem, not an algorithm problem.

8. Latency: retrieval on every message, far from the data

Retrieval took about 2 seconds and ran even on "hi" and "thanks"; Pinecone searches took 1.4 to 2.6 s because the index is in AWS us-east-1 and testing was from India. Fixes: triage, running retrieval in parallel with the conversation read, fetching 5 candidates instead of 20, and the lazy index handle so cold starts don't pay for it.

Glossary

Ingest
Loading documents into the system: read, chunk, tag, embed, store.
Heading path
All the headings above a chunk, outermost first.
Heading stack
The chunker's running list of headings in scope while reading a file.
Section key
document | Heading > Sub: a re-chunking-proof name for a section.
Programme catalogue
A school's programmes.yaml: programmes, their names, families, sections, overview.
Alias / context alias
A name visitors use for a programme / a short name that counts only within the same family.
Family
A word naming a group of programmes ("retreat").
Normalising
Rewriting text into one standard form before matching (lower case, units, no accents).
Focus boost
0.08 added to the similarity of the focused programme's sections.
Upsert
Insert, or update if the id already exists.
Document schema (Pinecone)
An index layout with named fields; requires the documents API.
Lazy initialisation
Creating something on first use instead of at start-up.
Dataclass
A class whose constructor and fields are generated from its annotations.
Throttle
Spacing calls out deliberately to stay under a rate limit.
Fallback
A simpler behaviour used when the preferred one fails.

Check yourself

Why do chunk ids include the position, and why is that not enough for evaluation labels?

So re-ingesting overwrites rather than duplicates. But positions shift whenever a document's text changes, so labels use section keys (document plus headings), which only change when headings do.

The chunker reads ## Daily Schedule while the stack is [(1, Title), (2, Curriculum), (3, Bandhas)]. What's the stack after?

[(1, Title), (2, Daily Schedule)]: everything at level 2 or deeper is popped, then the new heading is pushed.

Why is "7 day" a context alias but "7 day retreat" a normal alias?

"7 day" alone is ambiguous ("I can only come for 7 days"); it only means the 7-day retreat when the conversation is already about retreats.

With the 300-hour course in focus, why can the school-wide Laundry section still be returned first?

blend ranks everything by similarity plus a small boost (0.08) for the focus. A clearly better school-wide match beats the boosted programme sections; the focus is still guaranteed at least one place.

Why must the reranker's throttle be off in production?

It sleeps the whole process between calls to fit a trial key's limit; in production every visitor would queue behind it.

Why did re-ingesting a document fail after the first ingest, and what fixed it?

Deletes used Pinecone's plain vectors endpoint, which returns 400 on a document-schema index once the namespace exists. Deletes now go through index.documents with a document_id filter.

What does "the evaluation calls the production function" protect against?

An evaluation that measures a different code path from what ships, e.g. always fusing, or using a different candidate count.
