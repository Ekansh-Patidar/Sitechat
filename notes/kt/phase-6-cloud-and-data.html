2. Containers and the Dockerfile, line by line

A container image is a sealed package of everything the program needs to run: a slice of an operating system, Python, the libraries, and our code. Run it anywhere that runs containers, and it behaves the same. The Dockerfile is the recipe for building it. Here is Sitechat's whole Dockerfile, with its comments shortened:

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app/ app/
COPY static/ static/

RUN useradd --create-home --uid 1000 appuser && chown -R appuser:appuser /app
USER 1000

EXPOSE 8080

CMD exec uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8080} --workers 1
LineWhat and why
FROM python:3.12-slimStart from an official image with Python 3.12 on a minimal Debian. Pinned to a minor version: "python:3.12" plain "would silently move under you and turn a deploy into an unplanned upgrade". Slim leaves out compilers and tools we don't need.
ENV PYTHONDONTWRITEBYTECODE=1, PYTHONUNBUFFERED=1Don't write .pyc files (useless in a container); don't buffer output, because "buffering means logs appear late or not at all on a crash".
WORKDIR /appThe folder inside the image where everything goes.
COPY requirements.txt then RUN pip install, before copying the codeLayer caching. Docker caches each step; a step is re-run only if its inputs changed. Dependencies change rarely and code often, so this order means editing code doesn't reinstall every package. --no-cache-dir keeps pip's download cache out of the image.
COPY app/ app/, COPY static/ static/Only the service and the widget. Tests, scripts, docs, notes and secrets are kept out by .dockerignore (which lists .env, service-account.json, scripts/, tests/, docs/...).
useradd ... USER 1000Run as an ordinary user, not root: "If the process is ever compromised, it should not own the filesystem it is running on." By number, "so the platform can tell it is not root without a passwd file".
EXPOSE 8080Documentation: the port the app listens on.
CMD exec uvicorn ...The command the container runs. Shell form so ${PORT:-8080} is expanded (Cloud Run sets PORT and health-checks exactly that port; :-8080 is the default when unset). exec replaces the shell with uvicorn so uvicorn receives the shut-down signal itself (challenge 4). One worker, because "Cloud Run scales by adding instances, so a second worker inside one container competes for the same CPU rather than adding capacity". --host 0.0.0.0: listen on all interfaces (Phase 1, §3).

The image installs requirements.txt only. Test tools live in requirements-dev.txt, which adds them on top (-r requirements.txt), so pytest and friends never ship to production. Both files list exact versions (fastapi==0.142.4), so a build next month installs the same code as today.

3. Cloud Run: what "serverless containers" means

Cloud Run takes a container image and runs it behind an HTTPS address, starting more copies (instances) when traffic rises and stopping them when it falls, down to zero. You don't manage machines; you pay for the time instances are handling requests. Sitechat's real settings, read from the live service:

autoscaling.knative.dev/maxScale: '10'           # at most 10 instances
run.googleapis.com/startup-cpu-boost: 'true'     # extra CPU while starting
containerConcurrency: 80                         # up to 80 requests at once per instance
serviceAccountName: sitechat-runtime@sitechat-511008.iam.gserviceaccount.com
timeoutSeconds: 60                               # a request is cut off at 60 s

plus, from cloudbuild.yaml: --min-instances=0 (scale to zero when idle), --memory=1Gi, --cpu=1, --allow-unauthenticated (anyone may call it: the widget needs that; protection is per route, as earlier phases showed).

What each setting means for the code:

  • 60-second timeout → every model call has a deadline inside 40 s (Phase 4b, §8), and the digest sends at most 10 emails per run.
  • Up to 10 instances → rate-limit counters, caches and the token-usage cache are per instance, so the worst case is 10 times each limit (Phase 4a, §3).
  • 80 requests per instance, but routes are ordinary functions running in a thread pool of about 40 threads, so under heavy load requests would queue inside the container. Recorded as the reason for a future load test and possible async rewrite (backlog 45).
  • Request-based billing → CPU is fully available only while a request is in flight. Background tasks after the response (the immediate lead email) run on throttled CPU, which is why those emails arrived 12 to 24 s late.
  • Instances are disposable → nothing important may live only in memory; everything is in Firestore, and memory holds only caches.

Google's front end (the "GFE") sits in front of the container: it terminates HTTPS, appends the visitor's address to X-Forwarded-For, and reserves some paths like /healthz (two challenges from Phase 4a).

Analogy

A food truck company. You hand them your recipe and sealed ingredients box (the image). When customers queue, they send out more trucks (instances), up to ten; when nobody's around, every truck goes back to the depot (scale to zero). Each truck can serve 80 people at once but has one cook. And a truck that's just been sent out has to heat up before the first order (a cold start).

4. Cold starts, and how the digest fixed them

With --min-instances=0, the first request after a quiet spell must wait for a new instance: download the image, start Python, import every library, run the lifespan. Measured on 15 Oct after the smoke test timed out: 43.4 seconds (about 37 s for the container and Python to start, 6 s for the app), with 16 cold starts in the previous 36 hours, so real visitors met them.

Options recorded: --min-instances=1 (always one instance warm, roughly ₹1,500 a month: against your constraints), CPU boost during start-up (turned on), and making start-up itself cheaper (lazy Pinecone index handle, smaller image).

Then the lead digest went live, calling the service every 5 minutes. Measured on 17 Oct from logs: in the 15.7 hours after the job started (including 11.7 quiet overnight hours), 190 calls, all 200, never more than 5.7 minutes apart, and no idle cold start at all; the only new instances were deploys. With request-based billing an idle instance isn't charged. So a free scheduled job removed the cold-start problem as a side effect. The first request after each deploy still goes to a fresh instance.

Say it in an interview

"Scale-to-zero gave us a measured 43-second cold start. The paid fix was a minimum instance. Instead, the lead-digest job we needed anyway hits the service every five minutes, which in practice keeps an instance warm: we checked the logs and saw no idle cold starts over a 16-hour window. We kept startup CPU boost on and made the Pinecone client lazy so a new instance does less before serving."

5. Cloud Build: tests, then build, then deploy

CI/CD means continuous integration (automatically checking every change) and continuous delivery (automatically releasing it). Sitechat has two systems: GitHub Actions runs all the checks on every push and pull request (Phase 7), and a Cloud Build trigger deploys every push to main. The whole cloudbuild.yaml:

steps:
  # Tests first: a failing test stops the build here.
  - name: 'python:3.12-slim'
    entrypoint: bash
    env: ['ENVIRONMENT=development', 'GCP_PROJECT_ID=test-project', 'PIP_DISABLE_PIP_VERSION_CHECK=1']
    args: ['-c', 'pip install --quiet --no-cache-dir -r requirements-dev.txt && python -m pytest -q']

  - name: 'gcr.io/cloud-builders/docker'
    args: ['build', '-t', 'us-central1-docker.pkg.dev/$PROJECT_ID/sitechat/api:$SHORT_SHA',
           '-t', 'us-central1-docker.pkg.dev/$PROJECT_ID/sitechat/api:latest', '.']

  - name: 'gcr.io/cloud-builders/docker'
    args: ['push', '--all-tags', 'us-central1-docker.pkg.dev/$PROJECT_ID/sitechat/api']

  - name: 'gcr.io/google.com/cloudsdktool/cloud-sdk'
    entrypoint: gcloud
    args:
      - 'run'
      - 'deploy'
      - 'sitechat-api'
      - '--image=us-central1-docker.pkg.dev/$PROJECT_ID/sitechat/api:$SHORT_SHA'
      - '--region=us-central1'
      - '--allow-unauthenticated'
      - '--service-account=sitechat-runtime@$PROJECT_ID.iam.gserviceaccount.com'
      - '--set-secrets=OPENAI_API_KEY=OPENAI_API_KEY:latest,PINECONE_API_KEY=PINECONE_API_KEY:latest,...'
      - '--set-env-vars=ENVIRONMENT=production,GCP_PROJECT_ID=$PROJECT_ID,THROTTLE_RERANK=false,LEAD_DIGEST_INVOKER=lead-digest@$PROJECT_ID.iam.gserviceaccount.com'
      - '--min-instances=0'
      - '--max-instances=10'
      - '--memory=1Gi'
      - '--cpu=1'
      - '--timeout=60'
  1. Test. In a clean Python 3.12 container, install the dev requirements and run pytest, with the same settings as GitHub Actions. Any failure stops the build: nothing is built or deployed. Checked in a clean container: about 45 seconds, and a failing test exits 1. (Browser tests skip themselves: Playwright isn't installed there.)
  2. Build the image, tagged twice: with $SHORT_SHA (the commit's short id, so every deploy names exactly which code it is) and latest.
  3. Push both tags to Artifact Registry.
  4. Deploy that exact image (by commit tag, not latest) to Cloud Run, with the service account, secrets, environment and limits. Cloud Run creates a new revision and moves traffic to it once it starts; the previous revision stays available for rollback (gcloud run services update-traffic ... --to-revisions=PREVIOUS=100, written in notes/runtime-sa-setup.md).

Each step runs in its own container image (name:): Python for tests, Docker for building, the Cloud SDK for deploying. $PROJECT_ID and $SHORT_SHA are filled in by Cloud Build. tests/test_cloudbuild.py checks the file itself: for instance, that every secret in --set-secrets is granted to the runtime account in the setup notes.

6. Secrets: .env locally, Secret Manager in production

A secret is anything that grants access: API keys, the Sentry DSN, a service-account key file. Rules Sitechat follows:

  • Never in code or git. .env and service-account.json are in .gitignore and .dockerignore. CI runs gitleaks over the entire history on every push to catch an accidental commit (none found).
  • Locally: .env, read by pydantic-settings. The current file defines ENVIRONMENT, LOG_LEVEL, GCP_PROJECT_ID, OPENAI_API_KEY, GOOGLE_SERVICE_ACCOUNT_FILE, PINECONE_API_KEY, PINECONE_INDEX_NAME, COHERE_API_KEY, RESEND_API_KEY, NOTIFICATION_FROM_EMAIL and SENTRY_DSN (names only; the values are never shown).
  • In production: Secret Manager stores each secret, versioned. --set-secrets=OPENAI_API_KEY=OPENAI_API_KEY:latest tells Cloud Run to inject the latest version as an environment variable when an instance starts. The image contains no keys. Real list: COHERE_API_KEY, OPENAI_API_KEY, PINECONE_API_KEY, RESEND_API_KEY, SENTRY_DSN.
  • In code: SecretStr, so printed settings show asterisks (Phase 4a, §2).
  • No file key in production. The Google Sheets reader uses service-account.json only if the file exists; on Cloud Run it uses the service's own identity, so there's no long-lived key to leak there.

7. Service accounts and least privilege

A service account is a Google identity for a program. IAM (Identity and Access Management) grants identities roles, each a bundle of permissions. The principle of least privilege: give each identity only what it needs, so a compromise can do as little as possible.

AccountUsed byAllowed
sitechat-runtimeThe API on Cloud Runroles/datastore.user (Firestore) on the project; roles/secretmanager.secretAccessor on each of the five secrets only. Plus Viewer on each school's facts sheet, by sharing.
lead-digestCloud Scheduler signs its calls as this accountNothing. The endpoint only checks who signed the token.
Default compute accountCloud Build (likely)Editor on the project (broad); allowed to deploy as sitechat-runtime.

What the runtime account does not need, per notes/runtime-sa-setup.md: logging (Cloud Run collects output itself), Pinecone/OpenAI/Resend/Cohere/Sentry (API keys, not Google permissions), the digest token check (Google's public keys), and Sheets (sharing, not a role).

Challenge we faced: the service ran with near-owner power

The 16 Oct review (finding H2) confirmed the service ran as the default compute account, which held roles/editor, roles/run.admin and roles/artifactregistry.writer. "Any code execution in the app or a dependency would give near-owner control of the project: read every secret, delete Firestore, deploy other images." Fix (17 to 18 Oct): the dedicated sitechat-runtime account with only Firestore and its five secrets; the setup commands documented to run before pushing (or the deploy fails safely and the old revision keeps serving); a test that every deployed secret is granted. Still open, optional: a separate Cloud Build account and removing Editor from the default one.

8. Cloud Scheduler and signed calls

Real job, from the live project:

ID                    SCHEDULE     STATE
sitechat-lead-digest  */5 * * * *  ENABLED

*/5 * * * * is cron syntax: five fields for minute, hour, day of month, month, day of week; */5 in the minute field means "every 5 minutes", and * means "every". The job sends POST /internal/lead-digest with an OIDC token signed by Google for the lead-digest account and the audience sitechat-lead-digest, which the endpoint verifies (Phase 4a, §10). The creation command is in notes/lead-digest-setup.md, along with how to run it once by hand (gcloud scheduler jobs run ...), what to look for in the logs, and how to pause it.

9. Firestore in production

NAME       LOCATION_ID  TYPE
(default)  us-central1  FIRESTORE_NATIVE
  • Same region as Cloud Run (us-central1), so database calls from the server stay inside one Google region.
  • Native mode: the document database with transactions and real-time features (the alternative "Datastore mode" is an older API).
  • Indexes: every query Sitechat makes is a single-field equality (tenant_id ==, site_key ==, digest_due ==), which Firestore indexes automatically. Date filtering and sorting happen in Python, so no composite indexes needed creating.
  • TTL deletion: real state, gcloud firestore fields ttls list: 
    NAME       STATE
expire_at  ACTIVE
expire_at  ACTIVE
    Two policies are active. notes/retention-setup.md lists three (conversations, leads, feedback; the feedback one was added last, on 18 Oct "run it if not yet"), so one still needs its single gcloud command. Worth checking which.
  • Backups: point-in-time recovery restore has never been tested (backlog 59).
  • Security rules: the server uses the admin SDK, which bypasses Firestore's client security rules; rules matter only if a browser client is ever pointed at the database. The review listed checking they deny everything as an open item.

11. Logs and observability

Observability is being able to tell what a running system is doing from the outside. Sitechat's three sources:

  • Structured logs: one JSON object per line, with severity, message, logger, request_id, tenant_id, conversation_id (Phase 4a, §5). In Logs Explorer, jsonPayload.tenant_id="pyramid-yogshala" shows a school's activity; severity>=ERROR shows problems.
  • Timing lines: every reply logs "read+retrieve X s, model Y s"; retrieval logs embed and search milliseconds and the chunk ids chosen; persistence logs its duration. Measured in production: read plus retrieve 0.5 to 1.5 s, model 0.7 to 1.9 s.
  • Sweep summaries: Lead digest sweep: {'due': ..., 'sent': ..., 'held': ...} every 5 minutes, and facts sync counts.

Missing (backlog 22): alerting, meaning a message to you when the error rate or latency rises. Today, problems are seen by looking.

12. Costs and the free tier

Within free tiers today. The guard rails that keep a surprise bill from happening:

  • Firestore reads: caches for tenants, facts and catalogues; negative caching of bad site keys; the refusal limit; the digest flag written only when it changes.
  • OpenAI: the per-tenant daily token budget, the 600-token reply cap, triage skipping retrieval, and every expensive call happening last.
  • Email: the daily cap per school.
  • Cloud Run: scale to zero; max 10 instances.
  • Cloud Build: the test step adds about 2 minutes per build, inside the free 120 build-minutes a day.

14. Challenges we faced

1. A missing space blocked a deploy

A deploy failed with permission denied on secrets. SENTRY_DSN had been created but its access grant never ran, because the command had a missing space: SENTRY_DSN--member=... was parsed as one word. Lesson: when a cloud command "succeeds" oddly, read exactly what it did; and test that every secret is granted (tests/test_cloudbuild.py now does).

2. An account that didn't exist yet

Setting up the deploy failed because the default compute service account didn't exist: Google creates it lazily, the first time the Compute Engine API is enabled.

3. Deploys weren't gated on tests

Review finding H3: the Cloud Build trigger built and deployed every push to main, whatever GitHub Actions said, so a red test run still shipped. Fix (17 Oct): pytest is the first build step; a failure stops everything.

4. The container ignored the shut-down signal

The CMD ran uvicorn under /bin/sh, which became process 1 and didn't pass on Cloud Run's SIGTERM ("please stop"). After 10 seconds the platform killed everything (exit code 137), mid-request and mid-email. Checked in a local container: before, docker stop killed it with 137 and no shutdown log; after adding exec, uvicorn is process 1, logs "Shutting down", finishes in-flight work, and exits 0, with PORT still honoured.

5. Test packages in the production image

Review finding M7: pytest and several heavy packages were in the image. Split into runtime and dev requirements (666 → 650 MB). Cohere's dependencies stay, because rerank is a supported switch and Cohere imports lazily (1.5 ms), so it costs image size, not start time. A related trap: pip freeze > file in PowerShell writes UTF-16, which pip then can't read; the files are kept UTF-8 (noted in CLAUDE.md).

6. Python 3.14 locally, 3.12 everywhere else

The local virtual environment runs Python 3.14 (confirmed when generating this course), while CI, Cloud Build and the image use 3.12. A 3.14-only feature would pass locally and fail in deploy. The Cloud Build test step now catches that before anything ships; recreating the local environment on 3.12 is your call.

7. The 43-second cold start

Section 4: found because the smoke test's first run timed out; measured from logs; solved, as a side effect, by the 5-minute digest job, confirmed from logs two days later.

8. A faster deploy image, tried and reverted

The full Cloud SDK image (about 1.2 GB) took about 70 seconds to download when a new version came out; a slim one (about 350 MB) also has gcloud run deploy. Tried on 19 Oct as a trial commit and reverted with the rest of that day's changes at your request.

9. Geography is latency

Measured during development from India: Firestore writes 1.8 to 4.7 s, Pinecone searches 1.4 to 2.6 s, partly because the services sit in the US (Firestore and Cloud Run in us-central1, Pinecone in us-east-1). Moving writes to background tasks and parallelising removed most of the visitor's wait; the rest is distance.

Glossary

Container image
A sealed package of an OS slice, runtime, libraries and code.
Dockerfile
The recipe for building an image, one instruction per line.
Layer caching
Docker reusing unchanged build steps; why dependencies are installed before code is copied.

One running copy of the container / one deployed version of the service.

How many requests one instance handles at once (80 here).
CI/CD
Automatically checking every change / automatically deploying it.

Google's store for container images.
Secret Manager
Google's versioned store for secrets, injected at run time.
IAM role
A named bundle of permissions granted to an identity.
Least privilege
Granting only the permissions actually needed.
Cron
A five-field schedule syntax (minute, hour, day, month, weekday).
Observability
Understanding a running system from its logs, metrics and traces.
Rollback
Sending traffic back to a previous working revision.

Check yourself

Why does the Dockerfile copy requirements.txt and install it before copying app/?

Layer caching: dependencies change rarely, code often. With this order, a code change reuses the cached install layer instead of reinstalling everything.

What does exec in the CMD fix?

Without it, the shell is process 1 and doesn't pass on SIGTERM, so the container is killed mid-request. With it, uvicorn receives the signal and shuts down cleanly.

Why is the image deployed by its commit tag rather than latest?

So each deploy names exactly which code is running, and a rollback or comparison is unambiguous.

How do API keys get into the running container without being in the image?

Secret Manager stores them; --set-secrets makes Cloud Run inject them as environment variables at start-up; pydantic-settings reads them.

The runtime account has no role for Google Sheets. How does it read schools' sheets?

Each school shares its sheet (Viewer) with the account's email address. Sharing is the permission.

What does */5 * * * * mean?

Every 5 minutes, every hour, every day.

Why did scale-to-zero stop causing cold starts without paying for a minimum instance?

The 5-minute digest job keeps calling the service, so an instance stays warm; logs showed no idle cold starts afterwards.

Name three things missing before a first customer, and what each needs.

A verified email domain (a domain), a production/development split (a second project), alerting (monitoring policies); also bot protection (Turnstile, a domain), shared rate limits (Redis), emulator tests.
